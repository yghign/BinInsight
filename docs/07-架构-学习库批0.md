# 1. 整体架构与数据流

## 1.1 路由落点与站内存量关系

### 结论：新增 `/library`，`/cases` 并存，互链不合并

| 项 | 落点 | 职责 |
|---|---|---|
| `/library` | **新增** `src/app/library/page.tsx` | 学习库首页：列表 + 四维筛选 + 搜索三件套 + 学习地图 + 进度条（§1.1~1.4 PRD） |
| `/library/[id]` | **新增** `src/app/library/[id]/page.tsx` | 知识卡 / 方法论卡详情（形态 A / B / M） |
| `/cases` | **零改动** | 现有 4 个二进制沙箱分区（04 号 PRD 成果）+ 本地深度案例 |
| `/cases/sandbox/[id]` | **零改动** | 现有 SandboxPlayer 闯关 |
| 互链方向 | **仅学习库 → 主线/沙箱** | 学习库二进制主题卡（第 11 章缓冲区溢出/格式化字符串）链到 `/cases/sandbox/*`；学习库首页加「返回 8 级主线」 |
| 主线 → 学习库 | **批 0 不做**（Q5 让位红线） | 待用户明确批准 L7 红线例外后再加 |

**为什么不合进 `/cases`**（三条，均基于实读）：
1. `/cases/page.tsx:120-147` 刚落地「新手区 gets+fmtstr / 进阶区 UAF+ROP」的语义分区，82 类工具书接入会让该分区消失；
2. `/cases` 的卡片是 `SandboxCard`（`cases/page.tsx:33-82`），字段是 `SandboxCase`；学习库卡片字段是 `LearningEntry`，两者渲染/筛选/进度模型不同，合并需要一个大而全的判别组件，反而破坏模块化；
3. 用户要求「无顺序、想学哪个都行」，独立路由能让这条规则在 UI 上更干净地表达。

### 静态导出约束（实读 `next.config.js`）
```
output: 'export' + basePath: '/BinInsight' + images.unoptimized: true
```
→ 无服务端、无 API route；新增 `/library/[id]` **必须**实现 `generateStaticParams()`（参照现有 `src/app/cases/sandbox/[id]/page.tsx:10-12` 的写法）；`fetch` 相对路径在 basePath 下易错，因此**批 0 不引入运行时 fetch**（见 §1.3）。

## 1.2 数据流（单向，无服务端）

```
内容创作（逐章 Markdown，docs/06 Part 2 形态）
        ↓ 人工结构化（每章确认后一次性转化）
src/data/library/ch0.ts / ch1.ts / ...      ← 完整 8 段内容，按章分文件
        ↓ 构建期静态 import（列表只取轻量元数据）
src/data/library/index.ts                   ← LIBRARY_LIST：id/title/oneLiner/hazard/difficulty/scene/pinyin/kind/format
        ↓
/app/library/page.tsx (服务端) → LibraryBrowser ('use client')
        ├─ 搜索/筛选：纯前端对 LIBRARY_LIST 做过滤（不加载完整正文）
        └─ 点卡片 → /library/[id] (服务端) → 按章动态 import 完整条目 → 渲染
        ↓
术语解释：TermButton → GlossaryProvider → getGlossEntry(id)（glossary.ts 全量静态 import，批 0 不懒加载）
进度：useLibraryProgress → src/lib/storage.ts 独立 key（本地，不跨设备、不控可达性）
```

**三条数据流硬规则**：
1. **列表与正文分离**：首页只加载 `LIBRARY_LIST`（轻量元数据），完整 8 段正文按章 chunk 在点开详情时才加载（§1.3 实现）；
2. **无运行时网络请求**：批 0 无 `fetch`、无 API、无外部运行时依赖；站外真实案例只是 `<a>` 链接；
3. **进度不参与可达性**：`explored` 只用于卡角小勾和进度条，任何筛选/搜索/路由都不读它。

## 1.3 逐章交付如何落地：「加一章」= 追加数据 + 一行映射

### 批 0 就按章拆文件，后续章节不需要改架构

```
src/data/library/
├── types.ts          # 所有 interface / type（§2 定稿）
├── index.ts          # LIBRARY_LIST 汇总 + getLibraryItem(id) + LOADERS 映射
├── ch0.ts            # 第 0 章：1 张坐标系知识卡（形态 A + 3 题）
├── ch1.ts            # 第 1 章：9 条（4 低 / 5 中高）
└── methodCards.ts    # 批 0 只放 M01（三条铁律）；M02~M09 按 PRD §6.1 分批追加
```

**「加一章」要改的文件（固定 3 处，全是追加）**：
1. 新增 `src/data/library/ch<N>.ts`，`export const ch<N>Entries: LearningEntry[]`；
2. `src/data/library/index.ts` 的 `LIBRARY_LIST` 追加该章元数据条目；
3. `src/data/library/index.ts` 的 `LOADERS` 映射追加 `ch<N>: () => import('./ch<N>')` **一行**。

**关键实现细节（静态导出的分 chunk 正确性）**：动态 `import()` 的路径**不能写成模板字符串**（`import(\`@/data/library/ch${n}\`)` 会让 webpack 生成 context module、失去精确分 chunk）。必须用静态映射：

```ts
// src/data/library/index.ts —— 加一章只加一行
export const LOADERS: Record<string, () => Promise<{ default?: unknown; [key: string]: unknown }>> = {
  ch0: () => import('./ch0'),
  ch1: () => import('./ch1'),
  // ch2: () => import('./ch2'),   ← 批 1 追加这一行
};
```

这样：`output:'export'` 下每个 `ch*.ts` 被打包为独立 chunk；首页不加载正文；详情页只加载所属章的 chunk；路径全静态、无 basePath 问题。

### 术语懒加载为什么批 0 不做（§6.6 的技术修正）

- **现状**：`TermButton.tsx:5-6` 从 `GlossaryProvider` + `@/data/glossary` 静态 import；`GlossaryProvider.tsx:40-49` 的 `openTerm()` 是**同步**函数，走 `getGlossEntry()` 的 O(1) 查表（`glossary.ts:329-331`）。
- **若按 PRD §6.6 改为按需 fetch/chunk**：必须把 `openTerm` 改成 async、引入 loading 态、改 `TermButton`/`TermPopover` props —— 这三个组件被**主线 L0~L7 和现有 4 个沙箱案例共用**，任何改动都要做全站回归。
- **收益评估**：批 0 后术语共 89 条（45 现有 + 44 新增，10 条草案中 `cwe`/`shell` 复用不新增），纯文本几 KB，首屏无感。
- **结论与触发条件**：批 0 **不动** `TermButton` / `GlossaryProvider` / `TermPopover` 的加载机制；当术语总数 **>200 条** 或实测首屏 JS 明显变大时，再单独立任务拆 `glossary` chunk + 完整主线回归。届时的实现方案（供未来参考）：按章拆 `src/data/glossary/ch*.ts`，`openTerm` 改为 `async` + 动态 import + 缓存 Map，老词走同步快速路径。

## 1.4 术语与内容的文件组织规范

| 内容 | 文件 | 命名规范 | 说明 |
|---|---|---|---|
| 漏洞卡正文 | `src/data/library/ch<N>.ts` | `ch0` / `ch1` / … / `ch16`，与章节号一致 | 一章一文件，随章追加 |
| 轻量列表 | `src/data/library/index.ts` | `LIBRARY_LIST`、`LOADERS`、`getLibraryItem()` | 唯一汇总出口 |
| 方法论卡 | `src/data/library/methodCards.ts` | `METHOD_CARDS`，id 形如 `m01-three-laws` | 批 0 仅 M01 |
| 术语 | `src/data/glossary.ts` | 保持现有单一数据源，追加 `related?: string[]` | **不按章拆文件**（见 §1.3） |
| 章术语锚点 | 各 `ch<N>.ts` 条目内的 `terms: string[]` | 元素为 `GlossEntry.id` | 详情页渲染「本案例术语」行 |

**术语数据口径**（采信 PRD §5.2）：新增词条 `level` 一律 `'l8'`（不属主线、不考核）；`plain` ≤2 句；`anchor` 统一 `/reference/glossary#<id>`；`aliases` 2~5 个；低频词不单列、inline 白话；高频词建 `related`。

## 2.4 拼音搜索匹配函数（纯前端、零依赖）

**类型与签名**（新增 `src/lib/library-search.ts`）：

```ts
export interface LibraryListItem {          // 轻量列表项，LIBRARY_LIST 的元素
  id: string; title: string; kind: 'vuln' | 'method';
  chapter: number; difficulty?: LibraryDifficulty;
  scene?: LibraryScene[]; hazard?: HazardStar;
  aliases: string[]; signals: string[];
  pinyin: PinyinIndex;
  oneLiner: string; format?: 'card' | 'interactive';
}

export type HitReason = '标题' | '别名' | '信号' | '拼音';
export interface SearchHit {
  item: LibraryListItem;
  reason: HitReason;
  /** 命中片段（前后各 ~20 字） */
  snippet: string;
  /** 片段内命中起止下标，供高亮分段 */
  start: number; end: number;
}

export function normalizeQuery(q: string): string;
export function matchItem(item: LibraryListItem, normalizedQuery: string): SearchHit | null;
export function searchLibrary(query: string, items: LibraryListItem[]): SearchHit[];
export function searchSuggestions(query: string, items: LibraryListItem[]): LibraryListItem[];  // 最多 6 条
export function highlightParts(text: string, query: string): { text: string; hit: boolean }[];
```

**匹配伪码**（采信 PRD §4.5.1/§4.5.2，逐条对应）：

```
normalizeQuery(q):
  return q.trim().toLowerCase()

matchItem(item, q):
  if q == '': return null
  // 1) 中文/英文直接包含（标题 → 别名 → 信号，优先级即此顺序）
  for fieldName of ['title', ...aliases, ...signals]:
     idx = fieldName.toLowerCase().indexOf(q)
     if idx >= 0: return hit(reason = 字段类别, start=idx, end=idx+q.length)
  // 2) 拼音：输入去空格 + 小写
  nq = q.replace(/\s+/g, '')
  for source of [pinyin.full.replace(/\s+/g,''), pinyin.joined, pinyin.initial]:
     if source.includes(nq): return hit(reason='拼音', start=0, end=title.length)
     // 拼音命中时高亮中文标题（读者真正要看的），不是拼音串
  return null
```

- 「`sql zhu ru`」→ 去空格 `sqlzhuru` → 命中 `joined` ✓；「`zhu ru`」→ `zhuru` → 命中 `joined` ✓；「`sqlzr`」→ 命中 `initial` ✓；中文/英文直接 `includes` ✓。
- **高亮的安全实现（修正 PRD 的 DOM 思路）**：PRD §4.5.2 写「先 HTML 转义再插 `<mark>`」；在 React 中**不用 `dangerouslySetInnerHTML`**，改为 `highlightParts()` 把文本切成 `[{text,hit}]` 段，组件里映射为 `<mark>{part.text}</mark>` 或纯文本节点——React 默认转义，**天然防 XSS**，且无需额外依赖。
- **建议排序**（采信 §4.5.3）：前缀匹配 > 包含匹配 > 拼音匹配；同级内标题短者优先（不使用点击量，避免引入额外状态）；最多 6 条；键盘上下 + 回车直达。
