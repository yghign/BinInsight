## 章导语

**共同本质**：攻击者提供的内容被受害者的浏览器当作代码执行，或借受害者身份越权生效——如同把访客递来的便条直接当成指令照做。这类问题发生在浏览器一侧，绕过服务器边界，直接伤害使用者。

**与注入类（上一主题）的区别**：注入发生在**服务器上**——SQL 语句、系统命令、模板被篡改，服务器本身执行了攻击者的数据；客户端攻击发生在**受害者的浏览器里**——服务器可能毫发无损、甚至完全合规，用户却已经受害。因此客户端攻击常被称作「借刀杀人」：攻击者借的是每个受害者自己的浏览器。这也解释了为什么本主题的修复重心是「输出编码」而不是「输入拦截」——危险发生在数据被渲染的那一刻。

**和主线的连接**：主线是「输入太长，盖住了旁边的返回地址」——数据**物理上**越界；客户端攻击是「输入被浏览器当成代码或结构」——数据**语义上**越界。主线 L2「先找危险调用」在这里的对应动作是：找 `innerHTML`、`document.write`、`eval`、`location` 这类前端危险汇聚点，看用户数据有没有流进去。

**共同防护思路（四层，缺一不可）**：

1. **输出编码（根治）**：按上下文（HTML 正文 / 属性 / JS / URL / CSS）分别编码，让数据永远只是文字，不被当作标记解析。
2. **白名单净化**：富文本只留标签/属性白名单（如 DOMPurify）；跳转目标用映射表或相对路径白名单。
3. **权限与隔离收敛**：Cookie 安全属性（HttpOnly / Secure / SameSite）、限制页面被嵌入、第三方脚本最小化、消息来源校验。
4. **兜底**：CSP（限制脚本来源）、SRI（校验第三方资源完整性）；WAF 仅作兜底，不替代前三层。

## 2.1 跨站脚本（XSS）　`危险度 ★★★★☆（存储型 ★★★★★）`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: xss` ｜ `chapter: 2` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web` ｜ `hazard: 4` ｜ `aliases: 跨站脚本, XSS, Cross-Site Scripting, 反射型 XSS, 存储型 XSS, DOM 型 XSS` ｜ `pinyin: {full: 'kua zhan jiao ben', joined: 'kuazhanjiaoben', initial: 'kzjb'}` ｜ `related: csrf, open-redirect, client-storage-leak, m01-three-laws` ｜ `source: demo`

**难度判定**：三问法命中 0~1 项——概念一句「输入未经编码回显、被浏览器当脚本执行」能讲明白；信号是输入 `<b>test</b>` 看见加粗；无协议/状态机前置。与 SQL 注入同属「高危险、低门槛」（危险度 ★★★★☆，学习门槛低）。

**oneLiner（一句话）**：用户可控内容未经输出编码就进入 HTML 页面，浏览器将其当作脚本执行，攻击者可借受害者身份操作页面、窃取凭证。

**cause（成因与位置）**：输出位置把用户数据拼进页面而未做上下文编码。输出上下文决定载荷形态与修复方式：

| 输出上下文 | 示例 | 说明 |
|---|---|---|
| HTML 正文 | `<div>用户输入</div>` | 标签被解析，需 HTML 实体编码 |
| HTML 属性 | `<input value="用户输入">` | 引号逃逸后可挂 `on*` 事件 |
| JS 上下文 | `var a = "用户输入";` | 引号/反斜杠逃逸进脚本 |
| CSS 上下文 | `style="background:url(用户输入)"` | 可注入样式规则 |
| URL 上下文 | `<a href="用户输入">` | `javascript:` 伪协议可执行 |

**where（高发位置）**：搜索框回显、错误页、跳转参数、评论/昵称/工单/后台列表（存储型）、富文本编辑器、Markdown 渲染、PDF 预览、SVG 上传、文件名展示、导出文件与邮件通知。

**kinds（分类）**：

| 类型 | 数据流向 | 特点 | 常见位置 |
|---|---|---|---|
| 反射型 | 请求 → 服务端 → 立刻回显 | 需诱导点击，一次性 | 搜索框、错误页、跳转参数 |
| 存储型 | 请求 → 入库 → 他人访问时输出 | 无需交互、可蠕虫化，最危险 | 评论、昵称、工单、后台列表 |
| DOM 型 | 前端脚本直接读取不可信源写入危险位置 | 服务端日志里看不到载荷 | `innerHTML`、`document.write`、`eval`、`location` |

**signals（典型特征）**：
- 输入 `<b>test</b>` 后页面出现加粗（HTML 标签被解析）。
- 输入 `"><img src=x onerror=alert(1)>` 触发弹窗（演示样例，无害验证载荷）。
- 输入 `javascript:alert(1)` 放进链接后点击可执行。
- 单引号/双引号/反斜杠导致页面脚本报错（说明处于 JS 字符串上下文）。

**impact（危害）**：窃取 Cookie / localStorage 中的凭证（无 HttpOnly 时）；以受害者身份发起转账、改密、加管理员等操作；键盘记录、伪造登录框钓鱼；借助受害者浏览器探测内网；存储型 XSS 在管理后台触发时可直接触及管理员权限。
**为什么 XSS 能绕过 CSRF 防护**：CSRF 防护的核心假设是「攻击者拿不到 Token」；XSS 让攻击者能在受害者浏览器里执行脚本，自然就能读到页面里的 Token——所以只要存在 XSS，CSRF 防护就形同虚设。这也是 XSS 危险度通常高于 CSRF 的原因：前者能直接突破后者。

**verify（挖掘与验证思路）**：
1. 找所有回显点：搜索关键词是否出现在响应里（含 JS 变量、属性、注释、JSON 返回）。
2. 判断上下文，用最小编码验证：HTML 上下文用 `<b>`，属性用 `"`，JS 用 `';`。
3. 验证可执行性：把无害标记（`alert(1)` 或 `console.log`）放到真实上下文，确认浏览器真的执行。
4. 检查防护强度：是否只过滤 `<script>`（`<img onerror>`、`<svg onload>` 可绕）；是否只在前端过滤（抓包绕过）。
5. DOM 型：搜源码中 `innerHTML`、`outerHTML`、`document.write`、`eval`、`location.hash`、`postMessage`，追踪数据流。
6. 存储型：提交后到所有展示位置查看（列表、详情、导出文件、邮件通知、后台审核页）。

**protect（防护）**：
- **root（根治）**：按上下文输出编码——HTML 实体编码、属性编码、JS 字符串编码、URL 编码、CSS 编码，一套编码不能打天下。富文本用成熟净化库做标签/属性白名单（如 DOMPurify）。
- **harden（加固）**：CSP（`default-src 'self'; script-src 'self' 'nonce-…'`，禁用 `unsafe-inline`）；Cookie 加 `HttpOnly + Secure + SameSite`；框架默认转义保持有效，重点审查 `dangerouslySetInnerHTML`、`v-html`；前端用 `textContent` 替代 `innerHTML`。
- **fallback（兜底）**：WAF 规则仅作兜底；编码变形、分片、注释常可绕过单一规则。

**mistakes（易错点）**：
- 只做输入过滤（黑名单）不做输出编码——绕过方式无穷。
- 只在搜索框测，忽略 Header、文件名、JSON 错误信息、日志展示页。
- 忘记二次编码问题：URL 编码后又被解码，导致绕过。
- 认为「有 WAF 就安全」。
- 忽略 `<svg>`、`<math>`、`<details>` 等非 script 执行向量。
- 把 DOM 型 XSS 当成服务端问题排查——它的载荷在服务端日志里根本看不到。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：某评论区提交 `<b>hi</b>`，重新打开评论列表时 hi 显示为加粗。
问：这说明什么？
- A. 输出未经编码，HTML 标签被浏览器解析了 → ✔ 正确。解释：本该是纯文字的内容被当成标记渲染，这是 XSS 的第一信号。
- B. 浏览器把字体自动加粗了 → ✘ 错误。加粗是 `<b>` 标签被解析的结果，不是浏览器自动行为。
- C. 网络传输丢了部分数据 → ✘ 错误。数据完整到达并被渲染，问题在输出端。
- D. 这是 SQL 注入 → ✘ 错误。没有碰数据库，问题在页面渲染。

*题 2 · 怎么防（protect）*｜材料（演示样例）：同一评论区，开发给出四种改法：① 输出时做 HTML 实体编码；② 过滤 `<script` 关键字；③ 前端限制输入 20 个字符；④ 加一层 WAF。
问：哪个是根治？
- A. ① 按上下文输出编码 → ✔ 正确。解释：编码后 `<` 变成文字实体，标签永远不会被解析——根治。
- B. ② 过滤 `<script` → ✘ 错误。`<img onerror>`、`<svg onload>`、大小写与编码变形都能绕。
- C. ③ 限制长度 → ✘ 错误。短载荷同样可执行（如 `<svg/onload=…>`）。
- D. ④ 加 WAF → ✘ 错误。WAF 是兜底，不替代输出编码。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发说「输入里含 `<script` 的一律拒绝，安全了」。
问：为什么不够？
- A. 执行向量不止 `<script>`，根治是输出编码不是黑名单 → ✔ 正确。解释：事件属性、svg/math 标签、编码变形都能触发执行。
- B. 过滤得再全一点就够了 → ✘ 错误。黑名单永远追不完新向量。
- C. 只要前端也过滤一遍就安全 → ✘ 错误。前端过滤可被抓包绕过，服务端输出编码才是关键。
- D. 加 HTTPS 就行 → ✘ 错误。HTTPS 保护传输，不解决页面把输入当脚本执行。

## 2.2 跨站请求伪造（CSRF）　`危险度 ★★★☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: csrf` ｜ `chapter: 2` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web, API` ｜ `hazard: 3` ｜ `aliases: CSRF, 跨站请求伪造, Cross-Site Request Forgery, XSRF` ｜ `pinyin: {full: 'kua zhan qing qiu wei zao', joined: 'kuazhanqingqiuweizao', initial: 'kzqqwz'}` ｜ `related: xss, clickjacking, client-storage-leak` ｜ `source: demo`

**难度判定**：三问法命中 1 项——概念一句「登录态被借用发起请求」能讲明白；识别只需查「关键操作有无随机 Token」；唯一前置是「浏览器会自动携带 Cookie」这一个机制，一句话可补。

**oneLiner（一句话）**：攻击者诱导已登录用户在不知情下向目标站点发出带凭证的请求，借其登录态完成改密、转账等敏感操作。

**cause（成因与位置）**：服务端仅靠 Cookie 识别身份，且不校验请求是否来自本站——没有不可预测的随机 Token、没有 Origin/Referer 校验、Cookie 缺 `SameSite`。浏览器的自动凭证携带机制被利用：任何页面发出的同站请求都会附带用户的登录 Cookie。

**where（高发位置）**：改密、改邮箱、绑卡、下单、转账、加管理员、授权第三方应用等一切**改变状态**的接口；`GET` 方法实现的敏感操作尤其危险。

**kinds（分类）**：

| 类型 | 特点 | 判断信号 |
|---|---|---|
| 经典表单 CSRF | 自动提交的跨站表单带用户 Cookie 发请求 | 敏感操作无随机 Token |
| JSON CSRF | `Content-Type: text/plain` 的跨域表单可被服务端接受 | 接受非 JSON 内容类型 |
| 登录 CSRF | 强迫受害者登录攻击者账号后留下操作痕迹 | 登录接口无来源校验 |

**signals（典型特征）**：
- 关键操作（改密、改邮箱、下单、加管理员）没有任何随机 Token。
- 请求参数完全可预测；`GET` 方法就能完成敏感操作。
- 删除 `Referer` 头后请求依旧成功。
- `Content-Type: text/plain` 的跨域表单能被服务端接受。

**impact（危害）**：以受害者身份执行敏感操作（改密、转账、绑卡、授权）；常与 XSS 组合——XSS 可直接读取 Token，绕过 CSRF 防护，此时 CSRF 防护形同虚设。

**verify（挖掘与验证思路）**：
1. 抓取敏感操作请求，看是否有不可预测的 Token 且服务端强校验。
2. 检查 Cookie 的 `SameSite` 属性（`Lax` 挡住大部分跨站 POST，但挡不住顶层 GET 导航）。**顶层 GET 导航示例**（演示样例）：攻击者诱导用户点击 `<a href='https://bank.com/transfer?to=attacker&amount=1000'>点我领红包</a>`——点击后浏览器顶层跳转到银行网站，`SameSite=Lax` 的 Cookie 会被携带，转账请求生效。这是 Lax 的已知边界，敏感操作不能只靠 Lax。
3. 去掉 `Referer` / 改成外域后重放请求，看是否仍成功。
4. 尝试把 `POST` 改 `GET`、把 `JSON` 改 `form` 或 `text/plain`，看是否被接受。
5. 构造 PoC HTML（自动提交表单，演示样例）验证。

**protect（防护）**：
- **root（根治）**：CSRF Token——每会话/每请求随机、与用户绑定、服务端强校验（不在前端校验）；敏感操作不用 `GET`。
- **harden（加固）**：Cookie `SameSite=Lax` 起步、敏感操作配 `Strict`；校验 `Origin` / `Referer` 作辅助；敏感操作二次确认（密码/短信验证码）。
- **fallback（兜底）**：WAF 对跨站表单特征做拦截，仅作兜底。

**mistakes（易错点）**：
- 只保护「改密」，忽略改邮箱/绑卡/授权第三方——这些同样能接管账号。
- Token 可复用、不与用户绑定、过期不限。
- 只在前端校验 Token，服务端照单全收。
- 以为 `SameSite=Lax` 就万事大吉——顶层 GET 导航仍可触发。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：用户登录某银行网站后访问第三方页面；该页面含一个隐藏表单自动提交到银行的转账接口，转账在用户不知情时完成。
问：这是什么问题？
- A. 跨站请求伪造——浏览器自动带上了用户的登录凭证 → ✔ 正确。解释：用户已登录、浏览器自动携带 Cookie、请求由第三方页面发起，三者凑齐就是 CSRF。
- B. 跨站脚本——第三方页面执行了银行的脚本 → ✘ 错误。没有脚本在银行页面执行，只是借身份发请求。
- C. 银行密码被猜到了 → ✘ 错误。全程没有涉及密码，凭证是浏览器自动带的。
- D. 网络被劫持 → ✘ 错误。链路安全与否与此无关，问题在身份校验机制。

*题 2 · 怎么防（protect）*｜材料（演示样例）：同一转账接口，开发给出四种改法：① 每次请求带随机 CSRF Token，服务端强校验；② 校验 Referer 必须含本站域名；③ 转账改用 POST；④ 全站加 HTTPS。
问：哪个是根治？
- A. ① CSRF Token 服务端强校验 → ✔ 正确。解释：Token 不可预测且与会话绑定，跨站页面拿不到，伪造请求无法通过。
- B. ② 只校验 Referer → ✘ 错误。Referer 可被剥掉或伪造，只能作辅助。
- C. ③ 改 POST → ✘ 错误。跨站表单同样能发 POST。
- D. ④ 加 HTTPS → ✘ 错误。HTTPS 保护传输，不阻止跨站携带凭证。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发只给「修改密码」加了 CSRF Token，改邮箱、绑卡、授权第三方应用都没有。
问：这样够吗？
- A. 不够——改邮箱/绑卡/授权同样可用来接管账号 → ✔ 正确。解释：所有状态变更接口都要保护，接管路径不止改密一条。
- B. 够了，改密最危险 → ✘ 错误。改邮箱后走「忘记密码」即可接管，风险同级。
- C. 只要 Token 不重复使用就不用保护其他接口 → ✘ 错误。Token 复用与覆盖面是两个问题。
- D. 加一层 WAF 就不用管了 → ✘ 错误。WAF 是兜底，覆盖面缺失必须补。

**terms / relatedTerms**｜terms: `csrf`、`cookie-flags`、`same-origin-policy`、`waf`（复用）；relatedTerms: `cookie-flags`、`same-origin-policy`、`xss`

**相关术语网**：`csrf` → 根治机制：`cookie-flags`（SameSite）｜ 背景：`same-origin-policy` ｜ 组合风险：`xss`（XSS 能读 Token，绕过 CSRF 防护）｜ 近亲：`clickjacking`（借界面骗点击，不是借凭证发请求）

**realCases（选读，站外链接，不保证长期有效）**：
- `RC-203`｜某邮箱服务改密接口 CSRF（成因：状态变更接口无随机 Token；教训：Token 服务端强校验 + SameSite）｜来源：PortSwigger Web Security Academy — CSRF 实验〔平台〕

## 2.3 点击劫持（Clickjacking）　`危险度 ★★☆☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: clickjacking` ｜ `chapter: 2` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web` ｜ `hazard: 2` ｜ `aliases: 点击劫持, Clickjacking, UI 覆盖攻击, 界面伪装` ｜ `pinyin: {full: 'dian ji jie chi', joined: 'dianjijiechi', initial: 'djjc'}` ｜ `related: csrf, xss` ｜ `source: demo`

**难度判定**：三问法命中 0 项——概念一个例子讲明白（透明层盖在真实按钮上）；识别只需看两个响应头（`X-Frame-Options`、CSP `frame-ancestors`）；无前置知识。

**oneLiner（一句话）**：攻击者用透明 iframe 覆盖目标页面，诱导用户点击「看起来是别的按钮」的位置，实际触发授权、转账、删除等操作。

**cause（成因与位置）**：页面允许被任意站点嵌入 iframe，且敏感操作只需要一次点击。攻击者把自己的页面垫在下面、把目标页面透明化叠在上面，用户看到的是攻击者设计的界面，点到的却是目标页面的真实按钮。

**where（高发位置）**：OAuth 授权页、支付/转账按钮、关注/点赞、删除/注销、开启摄像头/麦克风的授权提示。

**kinds（分类）**：全页覆盖（目标页整页透明叠放）；局部覆盖（只盖住目标页的某一个按钮区域）。

**signals（典型特征）**：
- 响应头缺少 `X-Frame-Options` 与 CSP `frame-ancestors`。
- 页面 JS 有 `top != self` 之类的 frame busting 逻辑，但可被 `sandbox` 属性绕过。
- 目标页能被任意来源 iframe 嵌入且不报错。

**impact（危害）**：诱导用户完成 OAuth 授权（授权给攻击者应用）、诱导转账、诱导开启摄像头/麦克风、诱导删除数据——一切「一次点击即生效」的敏感操作都可被劫持。

**verify（挖掘与验证思路）**：
1. 检查响应头是否有 `X-Frame-Options: DENY/SAMEORIGIN` 或 CSP `frame-ancestors`。
2. 用本地 HTML（演示样例）把目标页嵌进 iframe 并设透明度，看是否成功嵌入。
3. 若有 JS frame busting，尝试 iframe 加 `sandbox` 属性，看是否被绕过。

**protect（防护）**：
- **root（根治）**：`Content-Security-Policy: frame-ancestors 'self'`（或白名单来源）；`X-Frame-Options: DENY` / `SAMEORIGIN`。**优先级**：两者同存时以 CSP `frame-ancestors` 为准（`X-Frame-Options` 是旧标准、语义更粗）；但老旧浏览器可能只认 `X-Frame-Options`——兼容起见两个响应头都配，效果取交集。
- **harden（加固）**：敏感操作增加二次确认（输入密码/验证码）；重要页面可检测自身是否被嵌入并跳转脱壳。
- **fallback（兜底）**：提示用户留意页面完整性，仅作辅助。

**mistakes（易错点）**：
- 只用 JS frame busting（`if (top != self) …`）——`sandbox` 属性可绕过。
- 只保护首页，支付页/授权页反而裸奔。
- 以为「页面视觉上没有 iframe 就没事」——透明嵌入不留痕迹。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：某抽奖页把一个透明 iframe 盖在「立即抽奖」按钮上，iframe 里的目标是某网盘的「删除文件」按钮；用户点「抽奖」，文件被删除。
问：这是什么攻击？
- A. 点击劫持——用透明层把用户的点击引到别的按钮上 → ✔ 正确。解释：用户以为点的是抽奖，实际点到的是被覆盖的真实按钮。
- B. CSRF——借用户身份发了删除请求 → ✘ 错误。CSRF 是「自动带凭证发请求」，不需要用户点击；这里是诱导点击。
- C. XSS——页面被注入了脚本 → ✘ 错误。目标页面没有被注入脚本，只是被嵌入。
- D. 钓鱼——伪造了网盘页面 → ✘ 错误。页面是真实的，被嵌入的是真页面。

*题 2 · 怎么防（protect）*｜材料（演示样例）：开发给出四种改法：① 响应头加 `Content-Security-Policy: frame-ancestors 'self'`；② JS 里判断 `top != self` 就跳转；③ 弹窗提醒用户别乱点；④ 把按钮改成两步确认。
问：哪个是根治？
- A. ① 用 `frame-ancestors` 禁止被嵌入 → ✔ 正确。解释：浏览器层面直接拒绝嵌入，透明层无从叠起。
- B. ② JS frame busting → ✘ 错误。可被 `sandbox` 属性绕过，只算加固。
- C. ③ 提醒用户 → ✘ 错误。透明层用户根本看不见，提醒无效。
- D. ④ 两步确认 → ✘ 错误。这是加固手段（也有用），但根治是禁止嵌入。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发说「我加了 `if (top != self) top.location = self.location`，安全了」。
问：为什么不够？
- A. iframe 加 `sandbox` 属性就能绕过这段 JS → ✔ 正确。解释：JS 判断运行在被嵌入页里，sandbox 可限制脚本执行从而绕过；必须用响应头。
- B. 这段代码写得不对，改对就行 → ✘ 错误。思路本身不可靠，改语法没用。
- C. 只要在 HTTPS 下就安全 → ✘ 错误。与传输加密无关。
- D. 加 WAF 就行 → ✘ 错误。WAF 管不到浏览器的嵌入行为。

**terms / relatedTerms**｜terms: `clickjacking`、`frame-protection`、`csp`、`csrf`；relatedTerms: `frame-protection`、`csp`、`csrf`

**相关术语网**：`clickjacking` → 根治：`frame-protection` ｜ 机制：`csp`（frame-ancestors）｜ 易混：`csrf`（不需要点击、自动发请求）

**realCases（选读，站外链接，不保证长期有效）**：
- `RC-204`｜某 OAuth 授权页可被嵌套导致误授权（成因：授权页无 frame-ancestors 限制；教训：授权页禁止被嵌入 + 二次确认）｜来源：OWASP Clickjacking 防护说明〔权威〕

## 2.4 原型污染（Prototype Pollution）　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: prototype-pollution` ｜ `chapter: 2` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, 系统` ｜ `hazard: 4` ｜ `aliases: 原型污染, Prototype Pollution, __proto__ 污染` ｜ `pinyin: {full: 'yuan xing wu ran', joined: 'yuanxingwuran', initial: 'yxwr'}` ｜ `related: xss, postmessage-communication, dom-clobbering` ｜ `source: demo` ｜ `templateId: TPL-INJECT`（第二期套模板，stages 留空）

**难度判定**：三问法命中 2 项——要先理解「JS 对象共享原型」这一机制，且需构造 `__proto__` 等特殊键名验证；但语法单一、攻击面集中，不到高。

**oneLiner（一句话）**：攻击者用 `__proto__`、`constructor.prototype` 等键名污染 JS 对象的共享原型，使所有对象继承恶意属性，轻则逻辑绕过，重则在 Node 服务端达成代码执行。

**cause（成因与位置）**：递归合并/深拷贝函数对键名不设防——用户控制的键名一路写进对象原型。高发位置：不安全的 `merge`/`extend`/`cloneDeep`、`JSON.parse` 后按路径赋值、URL 参数解析库、模板渲染的属性访问、Node 服务端的配置合并。

**where（高发位置）**：前后端的对象合并工具函数、配置合并、`lodash` 等库的深合并调用点、表单/JSON 结构动态赋值处。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 原型链污染 | 通过 `__proto__` 键改写对象底座 | `Object.prototype` 上出现意外属性 |
| 构造器污染 | 通过 `constructor.prototype` 间接改写 | `constructor[prototype]` 路径赋值生效 |
| 服务端污染 | Node 侧合并被污染，触发危险调用链 | 报错消失、默认值异常、拒绝服务 |

**signals（典型特征）**：
- 传 `{"__proto__":{"isAdmin":true}}` 后权限判断被绕过。
- 传 `?__proto__[x]=1` 后全局对象出现该属性。
- 前端库报错消失或出现意外默认值；服务端出现拒绝服务（污染 `toString` 等内置属性）。

**impact（危害）**：前端逻辑绕过（可串成 XSS 等利用链）、服务端拒绝服务、Node.js 环境下借助调用链可达远程代码执行（RCE，复用术语 `rce`）。

**verify（挖掘与验证思路）**：
1. 找所有「接收对象并递归合并」的入口（配置、表单、JSON、URL 参数解析）。
2. 用 `__proto__`、`constructor[prototype]`、`prototype` 三种键名分别测试。
3. 用 `Object.prototype.x` 是否被设置确认污染成立（演示样例，无害属性即可）。
4. Node 侧再评估是否存在可被污染触发的危险调用链（只在授权环境评估）。

**protect（防护）**：
- **root（根治）**：合并前过滤 `__proto__`、`constructor`、`prototype` 三个键；用 `Object.create(null)` 或 `Map` 承接用户数据。
- **harden（加固）**：`JSON.parse` 后做 schema 校验（字段与类型白名单）；升级有修复的依赖版本。
- **fallback（兜底）**：运行时监控异常属性出现，仅作兜底。

**mistakes（易错点）**：
- 只测前端忽略 Node 服务端（服务端才是 RCE 的入口）。
- 只测 `__proto__` 不测 `constructor.prototype`——两条路径都要堵。
- 把「合并前过滤」写在一处，另一处调用忘了复用同一工具函数。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
接口：POST /api/settings  （body 为 JSON，服务端做深合并）
请求体：
{ "theme": "dark", "__proto__": { "isAdmin": true } }

合并后控制台验证（演示样例）：
> ({ }).isAdmin
  true        ← 所有对象都继承到了 isAdmin
```

note：材料为演示样例，非现场运行、非真实系统；验证属性为无害标记。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：注入点不在引号，而在**键名**。普通字段写进对象，`__proto__` 这类特殊键写进的是「所有对象共享的底座」——一个键污染全场，这是它比普通注入更隐蔽的地方。
- **how（下一步看什么、怎么判断）**：① 找到「用户数据被合并进对象」的位置；② 用无害标记（如 `polluted: 1`）试三种键名；③ 检查 `Object.prototype` 是否多出属性；④ 成立即按「合并前过滤三个键」修，再评估服务端调用链。

〔本条术语锚点〕`prototype-pollution`、`prototype-chain`、`rce`、`type-validation`（复用）

**相关术语网**：`prototype-pollution` → 前置：`prototype-chain` ｜ 验证：`type-validation` ｜ 后果升级：`rce` ｜ 同为「结构被改写」家族：`nosql`（复用）

## 2.5 postMessage 跨窗口通信缺陷　`危险度 ★★★☆☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: postmessage-communication` ｜ `chapter: 2` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web` ｜ `hazard: 3` ｜ `aliases: postMessage, 跨窗口通信缺陷, message 事件注入, 跨域消息` ｜ `pinyin: {full: 'kua chuang kou tong xin que xian', joined: 'kuachuangkoutongxinquexian', initial: 'kcktxqx'}` ｜ `related: xss, dom-clobbering, prototype-pollution` ｜ `source: demo` ｜ `templateId: TPL-CLIENT`（第二期套模板，stages 留空）

**难度判定**：三问法命中 2 项——要理解「跨窗口消息传递」这一机制（消息从哪来、谁在听），且需构造跨页面消息验证；但协议面窄（只围绕 origin/消息体），定中。

**oneLiner（一句话）**：页面接收跨窗口消息时不校验来源与消息结构，任意站点都能向它注入指令或窃取数据，消息内容直达危险汇聚点时可升级为 XSS。

**cause（成因与位置）**：`addEventListener('message', …)` 回调里不校验 `event.origin` 与 `event.source`，或 `postMessage(data, '*')` 使用通配目标来源；消息内容直接进 `innerHTML`、`eval` 等危险汇聚点。高发位置：iframe 嵌入的支付/登录组件、跨域父子页面通信、微前端消息总线。

**where（高发位置）**：父子窗口/iframe 之间传数据的页面、SDK 接收配置的页面、跨域单点登录回调。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 来源不校验 | 任何站点都能发消息进来 | 监听器里没有 origin 白名单 |
| 目标用通配 | 消息发给「所有窗口」 | `postMessage(data, '*')` |
| 消息进危险点 | 消息内容直接当 HTML/脚本 | 消息体流入 `innerHTML`/`eval` |

**signals（典型特征）**：
- 源码中 `addEventListener('message', …)` 内没有 origin 校验。
- `postMessage(data, '*')` 使用通配目标来源。
- 消息内容直接进 `innerHTML` 或 `eval`。

**impact（危害）**：跨域数据窃取（token、用户信息）、消息驱动的 DOM XSS、在嵌入方页面执行越权操作。

**verify（挖掘与验证思路）**：
1. 搜源码所有 `message` 事件监听与 `postMessage` 调用。
2. 检查监听器是否用白名单**精确匹配** `event.origin`（协议+域名+端口全等）。
3. 追踪消息体去向：是否流入 `innerHTML`/`eval`/`location` 等危险汇聚点。
4. 用外部测试页（演示样例）发送伪造消息，观察目标页行为变化。

**protect（防护）**：
- **root（根治）**：严格校验 `event.origin`——白名单精确匹配（协议+域名+端口全等），不用 `indexOf`/`includes` 子串判断；`postMessage` 指定确切目标 origin，不用 `*`。
- **harden（加固）**：校验 `event.source`；消息体做结构校验（字段白名单、类型校验，复用 `type-validation`）；消息内容输出前按上下文编码。
- **fallback（兜底）**：CSP 限制可嵌入来源，仅作兜底。

**mistakes（易错点）**：
- 用 `origin.includes('trusted.com')` 判断——`trusted.com.evil.com` 可绕过。
- 只校验前缀不校验协议与端口（`http` 冒充 `https`、端口偷换）。
- 以为「消息来自 iframe 就可信」——iframe 的来源仍需校验。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
目标页（演示样例）：

  document.getElementById('box').innerHTML = e.data.html;   // 无 origin 校验

攻击页（演示样例，同浏览器另一标签）：
```

## 2.6 开放重定向（Open Redirect）　`危险度 ★★☆☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: open-redirect` ｜ `chapter: 2` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web, API` ｜ `hazard: 2` ｜ `aliases: 开放重定向, Open Redirect, 跳转漏洞, 重定向注入` ｜ `pinyin: {full: 'kai fang chong ding xiang', joined: 'kaifangchongdingxiang', initial: 'kfcdx'}` ｜ `related: xss, csrf, oauth-redirect` ｜ `source: demo`

**难度判定**：三问法命中 0 项——改一个跳转参数即可演示；信号直观（跳去了不该去的域名）；无前置知识。

**oneLiner（一句话）**：跳转目标完全由用户参数控制，攻击者可把用户从可信域名导向钓鱼站点，链接因此带上了可信外衣。

**cause（成因与位置）**：跳转地址直接取自用户参数而不做目标校验，或只做「包含可信域名」的子串校验。高发位置：登录后回跳（`next`/`returnUrl`）、退出跳转、短链服务、OAuth `redirect_uri`、`callback` 参数。

**where（高发位置）**：`next`、`return`、`redirect`、`url`、`callback`、`continue` 等跳转参数。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 协议相对跳转 | `//evil.com` 省略协议照样跳 | 跳转到外域 |
| 符号绕过 | `https:evil.com`、`@evil.com`、`/\evil.com` | 解析结果与预期不符 |
| 子串匹配绕过 | `trusted.com.evil.com` 骗过「包含即通过」 | 白名单校验形同虚设 |

**signals（典型特征）**：
- `?next=https://evil.com`、`?returnUrl=//evil.com`、`?url=/\evil.com` 均能跳出本站。
- 跳转参数可改成任意外域而无提示。
- OAuth 场景下 `redirect_uri` 只做前缀/子串校验。

**impact（危害）**：钓鱼（链接域名可信、受害者不易起疑）；OAuth 授权码被导向攻击者域名（复用 `oauth-redirect` 术语）；配合 SSRF 白名单绕过（跳转点被当作可信出口）。

**verify（挖掘与验证思路）**：
1. 收集所有跳转参数（`next/return/redirect/url/callback/continue`）。
2. 测试 `//evil.com`、`https:evil.com`、`@evil.com`、`%2f%2fevil.com` 等变体（演示样例，指向无害测试地址）。
3. 测白名单子串匹配绕过：`trusted.com.evil.com`。
4. OAuth 场景重点核对 `redirect_uri` 校验方式。

**protect（防护）**：
- **root（根治）**：跳转目标用**相对路径白名单**或映射表（id → 真实 URL），绝不直接使用用户传入的完整 URL；必须支持外跳时，解析 URL 后对 host 做**全等**比较。
- **harden（加固）**：跳转前提示「即将离开本站」；OAuth `redirect_uri` 用精确注册值比对。
- **fallback（兜底）**：网关层对跳转参数做外域告警，仅作兜底。

**mistakes（易错点）**：
- 只校验「是否包含可信域名」——`trusted.com.evil.com` 子串绕过。
- 只校验 `http://` 前缀——`//evil.com`、`https:evil.com` 照样跳。
- 只防钓鱼不看 OAuth 场景——`redirect_uri` 失守直接丢授权码。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：某登录页 `?next=//evil.example`，登录成功后浏览器跳到 `evil.example`，地址栏闪过的却是本站登录链接。
问：这是什么问题？
- A. 开放重定向——跳转目标被用户参数控制 → ✔ 正确。解释：可信域名做外衣、实际落点是外域，正是钓鱼的温床。
- B. XSS——跳转页执行了脚本 → ✘ 错误。没有脚本执行，只是跳去了外域。
- C. CSRF——借身份发了请求 → ✘ 错误。没有对本站发伪造请求。
- D. 服务器被入侵 → ✘ 错误。服务器行为正常，只是没校验跳转目标。

*题 2 · 怎么防（protect）*｜材料（演示样例）：同一跳转参数，四种改法：① 用映射表（id → 真实 URL），不接收完整 URL；② 校验参数「包含本站域名」；③ 只允许 `http://` 开头；④ 加 WAF。
问：哪个是根治？
- A. ① 映射表/相对路径白名单 → ✔ 正确。解释：跳转目标完全由服务端决定，用户只能选预设项，无外跳可能。
- B. ② 包含本站域名 → ✘ 错误。`trusted.com.evil.com` 可绕。
- C. ③ 只允许 http:// 开头 → ✘ 错误。`http://evil.com` 也满足前缀。
- D. ④ 加 WAF → ✘ 错误。WAF 是兜底。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发说「我校验了 redirect 参数必须包含 oursite.com，肯定安全」。
问：为什么不够？
- A. 子串匹配可被 `oursite.com.evil.com` 绕过，要解析后 host 全等 → ✔ 正确。解释：「包含」不等于「等于」，域名比较必须全等。
- B. 包含校验够了，攻击者注册不到那个域名 → ✘ 错误。`oursite.com.evil.com` 的域名是 `evil.com`，攻击者可注册。
- C. 只要全程 HTTPS 就安全 → ✘ 错误。HTTPS 不改变跳转目标校验问题。
- D. 加重提示语就行 → ✘ 错误。提示是加固不是根治。

**terms / relatedTerms**｜terms: `open-redirect`、`origin-check`、`allowlist`（复用）、`oauth-redirect`；relatedTerms: `origin-check`、`allowlist`、`oauth-redirect`

**相关术语网**：`open-redirect` → 根治：`origin-check`（host 全等）｜ 手段：`allowlist`（复用）｜ 升级风险：`oauth-redirect`（授权码失窃）｜ 易混：`xss`（执行脚本 vs 跳转去向）

**realCases（选读，站外链接，不保证长期有效）**：
- `RC-205`｜某 OAuth 提供方 redirect_uri 校验不严致授权码泄露（成因：子串匹配白名单；教训：精确注册比对）｜来源：PortSwigger Web Security Academy — OAuth 跳转实验〔平台〕

## 2.7 DOM 覆盖（DOM Clobbering）　`危险度 ★★☆☆☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: dom-clobbering` ｜ `chapter: 2` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web` ｜ `hazard: 2` ｜ `aliases: DOM Clobbering, DOM 覆盖, 全局变量覆盖, HTML 元素覆盖` ｜ `pinyin: {full: 'dom fu gai', joined: 'domfugai', initial: 'dfg'}` ｜ `related: xss, postmessage-communication, prototype-pollution` ｜ `source: demo` ｜ `templateId: TPL-CLIENT`（第二期套模板，stages 留空）

**难度判定**：三问法命中 2 项——要理解「HTML 元素的 id/name 会顶替同名全局引用」这一浏览器机制，且需构造带 id 的 HTML 验证；但变体少、原理单一，定中。

**oneLiner（一句话）**：攻击者用 HTML 元素的 `id`/`name` 顶替前端脚本依赖的全局变量或 DOM 属性，使脚本读到攻击者构造的对象，校验被绕过。

**cause（成因与位置）**：页面脚本用 `window.config`、`document.forms.x` 之类的全局引用取值，而页面又允许用户插入带 `id`/`name` 的 HTML——浏览器会把该元素挂到全局命名空间，遮蔽原有变量。高发位置：允许自定义 HTML 的富文本、个人主页、模板配置、`<form>`/`<img>`/`<iframe>` 的 id/name 属性可控处。

**where（高发位置）**：前端脚本读取 `window.x` / `document.x` 全局引用的页面；允许用户输入 HTML 标签属性（尤其 `id`、`name`）的位置。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 变量覆盖 | 元素顶替 `window.x` 变量 | 脚本读配置读到了 DOM 元素 |
| 表单/集合覆盖 | `document.forms.x` 被同名元素截胡 | 表单引用指向攻击者元素 |
| 校验绕过 | 布尔判断读到元素的属性 | `if (window.config.ok)` 恒真/恒假失真 |

**signals（典型特征）**：
- 页面脚本使用 `window.config`、`document.forms.x` 等全局引用。
- 页面允许用户插入带 `id`/`name` 的 HTML（富文本、自定义模块）。
- 读取配置的脚本值出现异常（类型不再是预期的对象/字符串）。

**impact（危害）**：前端校验绕过（如权限判断失真）、配合其他缺陷串成利用链（复用 `m07-vuln-chains` 思路）、在少数场景升级为脚本执行。

**verify（挖掘与验证思路）**：
1. 搜前端源码里对 `window.x`、`document.x` 的全局引用。
2. 确认用户 HTML 是否允许 `id`/`name` 属性（富文本/自定义模块）。
3. 插入带 `id` 的元素（演示样例，无害标记），看脚本读取的值是否被替换。
4. 检查读取处有无类型校验（预期对象却拿到元素时是否报错/拒绝）。

**protect（防护）**：
- **root（根治）**：不依赖全局 DOM 引用取配置——用显式查找（`document.getElementById`）并校验类型；配置走 JS 闭包/模块作用域，不挂全局。
- **harden（加固）**：用户 HTML 过滤 `id`/`name` 属性（标签/属性白名单，复用 `html-sanitize`）；框架层禁用全局变量注入。
- **fallback（兜底）**：入口处做类型断言，异常即拒绝，仅作兜底。

**mistakes（易错点）**：
- 只净化「标签」不管「属性」——`id`/`name` 属性才是覆盖的入口。
- 以为「Vue/React 项目没这问题」——只要代码里用 `window.x` 全局引用就存在风险。
- 只查 `<img>` 忽略 `<form>`、`<iframe>`、`<object>`——都能参与覆盖。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
页面脚本（演示样例）：
  if (window.config && window.config.isAdmin) { showAdminPanel(); }

用户可控 HTML（演示样例，个人主页自定义模块）——嵌套构造：
  <form id="config"><input name="isAdmin" value="true"></form>

结果：
  window.config 变成该 <form> 元素
  window.config.isAdmin 变成其内部的 <input> 元素（truthy）
  → 两个条件都满足，校验被绕过（演示样例，无害验证）

对比（错误做法，仅第一层顶替）：
  <img name="config">        ← window.config 变元素，但 config.isAdmin
                                仍是 undefined，第二个条件 falsy，绕不过去
```

note：材料为演示样例，载荷为无害验证标记，非现场运行、非真实系统。**要点**：单一 `id`/`name` 只能顶替第一层引用；要绕过嵌套属性检查必须构造父子结构（`<form>` + 命名子元素，或两个同名元素形成 HTMLCollection）。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：这里的「注入点」是**元素属性名**。`id`/`name` 不只是展示标识——浏览器会把带它们的元素挂进全局命名空间，脚本再按名字去取，取到的就是攻击者的元素。名字相同即顶替，这是浏览器的既定行为而非 bug。
- **how（下一步看什么、怎么判断）**：① 列出脚本依赖的全局引用清单；② 看用户 HTML 允许哪些属性；③ 插入无害元素验证替换——注意**单一的 `id`/`name` 只能顶替第一层引用（如 `window.config`），要绕过嵌套属性检查（如 `config.isAdmin`）需要构造父子结构**（`<form id="config"><input name="isAdmin">` 或两个同名元素）；④ 修复按「去掉全局引用 + 类型校验 + 属性白名单」三件套。

〔本条术语锚点〕`dom-clobbering`、`html-sanitize`、`type-validation`（复用）、`xss`

**相关术语网**：`dom-clobbering` → 防御：`html-sanitize` ｜ 校验：`type-validation`（复用）｜ 同为「客户端结构被改写」：`prototype-pollution`、`postmessage-communication` ｜ 升级风险：`xss`

## 2.8 CSS 注入 / 内容欺骗　`危险度 ★☆☆☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: css-injection` ｜ `chapter: 2` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web` ｜ `hazard: 1` ｜ `aliases: CSS 注入, 样式注入, 内容欺骗, CSS Injection` ｜ `pinyin: {full: 'css zhu ru', joined: 'csszhuru', initial: 'csszr'}` ｜ `related: xss, clickjacking` ｜ `source: demo`

**难度判定**：三问法命中 0 项——概念一句话（输入拼进 CSS 后改样式/伪造界面）；信号直观（页面样式异常）；无前置知识。

**oneLiner（一句话）**：用户输入被拼进 CSS 后，攻击者可覆盖页面样式、伪造界面诱导操作，还能配合属性选择器逐字符外带数据。

**cause（成因与位置）**：用户内容直接进入 `<style>` 块或 `style` 属性且未做值级过滤。高发位置：主题/皮肤自定义、富文本样式、邮件模板样式、用户昵称进 style 属性。

**where（高发位置）**：自定义主题色/字体、`style="…用户输入…"`、模板样式配置。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 界面伪造 | 覆盖页面样式伪装成别的界面 | 页面出现非预期的覆盖层/假按钮 |
| 数据外带 | 属性选择器逐字符猜数据 | 页面加载外域图片请求呈规律性 |

**signals（典型特征）**：
- 用户输入进入 `<style>` 或 `style` 属性后页面样式被改写。
- 构造 `}` 闭合样式规则后出现非预期样式效果。
- 出现按字符试探的外域资源请求（属性选择器外带）。

**impact（危害）**：界面伪造诱导点击（钓鱼）、配合属性选择器外带敏感数据（如 CSRF Token 的字符）、破坏页面可用性。危险度低（★☆），但常被忽视而成为组合利用的一环。

**verify（挖掘与验证思路）**：
1. 找用户内容进入 `<style>`/`style` 属性的位置。
2. 用 `}` 尝试闭合规则（演示样例，改无害样式如背景色），看效果是否可控。
3. 若样式值可含 `url()`，检查是否可加载外域资源。

**protect（防护）**：
- **root（根治）**：CSS 值用白名单/数值化（颜色取色板、字号取枚举）；用户内容不进 `<style>` 与 `style` 属性。
- **harden（加固）**：模板样式与用户数据分离；富文本净化覆盖 style 属性（复用 `html-sanitize`）。
- **fallback（兜底）**：CSP 限制样式来源，仅作兜底。

**mistakes（易错点）**：
- 以为「CSS 不能执行代码就不危险」——界面伪造与数据外带同样有杀伤力。
- 只过滤 `<script>` 标签不管样式上下文。
- 忽略 `url()` 可加载外域资源这一点。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：某主题设置里输入 `red; } body{display:none` 后整个页面变空白，只留一个假登录框。
问：这说明什么？
- A. 输入拼进了 CSS，样式规则被改写（界面伪造） → ✔ 正确。解释：`;`/`}` 让输入逃出原规则、写入新规则，页面被攻击者重绘。
- B. 浏览器故障 → ✘ 错误。只在提交该输入后出现，且效果与输入一致。
- C. 这是 XSS → ✘ 错误。没有脚本执行，只是样式被改写。
- D. 网络加载失败 → ✘ 错误。页面元素齐全，只是样式被覆盖。

*题 2 · 怎么防（protect）*｜材料（演示样例）：四种改法：① 颜色/字号用白名单枚举，用户数据不进 style；② 过滤 `<script`；③ 限制输入长度；④ 加 WAF。
问：哪个是根治？
- A. ① 值级白名单 + 用户数据不进样式 → ✔ 正确。解释：攻击者只能选预设样式值，规则无法被改写。
- B. ② 过滤 script → ✘ 错误。与样式上下文无关。
- C. ③ 限长度 → ✘ 错误。短输入也能闭合规则。
- D. ④ 加 WAF → ✘ 错误。WAF 是兜底。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发说「CSS 注入才一星，不用管」。
问：产品口径怎么看？
- A. 危害小≠可忽略，它常是组合利用（界面伪造钓鱼）的一环 → ✔ 正确。解释：★只说独立危害大小；组合链条里它可放大其他漏洞。
- B. 一星漏洞都不用修 → ✘ 错误。没有这条规则。
- C. 一星说明学习难度也低，可以直接跳过不学 → ✘ 错误。危险度与学习难度是两个维度。
- D. 只要页面视觉正常就没事 → ✘ 错误。数据外带（属性选择器）不改视觉也可发生。

## 2.9 客户端存储泄露　`危险度 ★★★☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: client-storage-leak` ｜ `chapter: 2` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web, 移动` ｜ `hazard: 3` ｜ `aliases: 客户端存储泄露, localStorage 泄露, 前端存储泄露, Token 明文存储` ｜ `pinyin: {full: 'ke hu duan cun chu xie lou', joined: 'kehuduancunchuxielou', initial: 'khdcckxl'}` ｜ `related: xss, csrf, frontend-supply-chain` ｜ `source: demo`

**难度判定**：三问法命中 0 项——打开浏览器存储面板即可看见明文 Token；概念一句话（敏感数据明文存在客户端）；无前置知识。

**oneLiner（一句话）**：Token、密钥、个人信息明文存在 `localStorage`、`sessionStorage`、IndexedDB 或无 HttpOnly 的 Cookie 中，一旦页面脚本失守或设备被接触即被读取。

**cause（成因与位置）**：图省事把长期凭证放客户端存储，且未做加密与过期控制。高发位置：`localStorage.getItem('token')`、前端打包产物里硬编码 AK/SK、Cookie 缺 `HttpOnly`、记住密码功能明文落盘。

**where（高发位置）**：登录后把 Token 写入 `localStorage`/`sessionStorage` 的代码；前端 bundle（JS 资源）里的常量；Cookie 属性配置。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 凭证明文 | Token 原样存本地 | 存储面板可见完整 Token |
| 密钥硬编码 | AK/SK 打进前端代码 | bundle 里出现密钥常量 |
| Cookie 裸奔 | Cookie 无 HttpOnly | 脚本可读 document.cookie |

**signals（典型特征）**：
- `localStorage.getItem('token')` / `sessionStorage` 里存着凭证。
- 前端 bundle（JS 资源）中出现 AK/SK、API Key 等常量。
- Cookie 缺 `HttpOnly`，`document.cookie` 可读到会话标识。

**impact（危害）**：凭证/密钥泄露导致账号接管、接口被滥用（复用 `arbitrary-rw` 式危害描述——越权读写数据）；与 XSS 组合时无需破解即可直接窃取；设备被接触（共享电脑、维修）同样泄露。

**verify（挖掘与验证思路）**：
1. 打开浏览器存储面板（Application 页签）逐项查看 `localStorage`/`sessionStorage`/IndexedDB/Cookie。**IndexedDB 查法**：展开 Application 页签的 IndexedDB 节点——它是结构化数据库，一个站点可能存在多张表，需逐库、逐表检查有无敏感数据（Token、个人信息）。
2. 全文搜前端 bundle 里的 `token`、`secret`、`apiKey`、`AK`/`SK` 常量。
3. 检查会话 Cookie 的 `HttpOnly`/`Secure`/`SameSite` 三属性（复用 `cookie-flags`）。
4. 评估「设备被接触」场景下的暴露面（共享设备、导出数据）。

**protect（防护）**：
- **root（根治）**：会话 Token 放 `HttpOnly + Secure + SameSite` Cookie；不在前端存长期密钥，密钥只存服务端。
- **harden（加固）**：确需本地暂存的敏感数据做加密并设过期；最小化存储范围；构建流程扫出 bundle 里的密钥（防硬编码）。
- **fallback（兜底）**：Token 可吊销、可轮换；异常读取告警，仅作兜底。

**mistakes（易错点）**：
- 以为「localStorage 只有 XSS 才能读」——设备被接触、共享电脑、浏览器插件同样能读。
- 把「前端加密」当防护——密钥也在前端，等于没锁。
- 只检查 `localStorage` 漏了 Cookie 属性与 bundle 硬编码。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：打开浏览器存储面板，`localStorage` 里有一条明文 `token=eyJhbGciOi…`。
问：这属于什么问题？
- A. 客户端存储泄露——凭证明文存放在可被脚本读取的位置 → ✔ 正确。解释：任何脚本（含注入的恶意脚本）都能读走它。
- B. 这是正常做法，不算问题 → ✘ 错误。明文 Token 可被任意脚本读取，暴露面过大。
- C. 这是 CSRF → ✘ 错误。CSRF 是借身份发请求，这里是凭证存放不当。
- D. 浏览器缓存问题 → ✘ 错误。localStorage 是主动写入的持久存储。

*题 2 · 怎么防（protect）*｜材料（演示样例）：四种改法：① Token 改存 `HttpOnly+Secure+SameSite` Cookie；② localStorage 里把 Token 做「前端加密」；③ 只存 sessionStorage；④ 加 WAF。
问：哪个是根治？
- A. ① HttpOnly Cookie——脚本根本读不到 → ✔ 正确。解释：`HttpOnly` 隔绝脚本访问，配合 `Secure`/`SameSite` 是会话凭证的标准存放方式。
- B. ② 前端加密 → ✘ 错误。解密密钥也在前端，等价于没加密。
- C. ③ 换 sessionStorage → ✘ 错误。同一页面脚本照样能读。
- D. ④ 加 WAF → ✘ 错误。WAF 管不到浏览器存储。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发说「Token 存 localStorage 没事，反正只有 XSS 才能偷，我们没有 XSS」。
问：为什么站不住？
- A. 设备被接触、共享电脑、恶意浏览器插件都能读，且「现在没有 XSS」不等于永远没有 → ✔ 正确。解释：存储位置决定暴露面，不能赌漏洞不存在。
- B. 他说得对 → ✘ 错误。暴露面不因「当前无 XSS」而消失。
- C. 只要 Token 设短过期就行 → ✘ 错误。过期是缓解，不是存放方式的根治。
- D. 加 HTTPS 就行 → ✘ 错误。HTTPS 保护传输，不保护本地存储。

**terms / relatedTerms**｜terms: `client-storage-leak`、`cookie-flags`、`info-leak`（复用）、`arbitrary-rw`（复用）；relatedTerms: `cookie-flags`、`info-leak`、`xss`

**相关术语网**：`client-storage-leak` → 根治：`cookie-flags` ｜ 本质：`info-leak`（复用）｜ 放大器：`xss`（XSS 直接偷走本地凭证）｜ 供应链近亲：`frontend-supply-chain`（第三方脚本可读全部本地存储）

## 2.10 浏览器扩展与前端供应链　`危险度 ★★★☆☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: frontend-supply-chain` ｜ `chapter: 2` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, 通用` ｜ `hazard: 3` ｜ `aliases: 前端供应链, 浏览器扩展滥用, 第三方脚本风险, 前端组件投毒` ｜ `pinyin: {full: 'qian duan gong ying lian', joined: 'qianduangongyinglian', initial: 'qdgyl'}` ｜ `related: xss, client-storage-leak, prototype-pollution` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（第二期套模板，stages 留空）

**难度判定**：三问法命中 2 项——要理解「第三方脚本与扩展拥有页面完全权限」这一信任模型（引入的代码=自己写的代码），且涉及 SRI/CSP 多个机制的组合；但利用与验证路径直观，定中。

**oneLiner（一句话）**：被入侵或恶意的浏览器扩展、第三方脚本（广告、统计、客服 SDK）拥有页面完全控制权，可窃取表单、注入脚本，把供应链变成攻击入口。

**cause（成因与位置）**：页面无条件信任引入的第三方代码——脚本权限与自研代码等同，一旦上游被篡改或本身就恶意，攻击直达所有用户。高发位置：CDN 引入的公共库、统计/广告/客服 SDK、浏览器扩展的用户量变现、前端组件包（都属于 `supply-chain` 供应链攻击的前端形态）。

**where（高发位置）**：`<script src="…">` 外链脚本、`npm` 安装的前端组件、浏览器扩展、CDN 资源。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 恶意扩展 | 扩展读表单/改页面 | 扩展申请过宽权限 |
| 第三方脚本被篡改 | CDN/SDK 上游被投毒 | 脚本哈希与预期不符 |
| 组件投毒 | 依赖包作者被收买/被盗号 | 依赖版本异常更新、代码风格突变 |

**signals（典型特征）**：
- 页面从第三方域名加载脚本且无完整性校验。
- 引入的 SDK 权限过宽（可读全部 DOM、可发任意请求）。
- 依赖包出现异常版本更新、安装脚本可疑。

**impact（危害）**：窃取表单数据（含密码、支付信息）、注入脚本（等同 XSS 的全量能力）、批量影响所有访问用户——供应链一旦失守是「一处污染、全量中招」。

**verify（挖掘与验证思路）**：
1. 盘点页面全部外链脚本/样式与 `npm` 直接依赖清单。
2. 检查是否配置 SRI（`integrity` 属性）与 CSP（复用 `csp`）限制脚本来源。
3. 评估第三方组件申请的权限范围（DOM 访问、网络请求、存储读写）。
4. 审查依赖更新记录与发布者变更（组件来源可信度）。

**protect（防护）**：
- **root（根治）**：最小化第三方脚本——非必要不引入；必要引入用 SRI（子资源完整性，复用 `sri`）钉死哈希。
- **harden（加固）**：CSP 限定脚本来源（复用 `csp`）；定期审计第三方组件与扩展权限；依赖锁定版本、审查更新。
- **fallback（兜底）**：内容变更告警与快速下线机制，仅作兜底。

**mistakes（易错点）**：
- 以为「大厂 CDN 就安全」——上游被篡改照样中招。
- 只审计自己代码不审第三方脚本与扩展。
- 引入 SRI 后忘了更新哈希，脚本升级后被浏览器拒绝加载（可用性问题），反过来又把 SRI 摘掉。
- **SRI 只适用静态资源**（固定版本的库文件）；动态生成的脚本（统计脚本、A/B 测试脚本）无法钉死哈希，SRI 用不上——这类脚本只能用 CSP 限制来源，并尽量少引。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
页面引入（演示样例）：
  <script src="https://cdn.example.com/analytics.js"></script>   ← 无 integrity

上游被篡改后（演示样例）：
  analytics.js 内容变成读取表单并外发的脚本
  → 所有用户中招，而本站代码一行未改

加 SRI 后（演示样例）：
  <script src="…" integrity="sha384-…" crossorigin="anonymous"></script>
  → 哈希不符，浏览器拒绝执行被篡改的脚本
```

note：材料为演示样例，域名与哈希为占位示例，非现场运行、非真实系统。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：判断「引入的代码是不是等于自己写的代码」。外链脚本与扩展跑在页面里，权限与自研代码完全一样——**信任它们就等于把页面钥匙交出去**。供应链攻击的狠处是：本站代码一行没改，用户却全量中招。
- **how（下一步看什么、怎么判断）**：① 列出全部第三方脚本/依赖清单；② 逐个问「有没有完整性校验（SRI）」「来源是否被 CSP 限制」；③ 检查扩展与 SDK 的权限申请是否超出所需；④ 修复按「最小化引入 + SRI + CSP + 定期审计」四件套。

〔本条术语锚点〕`frontend-supply-chain`、`supply-chain`、`sri`、`csp`、`third-party-script`

**相关术语网**：`frontend-supply-chain` → 上位概念：`supply-chain` ｜ 根治：`sri` ｜ 来源限制：`csp` ｜ 信任对象：`third-party-script` ｜ 泄露后果：`client-storage-leak`、`xss`

**realCases（选读，站外链接，不保证长期有效）**：
- `RC-207`｜某统计 SDK 供应链被投毒致批量数据外带（成因：无 SRI 的第三方脚本被篡改；教训：SRI + CSP 限源 + 最小化引入）｜来源：OWASP 第三方脚本风险说明〔权威〕
