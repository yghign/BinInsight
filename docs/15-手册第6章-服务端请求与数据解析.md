## 章导语

**共同本质**：**服务端替攻击者发起请求（SSRF），或解析攻击者构造的数据结构（XXE、反序列化、YAML），从而突破网络边界或执行代码。**一边是「借服务器的手去敲门」，一边是「让解析器照着伪造的说明书干活」——攻击者自己够不到的地方，服务端代劳；攻击者自己执行不了的代码，解析器代执行。

**与前五个主题的衔接**：注入类把数据变成指令，攻击发生在**服务端解析环节**（数据进指令位）；客户端攻击借浏览器执行内容，攻击发生在**受害者的浏览器里**；认证与会话攻击的是**身份证明**；访问控制与授权攻击的是**权限边界**；文件与服务端资源攻击的是**文件出入口**；本主题攻击的是**服务端的出站能力与解析能力**——它替谁干活、听谁的说明书。防御重心：出站请求要受控、解析器不信任数据结构、用户代码能力要么不给要么强隔离。

**本主题的三条底线**（6 条都可对号入座）：
1. **出站请求受控**：协议白名单 + 目标白名单 + 解析后校验（用校验过的 IP 发起请求），不随便替用户敲门。
2. **解析器不信任数据结构**：禁 DTD 与外部实体、安全加载（`safe_load`）、类白名单、拒绝重复键——说明书不能由递件人写。
3. **用户代码能力强隔离或不给**：规则引擎/脚本/表达式要么不开，要么独立进程+容器+无网络+资源限制。

**共同防护思路（三层）**：

1. **入口收敛（根治）**：URL 协议/目标白名单（复用 `allowlist`）；XML 禁 DTD；不反序列化不可信数据（改 JSON + 严格结构校验，复用 `type-validation`）。
2. **隔离收敛（加固）**：业务服务器与元数据/管理网段隔离；用户脚本独立进程容器化；解析资源限额（大小/深度/时间）。
3. **兜底**：出站流量代理与审计；解析异常告警；组件升级（历史缺陷多）。

**本主题难度一览**（难度=学习复杂度，与危险度★无关；中/高=知识卡+案例演示+静态指导，交互闯关留待后续批次；**本主题无低档条目，故无 3 题自测**——6 条都涉及机制/协议级理解，无「单一输入点+生活例子+无前置」全满足者）：

## 6.1 SSRF（服务端请求伪造）　`危险度 ★★★★★`　`本站难度：高`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: ssrf` ｜ `chapter: 6` ｜ `difficulty: advanced` ｜ `format: interactive` ｜ `scene: Web, 云` ｜ `hazard: 5` ｜ `aliases: SSRF, 服务端请求伪造, Server-Side Request Forgery, 服务器端请求伪造` ｜ `pinyin: {full: 'fu wu duan qing qiu wei zao', joined: 'fuwuqingqiuweizao', initial: 'fwdqqwz'}` ｜ `related: xxe, parser-defect, client-storage-leak` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=服务器出站请求的网络边界→试可达=内网/云元数据→判影响=临时凭证/内部服务→选根治=协议+目标白名单、解析后校验；06 §2.5 链式适用清单明确含 SSRF/云元数据）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 3 项——问①前置>2（服务端代发请求、云元数据服务、DNS 重绑定均为新概念；`trust-boundary`/`oob` 前序已讲不计入）；问②要理解协议与网络信任边界（服务器的位置即权限）；问③要构造 URL 请求与地址变体验证 → **高**。链式明显：SSRF 本身只是「敲门」，敲到云元数据→拿临时凭证→接管云资源才到沦陷。

**oneLiner（一句话）**：服务端按用户提供的 URL 发起请求时，攻击者借此让服务器访问内网服务、云元数据或本地文件，突破网络隔离。

**cause（成因与位置）**：图片/链接抓取、URL 预览、WebHook、PDF/截图生成、文件导入（`?url=`）、代理接口、RSS 订阅、翻译/OCR、回调验证——凡「由服务端发请求」且 URL 可控（哪怕只部分可控：域名可控、路径可控）的功能都是入口。**「为什么服务器发起的请求更危险」**：外网进不去的门（内网服务、云配置接口），**服务器自己去敲就开了**——它站在内网里、带着内网信任，甚至带着云主机的临时凭证。攻击者的 URL 只是「让谁去敲门」的指令。

**where（高发位置）**：`?url=`、`?image=`、`?callback=`、`?target=`、`?webhook=` 等完整 URL 参数；导出/截图/预览服务；第三方回调验证。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 回显型 SSRF | 响应里带回目标内容 | 能读到 `http://127.0.0.1:端口` 的响应 |
| 盲 SSRF | 看不到响应但请求发出 | 带外平台/DNSLog 收到服务器的请求 |
| 协议滥用 | 换协议读文件/发命令 | `file://`、`gopher://`、`dict://` 生效 |
| 重定向/DNS 绕过 | 校验后目标再变 | 外部 302 跳内网、DNS 重绑定 |

**signals（典型特征）**：
- 参数是完整 URL：`?url=`、`?image=`、`?callback=`、`?target=`、`?webhook=`。
- 可让服务器访问你自己的 HTTP 服务（用带外平台或自建监听确认）。
- 能读到 `http://127.0.0.1:端口` 的响应（回显型）；能访问云元数据地址（如 `http://169.254.169.254/latest/meta-data/`——IMDS，云主机内默认可访问的「本机配置查询口」，可查临时凭证）。
- 地址变形（十进制/十六进制/IPv6 缩写）与重定向后目标变化。

**impact（危害）**：内网探测与端口扫描；访问未授权内部服务（Redis、Elasticsearch、K8s API、Jenkins 等）；窃取云主机临时凭证（AWS/GCP/阿里云元数据）→ 接管云资源；读取本地文件（`file://`）；经 `gopher` 等协议构造内部服务命令。

**verify（挖掘与验证思路）**：
1. 列出所有「由服务端发请求」的功能，确认 URL 是否可控（域名可控/路径可控都算）。
2. 用**带外通道**（DNSLog / 自建 HTTP 服务，复用 `oob` 思路）确认服务器真的发出了请求。
3. 测试协议：`http`、`https`、`file`、`gopher`、`dict`、`ftp`。
4. 测试地址变形：`127.0.0.1`、`localhost`、`0.0.0.0`、`[::1]`、十进制/十六进制表示、`127.1`、`foo@127.0.0.1`。
5. 测试重定向绕过（外部 URL 302 跳内网——校验只发生在第一次请求）与 DNS 重绑定（首次解析到公网过校验、再次解析到内网）。
6. 盲 SSRF：以时间差异判断端口开放。

**protect（防护）**：
- **root（根治）**：**协议白名单**（只允许 http/https）+ **目标白名单**（只允许业务确需的域名/IP 段，复用 `allowlist`）；**解析后校验**——先 DNS 解析，对解析出的 IP 做内网/保留地址校验，并且**用校验过的 IP 发起请求**（防 DNS 重绑定）。
- **harden（加固）**：禁止跟随重定向，或对每一跳重新校验；网络层隔离（业务服务器不达元数据服务与管理网段；云上使用 IMDSv2——需临时令牌且限制跳数）；不把原始响应体返回给用户（降低回显型价值）。
- **fallback（兜底）**：出站流量统一走代理并审计；异常出站告警。

**mistakes（易错点）**：
- 只黑名单 `127.0.0.1`（十进制/十六进制/IPv6 缩写/DNS 变形绕过）。
- 只校验第一次请求（302 重定向绕过）。
- 校验用字符串匹配而不解析 URL（`http://evil.com#@127.0.0.1` 之类的解析差异）。
- 忽略盲 SSRF——看不到回显不等于没打到内网（带外确认照样成立）。

**演示样例材料**（language: plaintext）：

```
场景（演示样例，站点 example.com 的「网页预览」功能）：
服务端逻辑（演示样例）：
  resp = http_get($_GET['url']);     ← 用用户给的 URL 发起请求，返回内容摘要

攻击步骤：
1. 正常请求：GET /preview?url=https://example.org/page
   → 服务端抓取外网页（正常）
2. 内网探测：GET /preview?url=http://127.0.0.1:6379/
   → 服务端从自己所在网段访问本机 Redis 端口（外网进不来的门，服务器自己敲就开）
3. 云元数据：GET /preview?url=http://169.254.169.254/latest/meta-data/
   → 服务端访问云元数据服务（IMDS），返回云主机临时凭证（演示样例，虚构响应）

逻辑链自查（硬标准：参数与目标逐字符对上，包括协议/主机/端口/路径，无隐藏前后缀拼接）：
输入（url 参数，服务端原样使用、无前缀后缀包装）
→ 机制（服务端以自己的网络身份发起请求，带着内网位置与云凭证）
→ 结果（②探到内网端口、③读到云元数据）✔
逐字符核对：url=http://169.254.169.254/latest/meta-data/
  → 请求目标即该 URL 本体：协议 http、主机 169.254.169.254、路径 /latest/meta-data/ ✔ 无拼接
  → url=http://127.0.0.1:6379/ → 目标为本机 6379 端口本体 ✔
```

note：材料为演示样例，站点、端口、响应均为虚构，非现场运行、非真实系统。修法对照：协议白名单（第 3 步的 file/gopher 类被拒）+ 目标白名单（127.0.0.1/169.254.169.254 不在名单被拒）+ 解析后校验用校验过的 IP 发起（重绑定失效），任一层到位即断链。DNS 重绑定口径：重绑定场景需两次 DNS 解析间隔（首次解析到公网过校验、再次解析到内网），本卡不展开；修法「用校验过的 IP 发起请求」正是堵这个窗口。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「服务端会不会按用户给的地址去敲门」。关键不是「有没有 `url=` 参数」，而是**服务器替谁干活、带着什么信任**——内网位置、云凭证都是它的「通行证」，攻击者只是递了张纸条。盲 SSRF 也要盯：看不到响应≠没敲到门（带外确认）。

## 6.2 XXE（XML 外部实体注入）　`危险度 ★★★★★`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: xxe` ｜ `chapter: 6` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, 系统` ｜ `hazard: 5` ｜ `aliases: XXE, XML 外部实体注入, XML External Entity, XML 实体注入` ｜ `pinyin: {full: 'wai bu shi ti zhu ru', joined: 'waibushitizhuru', initial: 'wbstzr'}` ｜ `related: ssrf, deserialization, parser-defect` ｜ `source: demo` ｜ `templateId: TPL-INJECT`（认信号=实体被解析→认类型=回显/盲（OOB）→判严重=读文件/SSRF→选根治=禁 DTD 与外部实体；「数据被当结构解析」是注入骨架同构——实体声明把数据变形成取件指令）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 2 项——问②要理解 XML 实体解析机制（实体=给内容起别名、别名可指向外部资源，解析器代取）；问③要构造 XML 载荷验证。问①边缘不命中：DTD/实体/参数实体同属「实体机制」一个机制家族，按前置概念计数规则不逐词计 → **中**。**边界说明**：若要求独立构造参数实体+外部 DTD 的盲外带完整链，难度升为高——本卡目标是「认出实体被解析 + 布防」，不要求到那一层。

**oneLiner（一句话）**：XML 解析器允许外部实体时，攻击者可在 XML 里定义实体引用本地文件或远程 URL，从而读取文件、发起请求，特定环境下可执行代码。

**cause（成因与位置）**：默认配置的 XML 解析器（Java `DocumentBuilderFactory`/`XMLReader`、Python `lxml`、PHP `SimpleXML` 等）会解析文档里的实体声明。「实体」本是给内容起别名的机制（写一次 `&xxe;` 多处复用），但**别名可以指向外部资源**（`SYSTEM "file:///etc/passwd"`）——解析器展开实体时就替用户去取。**「为什么 XML 能读文件」**：文档变成了「取件单」——`&xxe;` 是取件码，`SYSTEM` 后的地址是取件柜，解析器照单取件、把内容填回文档。入口伪装多：SOAP 接口、SVG 上传、DOCX/XLSX（本质是 zip+XML）、RSS、SAML 断言、配置文件导入。

**where（高发位置）**：`Content-Type: application/xml` / SOAP 接口、SVG 图片、Office 文件导入、`.xml` 配置导入、SAML 断言（认证与会话主题的 SAML 条目已注明 XXE 归本主题——本条落地即收编该引用）。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 有回显 XXE | 文件内容直接回显 | 响应中出现文件内容 |
| 盲 XXE / OOB | 无回显但外部请求发出 | 实体指向攻击者服务器，DNS/HTTP 日志可见 |
| 参数实体外带 | 用外部 DTD 借道外带 | 组合参数实体把文件内容发到外部 |
| 膨胀拒绝服务 | 实体递归撑爆内存 | Billion Laughs 类载荷（解析缺陷面，见 6.5） |

**signals（典型特征）**：
- 插入 `DOCTYPE` 与实体定义后被接受、被解析（返回内容中出现文件内容=有回显）。
- 无回显时实体指向外部服务器，DNS/HTTP 日志出现解析器的请求（盲 XXE/OOB）。
- 报错信息中出现实体解析相关错误。
- 入口在 SVG/Office/SAML 等「不像 XML」的地方。

**impact（危害）**：读取任意文件（配置、密钥、源码）；SSRF（解析器代发请求，与 6.1 同害）；内网探测；拒绝服务（实体膨胀）；特定环境下代码执行（如 PHP `expect://` 类封装、配合反序列化链）。

**verify（挖掘与验证思路）**：
1. 找所有接收 XML 的接口（`Content-Type: application/xml`、SOAP、文件导入、SVG/Office 上传）。
2. 尝试插入 `DOCTYPE` 与实体定义，观察是否被接受、是否解析。
3. 有回显 → 直接读文件；无回显 → 外部 DTD + 参数实体做 OOB 外带（复用 `oob`）。
4. 注意入口伪装：SVG、DOCX/XLSX/PPTX、`.xml` 配置、SAML 断言。

**protect（防护）**：
- **root（根治）**：解析器**禁用 DTD 与外部实体**（Java `disallow-doctype-decl`、Python lxml `resolve_entities=False`、.NET `DtdProcessing=Prohibit`）；业务允许时用 JSON 替代 XML。
- **harden（加固）**：上传的 Office/SVG 做安全解析或转换（与文件与服务端资源主题 5.5 的解析面互引）；升级解析库，避免已知绕过（部分老版本防护开关可被绕过）。
- **fallback（兜底）**：解析资源限额（防膨胀，见 6.5）；异常解析告警。

**mistakes（易错点）**：
- 只防一个解析器（项目里常有多处 XML 解析入口）。
- 只测 SOAP 不测文件上传（SVG/Office 就是 XML）。
- 以为「内网接口不需要防」——内网接口被 XXE 打穿同样失守。
- 只关外部实体不关 DTD（部分场景仍可膨胀/绕过）。

## 6.3 反序列化漏洞　`危险度 ★★★★★`　`本站难度：高`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: insecure-deserialization` ｜ `chapter: 6` ｜ `difficulty: advanced` ｜ `format: interactive` ｜ `scene: Web, 系统` ｜ `hazard: 5` ｜ `aliases: 反序列化漏洞, 不安全反序列化, Insecure Deserialization, gadget 链` ｜ `pinyin: {full: 'fan lie xua hua lou dong', joined: 'fanliexuhualoudong', initial: 'flxhld'}` ｜ `related: parser-defect, xxe, sandbox-escape` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=还原过程→试可达=gadget 链触发→判影响=任意执行→选根治=不反序列化/类白名单；利用本体就是链式，骨架天然贴合）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 3 项——问①前置>2（序列化/还原机制、gadget 链、魔术方法/类白名单多个新概念）；问②要理解「还原对象=按数据里的指令重建」这一底层机制；问③要构造匹配目标组件的载荷验证 → **高**。与 06 §3.3 锚定示例（反序列化=高：要理解 gadget/链式概念多）维持一致。

**oneLiner（一句话）**：程序把不可信数据按字节流「还原成对象」时，攻击者塞进去的类名和调用关系被当作指令执行，触发任意代码。

**cause（成因与位置）**：序列化是「把对象变成字节流」，反序列化是「按字节流重建对象」——重建过程会**照着数据里的类名与调用关系走**。攻击者只要能提交字节流，就能塞进「要重建什么类、重建时触发什么」的指令。**「为什么还原对象会执行代码」**：还原不是「读数据」，而是「按说明书组装」——说明书（字节流）由攻击者写，组装线上有带副作用的零件（gadget）。**gadget 链像多米诺：第一块倒下，后面连环触发**——单个类的读取/析构方法无害，但类与类连成链就通到命令执行。入口：Java `ObjectInputStream`、Fastjson `@type`、Shiro `rememberMe` Cookie、PHP `unserialize()`、Python `pickle.loads`/`yaml.load`、.NET `BinaryFormatter`、Node `node-serialize`。

**where（高发位置）**：Cookie/请求体里的长 Base64（`data`、`token`、`state`、`viewState` 参数）、Session 存储、缓存（Redis 对象）、RMI/中间件协议（T3 等）、JSON 的 `@type` 字段。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 字节流还原 | 二进制序列化载荷 | `rO0AB`（Java Base64 头）、`aced0005` 魔术字节 |
| JSON 自动类型 | JSON 里的类型声明被当指令 | `{"@type":"..."}` 类字段 |
| 魔术方法触发 | 还原/销毁时钩子被调用 | PHP `__destruct/__wakeup`、Python `__reduce__` |
| gadget 链利用 | 类与类连成链，连环触发到危险操作 | 目标环境组件匹配（Commons 系/Spring 系等） |
| 中间件/缓存还原 | 存储里的对象被还原 | Redis 缓存对象、Session 反序列化 |

**signals（典型特征）**：
- 请求体或 Cookie 中出现 `rO0AB`（Java 序列化 Base64 头）、`aced0005`（十六进制魔术字节）、`O:8:"stdClass"`（PHP）、`__reduce__`（Python）。
- Cookie `rememberMe=deleteMe`（Shiro 特征）；JSON 可提交 `{"@type":"..."}`。
- 参数名像 `data`/`token`/`state`/`viewState`，内容是长 Base64。

**impact（危害）**：即使无可用 gadget 链，也可造成拒绝服务或信息泄露（复用 `info-leak`，这是更常见的情形）；一旦有匹配的 gadget 链则直达远程代码执行（复用 `rce`，通常直接判严重）。

**verify（挖掘与验证思路）**：
1. **识别**：抓包看数据特征（Base64 解码看魔术字节）；看框架指纹（Shiro、Fastjson、WebLogic 等）。
2. **确认还原点**：修改数据后是否报反序列化相关错误（类找不到/类不匹配异常）——报错即证明在还原。
3. **构造利用链**：需要与目标组件匹配的 gadget（常用 ysoserial 类工具生成载荷，授权环境）。
4. 无回显时用带外/延时确认执行成功（复用 `oob`）。
5. 注意「看起来不是序列化」的地方：`viewState`、Session、缓存对象、远程调用协议。

**protect（防护）**：
- **root（根治）**：**不还原不可信数据**——首选架构方案改用 JSON + 严格结构校验（复用 `type-validation`）；必须使用时**类白名单**（只允许可还原的类）。
- **harden（加固）**：签名校验（HMAC 防篡改）；禁用自动类型（Fastjson 安全模式）；更换硬编码默认密钥（如 RememberMe 的 AES key 硬编码是经典问题）；升级组件（Shiro/Fastjson/XStream 历史缺陷多）。
- **fallback（兜底）**：隔离运行（低权限、容器、出站限制）——即使被利用也难以横向。

**mistakes（易错点）**：
- 只关注请求体忽略 Cookie/Session/缓存。
- 只测 Java 忽略 PHP/Python/.NET。
- 以为「用了 JSON 就安全」——JSON 库的自动类型机制同样是反序列化。
- 忽略中间件与缓存（Redis 里的对象还原）。

**演示样例材料**（language: plaintext）：

```

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「有没有把用户数据当说明书组装对象」。判断它存在不难（魔术字节/报错特征），难在理解**为什么危险**——还原过程会执行数据里的调用链。一句话记牢：**字节流是递件人写的说明书，组装线不能照单全收**。

〔本条术语锚点〕`gadget-chain`（本条新增）｜ `deserialization`、`rce`、`type-validation`（复用，更早主题）

## 6.4 表达式/脚本沙箱逃逸　`危险度 ★★★★★`　`本站难度：高`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: sandbox-escape` ｜ `chapter: 6` ｜ `difficulty: advanced` ｜ `format: interactive` ｜ `scene: Web, 系统` ｜ `hazard: 5` ｜ `aliases: 沙箱逃逸, 表达式逃逸, 脚本逃逸, Sandbox Escape` ｜ `pinyin: {full: 'biao da shi sha xiang tao yi', joined: 'biaodashishaxiangtaoyi', initial: 'bdsxty'}` ｜ `related: expression-engine, insecure-deserialization, rce` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=沙箱边界→试可达=逃逸手法（反射/内置对象/危险 API）→判影响=宿主权限→选根治=不给能力或独立进程容器隔离；边界逃逸链）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 3 项——问①前置>2（沙箱模型、逃逸手法、资源限制多个新概念）；问②要理解「能力边界」这一底层机制（表达力与宿主系统只隔一层限制）；问③要构造脚本验证逃逸 → **高**。

**oneLiner（一句话）**：应用提供「可执行用户脚本」的能力（规则引擎、公式、插件、表达式）时，沙箱限制不严可逃逸到宿主系统执行任意操作。

**cause（成因与位置）**：规则引擎/公式字段/插件系统/模板表达式（JEXL、Groovy、JS 引擎、SpEL 等，表达式引擎概念复用 `expression-engine`）让用户能写「一点逻辑」。**「为什么给了脚本能力就危险」**：脚本的表达力与宿主系统**只隔一层限制**——限制靠黑名单（禁几个关键字）就总有旁路（反射、内置对象、类加载器），限制不严即穿透到宿主。沙箱的本质是「能力白名单」，不是「危险词过滤」。

**where（高发位置）**：低代码平台的公式/表达式字段、规则引擎、模板表达式（SSTI 的姊妹面，见注入类主题）、报表自定义脚本、插件机制、工作流条件表达式。

**kinds（分类）**（前三类是穿透沙箱限制的手法，第四类是资源上限缺失的另一维度——不是「逃出去」而是「没拦住消耗」，同属能力边界失守）：

| 类型 | 白话 | 信号 |
|---|---|---|
| 反射逃逸 | 绕过黑名单摸到危险类 | 反射/类加载拿到宿主能力 |
| 内置对象滥用 | 从脚本环境的内置对象出发 | 经内置对象链走到系统 API |
| 危险 API 未禁 | 白名单没盖住危险能力 | 文件/网络/进程 API 可调 |
| 资源无限制 | 算力被脚本吃满 | 死循环/巨量分配拖垮服务 |

**signals（典型特征）**：
- 应用接受用户提交的表达式/脚本片段并在服务端求值。
- 沙箱靠「禁用几个关键字/类名」实现（黑名单式）。
- 脚本环境里可访问反射、类加载、文件/网络/进程 API。
- 表达式引擎版本老旧（历史逃逸缺陷多）。

**impact（危害）**：宿主系统任意代码执行（复用 `rce`）；数据读取/篡改；拒绝服务（资源耗尽）。

**verify（挖掘与验证思路）**：
1. 盘点「用户能写逻辑」的功能（公式、规则、插件、模板表达式）。
2. 确认求值位置（服务端还是客户端）与沙箱实现方式（黑名单/白名单/独立进程）。
3. 授权环境试探逃逸手法（内置对象链、反射类名，无害验证）；测试资源限制（超时/内存上限）。

**protect（防护）**：
- **root（根治）**：**不给用户脚本能力**（用预置规则选项替代表达式）；必须给时白名单 API（只暴露必要函数）。
- **harden（加固）**：独立进程 + 容器 + 无网络 + 只读文件系统 + 严格超时与资源限制；表达式引擎升级到无已知逃逸的版本。
- **fallback（兜底）**：脚本执行审计留痕；异常调用告警。

**mistakes（易错点）**：
- 用黑名单禁关键字当沙箱（反射/内置对象旁路无穷）。
- 只限制函数不限制资源（死循环照样拖垮）。
- 以为「客户端求值就安全」——逻辑一旦回服务端求值就是服务端风险。
- 与注入类主题的表达式注入混为一谈（那里是「输入进表达式」，本条是「给了表达式能力」——入口不同、根治同源）。

## 6.5 XML / JSON / YAML 解析缺陷　`危险度 ★★★☆☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: parser-defect` ｜ `chapter: 6` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, 系统` ｜ `hazard: 3` ｜ `aliases: 解析缺陷, Billion Laughs, YAML 反序列化, 重复键, JSON 深嵌套` ｜ `pinyin: {full: 'jie xi que xian', joined: 'jiexiquexian', initial: 'jxqx'}` ｜ `related: xxe, insecure-deserialization, redos` ｜ `source: demo` ｜ `templateId: TPL-INJECT`（认信号=畸形输入致解析异常→认类型=膨胀/深嵌套/重复键/精度→判严重=拒绝服务/权限绕过/金额篡改→选根治=限额/安全加载/拒绝重复键；「数据被当结构解析」注入骨架同构）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 2 项——问②要理解「解析器按数据结构的指引干活」这一机制；问③要构造畸形结构验证（膨胀/深嵌套/重复键载荷）。问①边缘不命中：五个变体都属「解析器信任数据结构」一族，按机制家族计一个 → **中**。

**oneLiner（一句话）**：XML/JSON/YAML 解析器被攻击者构造的数据结构触发缺陷——实体膨胀撑爆内存、深层嵌套耗尽 CPU、重复键造成取值分歧、精度丢失造成金额篡改。

**cause（成因与位置）**：结构化数据的「结构」本身携带指令性——XML 实体可递归展开、JSON 可无限嵌套、YAML 可声明任意对象、键可重复。解析器照单处理时没有限额与一致性约束，缺陷就出在「结构被信任过头」。**「为什么重复键能改权限」**：`{"role":"user","role":"admin"}` 里两个同名键，不同解析器取值不同（有的取第一个、有的取最后一个）——攻击者让「校验层看 user、执行层看 admin」，**两段代码各取所需**，权限分歧就成了绕过。

**where（高发位置）**：XML/JSON/YAML 接口与文件导入、配置解析、金额/数量字段、带权限字段的请求体。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 实体膨胀 | 递归实体撑爆内存 | Billion Laughs 类载荷致拒绝服务 |
| YAML 不安全加载 | YAML 声明任意对象 | `yaml.load` 可构造对象 → 还原执行（联动 6.3） |
| JSON 深嵌套 | 超深嵌套耗尽资源 | 栈溢出/CPU 耗尽 |
| 重复键分歧 | 同名键各取所需 | 校验层与执行层取值不同 |
| 数字精度 | 大数/浮点丢精度 | 金额篡改（JSON 与后端语言精度差异） |

**signals（典型特征）**：
- 小体积载荷引发大资源消耗（膨胀/深嵌套）。
- 重复键请求体在不同层行为不一致。
- 金额/数量在传输后发生微小变化（精度丢失）。
- YAML 加载用的是不安全模式（非 `safe_load`）。

**impact（危害）**：拒绝服务（内存/CPU 耗尽）；权限绕过（重复键）；金额篡改（精度）；YAML 不安全加载直达代码执行（与 6.3 同害）。

**verify（挖掘与验证思路）**：
1. 构造实体膨胀/深嵌套载荷（演示样例，限资源环境），观察内存/CPU 与响应时间。
2. 重复键载荷分别观察校验层与执行层的取值。
3. 金额字段传大整数/高精度浮点，核对入账值。
4. 检查 YAML 加载模式（`safe_load` 与否）、JSON 解析库的深度/大小限制。

**protect（防护）**：
- **root（根治）**：限制实体展开、文档大小与嵌套深度；YAML 用 `safe_load`（复用 `type-validation` 思路）；**拒绝重复键**。
- **harden（加固）**：金额用字符串或整数分传递（不走浮点）；解析超时与内存上限。
- **fallback（兜底）**：解析异常告警；组件升级。

**mistakes（易错点）**：
- 只测功能正确性不测畸形输入（解析缺陷都是「怪输入」触发的）。
- 以为「JSON 比 XML 安全」——深嵌套、重复键、精度问题 JSON 同样有。
- YAML 沿用不安全加载（历史上多次直接 RCE）。
- 重复键当小问题（它是权限绕过，见访问控制与授权主题的参数污染招式）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
场景（演示样例，站点 example.com 的「更新个人资料」JSON 接口）：
服务端逻辑（演示样例）：
  body = json_parse(request.body)      ← 解析 JSON
  validate(body.role)                  ← 校验层看 role
  user.role = body.role                ← 执行层赋值

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「结构本身会不会发号施令」。膨胀=结构让解析器做重活、深嵌套=结构让解析器走死路、重复键=结构让两段代码各看各的、精度=结构在传输中变形。一句话：**结构不能带指令性，解析器要限额、要一致、要拒绝歧义**。
- **how（下一步看什么、怎么判断）**：① 找全部结构化数据入口；② 四类畸形载荷各试一遍（膨胀/嵌套/重复键/精度）；③ 查 YAML 加载模式与解析限额；④ 修复按「限额+safe_load+拒重复键+金额字符串化」四件套。

## 6.6 ReDoS（正则表达式拒绝服务）　`危险度 ★★☆☆☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: redos` ｜ `chapter: 6` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, 系统` ｜ `hazard: 2` ｜ `aliases: ReDoS, 正则拒绝服务, 正则表达式拒绝服务, Regular Expression DoS` ｜ `pinyin: {full: 'zheng ze biao da shi ju jue fu wu', joined: 'zhengzebiaodashijujiefuwu', initial: 'zzbdsjjfw'}` ｜ `related: parser-defect, rate-limiting` ｜ `source: demo` ｜ `templateId: TPL-CHAIN（贴合度中等，已注明）`（认边界=回溯触发点→试可达=灾难串→判影响=CPU 耗尽→选根治=线性引擎/超时；触发→放大的资源耗尽链，第二期按「触发-放大」形态设计不硬套四关）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 2 项——问②要理解「正则引擎回溯」这一机制（为何嵌套量词让匹配尝试指数爆炸）；问③要构造灾难性输入验证 → **中**。**边界说明**：若要求独立证明回溯复杂度、构造最小化灾难串，难度升为高——本卡目标是「认出风险正则 + 布防」，不要求到那一层。

**oneLiner（一句话）**：存在灾难性回溯的正则（如嵌套量词 `(a+)+$`）处理超长恶意输入时，匹配尝试指数爆炸，CPU 被拖满、服务不可用。

**cause（成因与位置）**：正则引擎匹配失败时会**逐个尝试所有可能的分组组合**（回溯）。嵌套量词（`(a+)+`）+ 重叠分支让组合数随输入长度指数增长。**「为什么正则能拖垮服务」**：引擎找不到匹配时不甘心，把每条岔路都走一遍再回头——岔路数量随输入指数增长，一个小输入就能让 CPU 一直算下去。校验接口（邮箱/手机号/密码规则）是最常见入口：**校验器本该是防线，却成了拒绝服务的入口**。

**where（高发位置）**：输入校验的正则（邮箱、手机号、密码强度、URL、身份证）、搜索/过滤的正则参数、日志分析规则。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 嵌套量词 | `(a+)+` 类模式 | 特定长输入响应指数变慢 |
| 重叠分支 | `(a|a)+` 类模式 | 两个分支能匹配同一段 |
| 回溯炸弹 | 精心构造的失败串 | 短输入引发长耗时 |

**signals（典型特征）**：
- 某个输入校验接口在特定字符串下响应时间指数增长。
- 正则含嵌套量词（`(x+)+`、`(x*)*`）或重叠分支（`(a|a)+`）。
- 无输入长度限制、无正则执行超时。

**impact（危害）**：单请求即可拖满 CPU、无需并发——与一般 DoS（靠流量/并发堆资源）有本质区别，一个精心构造的输入就足以让服务不可用；配合并发可放大成全站不可用。

**verify（挖掘与验证思路）**：
1. 收集全部服务端正则（校验/解析/过滤），识别嵌套量词与重叠分支。
2. 构造递增长度的失败输入（演示样例），测响应时间曲线（指数增长即命中）。
3. 测输入长度限制与执行超时是否存在。

**protect（防护）**：
- **root（根治）**：避免嵌套量词与重叠分支；改用线性时间的正则引擎（RE2 类，无回溯设计）。
- **harden（加固）**：限制输入长度；正则执行设超时。
- **fallback（兜底）**：慢请求告警与限流（复用 `rate-limiting`）。

**mistakes（易错点）**：
- 以为「正则只是校验，无风险」——校验器正是被怪输入打的入口。
- 只限制请求频率不限输入长度（单个长请求照样拖满）。
- 用复杂正则追求「一条全匹配」——复杂度正是风险来源。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
场景（演示样例，站点 example.com 的邮箱格式校验）：
服务端逻辑（演示样例）：
  re.match(r'^(\w+\s?)*$', user_input)    ← 嵌套量词 (\w+\s?)*

攻击输入（演示样例）：
  "aaaaaaaaaaaaaaaaaaaaaaa!"             ← 24 个 a + 感叹号（结尾不匹配）

机制：
  引擎把 24 个 a 按 (\w+\s?)* 的所有分组组合逐一尝试后失败
  组合数随 a 的个数指数增长 → CPU 耗时指数上升

逻辑链自查（硬标准：正则模式与触发串逐字符对上，包括量词嵌套与结尾不匹配字符）：
输入（结尾不匹配的长串，触发回溯）
→ 机制（嵌套量词使匹配尝试组合数指数爆炸，引擎逐条回溯）
→ 结果（单请求 CPU 耗尽，接口不可用）✔
逐字符核对：模式 ^(\w+\s?)*$ 为嵌套量词结构（(\w+\s?)* 外层 * 内层 +）✔
           触发串 "aaa…a!" 结尾字符 ! 不在 \w/\s 类 → 全部组合尝试后失败 ✔
           （若串以 a 结尾会匹配成功、无爆炸——不匹配的结尾是触发关键）✔
```

note：材料为演示样例，站点与正则为虚构，输入为无害字符，非现场运行、非真实系统。修法对照：改线性引擎/拆解正则（无指数回溯）+ 输入长度限制 + 执行超时（第 2 步机制不成立）。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「校验用的正则长什么样」。嵌套量词 + 失败结尾 = 回溯炸弹。校验器是每个请求都要过的门——**门本身被怪输入卡死，全员过不去**。风险不在正则「复杂」，在「回溯组合数」。
- **how（下一步看什么、怎么判断）**：① 收集服务端正则，找嵌套量词/重叠分支；② 递增长度失败输入测时间曲线；③ 查长度限制与超时；④ 修复按「线性引擎/拆正则+限长度+设超时」三件套。
