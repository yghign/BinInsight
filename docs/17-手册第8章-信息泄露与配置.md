## 章导语

**共同本质**：**不该被看到的东西被看到了。**单个信息泄露往往只是低危，但它是所有攻击链的起点——拿到源码可以白盒找洞，拿到密钥可以直接接管，拿到路径可以少走一半弯路。前面是主动攻击的洞，本章是系统**自己把信息亮出来**。

**与前七个主题的衔接**：注入类把数据变成指令（攻击发生在服务器解析环节）；客户端攻击借浏览器执行内容（受害者浏览器里）；认证与会话攻击**身份证明**；访问控制与授权攻击**权限边界**；文件与服务端资源攻击**文件出入口**；服务端请求与数据解析让服务端**替攻击者干活**；逻辑与业务流程攻击**流程与规则的缺口**——七个主题都是攻击者主动动手；本主题是**暴露面**：信息本身站错了位置，攻击者只是看了一眼。防御重心也因此不同：前七章修「洞」，本章修「摆放」——秘密不进代码、生产面收敛、敏感数据脱敏。

**四处易混边界（逐条划清）**：
1. **8.2 源码与备份文件泄露 vs 访问控制与授权主题 4.3 路径穿越 / 文件与服务端资源主题 5.3 任意文件读取**：4.3/5.3 是**手法**（怎么拿到文件——穿越目录、越权读取），本章是**暴露面**（文件本来就放在可被访问的位置）——攻击者不需要任何技巧，敲个地址就有。
2. **8.3 报错信息泄露 vs 注入类主题 1.1 SQL 注入的报错回显**：注入类的报错是**信号面**（报错文本证明注入存在、借报错带出数据）；本章是**信息本身的泄露**（堆栈、配置、内部路径、版本号）——前者报错是攻击的工具，后者报错是泄露的货物。
3. **配置不当 vs 各主题的防护配置**：本章的配置是**暴露面配置**（目录列表、默认凭据、调试模式、缓存键），不是某漏洞的防护配置（CSP、白名单、参数化查询那些是各主题 protect 的内容）。
4. **8.6 调试端点未授权 vs 访问控制与授权主题 4.4 强制浏览**（实读时发现的第四处边界）：同一现象两个视角——4.4 讲「入口隐藏 ≠ 鉴权」（授权视角，修法是补鉴权），8.6 讲「调试端点不该出现在生产公网」（配置视角，修法是关端点/收敛暴露面）；4.4 的信号清单里有 `/actuator`、`/swagger-ui.html` 等端点，本章 8.6 是这些端点的专题（含 heapdump 提取密钥等高价值面）。

**共同防护思路（三层）**：

1. **秘密不进代码（根治）**：密钥放密钥管理服务；前端不持有长期密钥；泄露立即**轮换**（删除代码不等于止血）。
2. **生产面收敛（加固）**：统一错误页、关 debug 模式、关目录列表、改默认口令、调试/管理端点关闭或鉴权、Web 根只放该放的。
3. **敏感数据脱敏（兜底）**：日志脱敏、元数据清理（EXIF/文档属性）、监控系统鉴权与隔离。

**本主题难度一览**（难度=学习复杂度，与危险度★无关；低=知识卡+3 题自测，中/高=知识卡+案例演示+静态指导，交互闯关留待后续批次）：

## 8.1 敏感信息硬编码　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: hardcoded-secret` ｜ `chapter: 8` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, 移动` ｜ `hazard: 4` ｜ `aliases: 敏感信息硬编码, 密钥硬编码, 硬编码密钥, AK/SK 泄露` ｜ `pinyin: {full: 'min gan xin xi ying bian ma', joined: 'minganxinxiyingbianma', initial: 'mgxxybm'}` ｜ `related: source-leak, debug-endpoint` ｜ `source: demo` ｜ `templateId: 不挂（静态暴露面检查型——看产物即发现，无攻击骨架可套，不硬凑；第二期若做闯关按「找暴露点」形态设计）`｜ `stages: []`（第二期补）

**难度判定**：三问法命中 1 项（问③：四个载体需分别用不同手段验证——看 bundle/查配置/反编译 App/翻 Git 历史）+ **多变体补充规则**（≥3 个需要分别验证的变体：JS bundle/源码配置/移动 App 包/Git 历史，kinds 表逐条列出）→ 判**中**。问①不命中：核心机制「密钥写进了代码」一句话；问②不命中：无协议/状态机。**「为什么删代码不等于止血」**：Git 历史里被「删除」的密钥仍可还原——密钥一旦进过版本库就必须**轮换**，删代码只是藏了现场。

**oneLiner（一句话）**：密钥、口令、内部地址被写进代码或前端产物时，谁拿到产物（JS bundle、App 包、Git 历史）谁就拿到钥匙。

**cause（成因与位置）**：开发时图省事把凭证写进代码/配置/前端；发布时产物原样下发。四个载体各有一条泄露路径：前端 JS bundle 随页面下发（打开即见）、源码配置随部署落地、App 包反编译即得、Git 历史记录一切（删了也能翻出来）。

**where（高发位置）**：前端 JS bundle（AK/SK、地图 key、内部接口地址、测试账号）；源码/配置（数据库口令、JWT 密钥、支付密钥）；移动 App 包（反编译）；Git 历史（被删的密钥）。

**kinds（分类）**（四载体四变体，多变体补充规则依据）：

| 类型 | 白话 | 信号 |
|---|---|---|
| 前端 bundle 硬编码 | 密钥随 JS 下发 | F12 看 JS 里有 AK/SK、key |
| 源码/配置硬编码 | 口令写在配置里 | 配置文件含数据库口令、JWT 密钥 |
| App 包硬编码 | 打包进移动应用 | 反编译包里有密钥 |
| Git 历史泄露 | 删掉的密钥还在历史里 | `git log` 能翻出旧版密钥 |

**signals（典型特征）**：
- 前端 JS bundle 中出现 AK/SK、地图 key、内部接口地址、测试账号。
- 源码/配置中出现数据库口令、JWT 密钥、第三方支付密钥。
- 移动 App 包中硬编码密钥（反编译即得）。
- Git 历史中有被「删除」的密钥（历史仍可查）。

**impact（危害）**：云端资源被接管（AK/SK 直接调云 API）；数据库失守；JWT 可伪造任意身份（联动认证与会话主题 JWT 缺陷）；测试账号进生产。

**verify（挖掘与验证思路）**：
1. 前端：打开 F12 / 读打包后的 JS，搜 `key`、`secret`、`token`，以及云厂商密钥前缀（AWS=`AKIA`、腾讯云=`AKID`、阿里云=`LTAI`）等模式（演示样例，自有资产）。
2. 源码/配置：检查部署产物里的配置文件；注意区分「占位符」与「真实值」。
3. App：反编译检查字符串常量。
4. Git：`git log -p` 翻历史（含被删行）。

**protect（防护）**：
- **root（根治）**：密钥统一放密钥管理服务（KMS/Vault）；前端不持有任何长期密钥（用短时令牌换）。
- **harden（加固）**：CI 集成密钥扫描（提交前拦）；移动端用服务端换发令牌。
- **fallback（兜底）**：密钥泄露后**立即轮换**（不只是删除代码——Git 历史还在）。

**mistakes（易错点）**：
- 删代码当止血（Git 历史仍可查，必须轮换）。
- 只查源码不查产物（bundle/App 是下发到用户手里的）。
- 以为「内部 key 不重要」（地图 key 被刷量、测试账号进生产都算）。
- CI 扫描只扫新增不扫历史。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

## 8.2 源码与备份文件泄露　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: source-leak` ｜ `chapter: 8` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web` ｜ `hazard: 4` ｜ `aliases: 源码泄露, 备份文件泄露, .git 泄露, 源码与备份泄露` ｜ `pinyin: {full: 'yuan ma yu bei fen wen jian xie lou', joined: 'yuanmayubeifenwenjianxielou', initial: 'ymybfwjxl'}` ｜ `related: hardcoded-secret, directory-listing, forced-browsing` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=Web 根暴露面→试可达=访问备份/隐藏文件→判影响=源码与密钥泄露（白盒审计链式起点）→选根治=发布面收敛；06 §2.5 链式适用清单含「配置类」）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 1 项（问③：需要构造路径探测请求——目录扫描、备份后缀枚举）+ **多变体补充规则**（≥3 变体：`.git`/`.svn`/备份压缩包/`.bak` 后缀/`.env`/`.DS_Store`，kinds 表逐条列出）→ 判**中**。问①不命中：「文件放在 Web 根被直接访问」一句话；问②不命中。**与 4.3/5.3 的边界**（章导语边界 1）：那两条是**手法**（穿越/越权去拿文件），本条是**暴露面**（文件本来就摆在可被访问的位置）——修法是「不放上去」而不是「拦住拿」。

**oneLiner（一句话）**：`.git`、备份包、`.env` 这类文件被发布到了 Web 根目录，攻击者敲个地址就能拿走源码、配置和密钥。

**cause（成因与位置）**：发布流程把「家底」搬进了前台——源码仓库目录（`.git`/`.svn`）、备份压缩包（`www.zip`/`backup.sql`）、编辑器残留（`.bak`/`.swp`/`~`）、配置文件（`.env`）被打包进 Web 可访问目录。Web 服务器只看「在不在 Web 根」，不看「该不该被看」。

**where（高发位置）**：`/.git/config`、`/.svn/entries`、`/www.zip`、`/backup.sql`、`/index.php.bak`、`/.DS_Store`、`/.env`、`/composer.lock`、`/package.json`。

**kinds（分类）**（多变体补充规则依据）：

| 类型 | 白话 | 信号 |
|---|---|---|
| 版本库暴露 | 整个 Git/SVN 历史可下载 | `/.git/HEAD` 返回 `ref: refs/heads/...` |
| 备份包暴露 | 打包的源码/数据库可下载 | `/www.zip`、`/backup.sql` 可访问 |
| 编辑器残留 | 编辑器备份文件没清 | `.bak`、`.swp`、`~` 后缀可访问 |
| 配置文件暴露 | 配置随部署落地 | `/.env`、`composer.lock` 可访问 |

**signals（典型特征）**：
- `/.git/config`、`/.svn/entries`、`/www.zip`、`/backup.sql`、`/index.php.bak`、`/.DS_Store`、`/.env`、`/composer.lock`、`/package.json` 可访问。
- `/.git/HEAD` 返回 `ref: refs/heads/master` 类内容（或 `ref: refs/heads/main`，新仓库默认分支）（版本库完整可还原）。

**impact（危害）**：拿到源码即可白盒审计（找注入、密钥、内网地址——**所有攻击链的起点**）；`.git` 可还原完整历史（联动 8.1 硬编码的历史密钥）；`.env` 直接给数据库口令。

**verify（挖掘与验证思路）**：
1. 目录扫描 + 常见备份后缀（`.bak .old .swp .zip .tar.gz .sql ~`）。
2. `.git` 探测：请求 `/.git/HEAD`，看是否返回 `ref: refs/heads/...`（演示样例，自有资产）。
3. 拿到源码后评估可挖什么（密钥/注入点/内部地址）——这就是「链式起点」。

**protect（防护）**：
- **root（根治）**：Web 根目录只放静态资源与入口文件；发布流程禁止把源码/配置打包到 Web 目录；`.git` 目录不可外置到 Web 根。
- **harden（加固）**：禁止访问隐藏文件与备份后缀（服务器配置层面）；定期扫描残留。
- **fallback（兜底）**：监控对备份/隐藏路径的异常访问。

**mistakes（易错点）**：
- 只防「下载接口」不防「直接敲路径」（本条是暴露面不是接口问题）。
- 以为「`.git` 没什么」——它包含全部源码与历史。
- 发布脚本把整个工程目录 rsync 进 Web 根。
- 只删线上文件不清部署包（`/www.zip` 还在）。

## 8.3 报错信息泄露　`危险度 ★★☆☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: error-disclosure` ｜ `chapter: 8` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web` ｜ `hazard: 2` ｜ `aliases: 报错信息泄露, 错误信息泄露, 堆栈泄露, verbose error` ｜ `pinyin: {full: 'bao cuo xin xi xie lou', joined: 'baocuoxinxixielou', initial: 'bcxxl'}` ｜ `related: source-leak, debug-endpoint` ｜ `source: demo` ｜ `templateId: 无（低档 card 形态，不涉及闯关）`

**难度判定**：三问法命中 0（三问均不中：前置 0——「报错把内部细节说出来」一句话；无协议机制；触发一次报错即见堆栈，无需构造载荷）→ **低**。与 06 §3.3 锚定示例「报错泄露=低」一致。

**oneLiner（一句话）**：生产环境的报错页把堆栈、SQL 语句、绝对路径、版本号摊给访客看——报错是给开发者排障的，不是给用户看的。

**cause（成因与位置）**：debug 模式没关（`DEBUG=True`、`app.debug=true`），或错误处理把内部异常详情直接写进响应。**「为什么报错会泄密」**：报错信息是给开发者排障的「调试说明书」，里面自然带着内部细节——生产环境等于把说明书摊在了每个访客面前。**与注入类主题报错回显的边界**（章导语边界 2）：注入类的报错是**信号面**（借报错证明注入存在、带出数据），本条是**信息本身的泄露**——报错是货物不是工具。

**where（高发位置）**：未关 debug 的生产环境、异常处理中间件、API 错误响应体、HTTP 500 页面。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 堆栈泄露 | 异常调用栈直接返回 | 响应含框架类名、行号 |
| SQL/查询泄露 | 报错带出 SQL | 响应含 SQL 语句片段 |
| 路径/版本泄露 | 绝对路径、版本号可见 | 响应含服务器路径、框架版本 |

**signals（典型特征）**：堆栈信息、SQL 语句、绝对路径、框架与版本号、内部 IP、依赖版本出现在响应里。

**impact（危害）**：为后续攻击供料——绝对路径帮 4.3/5.3 定位文件、SQL 片段帮注入类理解查询结构、版本号帮找已知缺陷（联动组件主题）；单独看是低危，**是攻击链的起点**。

**verify（挖掘与验证思路）**：
1. 触发一次报错（传畸形参数、超长输入、类型错误），看响应体（演示样例，自有资产）。
2. 分辨「用户友好的错误页」与「调试页」——后者带堆栈/路径/SQL。
3. 记录泄露的版本号/路径，评估为后续攻击供了什么料。

**protect（防护）**：
- **root（根治）**：生产环境统一错误页；关闭 debug 模式（`DEBUG=False`、`app.debug=false`）。
- **harden（加固）**：错误码与内部细节分离（用户看错误码，细节只落日志）；日志只落服务端。
- **fallback（兜底）**：线上异常监控（错误率突增告警）。

**mistakes（易错点）**：
- 以为「有错误页就算处理了」——错误页里带着堆栈等于没处理。
- 只关了 Web 框架 debug，没关 ORM/数据库的详细报错。
- 把「日志只落服务端」理解成「日志可以不脱敏」（联动 8.9）。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：某 API 传入畸形参数后返回 HTTP 500，响应体含完整 Java 堆栈与服务器绝对路径。
问：这暴露了什么？
- A. 报错信息泄露——调试细节摊给了访客 → ✔ 正确。解释：堆栈和绝对路径是给开发者排障的，不该出现在生产响应里。
- B. SQL 注入 → ✘ 错误。没看到注入构造与查询结构被改写。
- C. 这是拒绝服务 → ✘ 错误。服务返回了错误页，不是被打瘫。
- D. 这是版本泄露的全部 → ✘ 错误。版本号只是泄露面之一，堆栈/路径/SQL 都算。

*题 2 · 怎么防（protect）*｜材料（演示样例）：四种改法：① 生产统一错误页 + 关 debug，细节只落日志；② 把堆栈翻译成英文；③ 报错页加公司 logo；④ 加 WAF。
问：哪个是根治？
- A. ① 统一错误页 + 关 debug + 细节落日志 → ✔ 正确。解释：用户看错误码，细节只进服务端日志——泄露面收敛到内部。
- B. ② 翻译成英文 → ✘ 错误。换了语言，细节还在。
- C. ③ 加 logo → ✘ 错误。美化不是收敛。
- D. ④ 加 WAF → ✘ 错误。WAF 不管响应内容。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发说「日志里有完整堆栈就够了，报错页也可以带一点方便调试」。
问：为什么不行？
- A. 报错页是对外的——细节进日志可以，进响应就是泄露 → ✔ 正确。解释：对外/对内要分清，方便调试不能靠把调试信息发给用户。
- B. 日志里也不该有堆栈 → ✘ 错误。日志是内部的，堆栈进日志是对的。
- C. 只要加 HTTPS 就行 → ✘ 错误。与传输无关。
- D. 只要错误码够长就行 → ✘ 错误。错误码是掩护，不是根治。

## 8.4 目录列举与文件元数据　`危险度 ★★☆☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: directory-listing` ｜ `chapter: 8` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web` ｜ `hazard: 2` ｜ `aliases: 目录列举, 目录列表, EXIF 泄露, 文件元数据泄露` ｜ `pinyin: {full: 'mu lu lie ju yu yuan shu ju', joined: 'mululiejiyuyuanshuju', initial: 'mlljyysj'}` ｜ `related: source-leak, forced-browsing` ｜ `source: demo` ｜ `templateId: 无（低档 card 形态，不涉及闯关）`

**难度判定**：三问法命中 0（三问均不中：访问目录/看文件属性即见，无需构造载荷）→ **低**。与 06 §3.3 锚定示例「目录列举=低」一致。

**oneLiner（一句话）**：访问目录返回文件列表、图片 EXIF 带着 GPS、文档属性写着内部用户名——系统把「有什么、在哪」直接念给了访客。

**cause（成因与位置）**：Web 服务器的目录列举（`autoindex`）没关；上传的图片/文档没清理元数据。**「为什么目录列举省了攻击者一半功夫」**：攻击面发现本来靠「猜」（字典爆破、路径枚举），目录列表把「猜」变成了「读清单」——文件名、备份包、隐藏目录一字排开。

**where（高发位置）**：开放 `autoindex` 的静态目录、上传目录、图片 EXIF（GPS/设备）、文档属性（用户名/路径）。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 目录列举 | 访问目录返回文件清单 | 目录 URL 显示文件列表页 |
| EXIF 泄露 | 图片元数据带隐私 | GPS 坐标、设备型号、拍摄时间 |
| 文档属性泄露 | 文档内嵌内部信息 | 作者名、内部路径、修订历史 |

**signals（典型特征）**：访问目录返回文件列表；图片 EXIF 含 GPS 与设备信息；文档属性含内部用户名与路径。

**impact（危害）**：文件名/路径清单直接喂给 8.2/8.6（找备份、找调试端点）；GPS 泄露住址与行动轨迹；文档属性泄露内部用户名（联动枚举）。

**verify（挖掘与验证思路）**：
1. 访问静态目录（去掉文件名只留路径），看是否返回列表页（演示样例，自有资产）。
2. 下载图片看 EXIF（位置/设备）；看文档属性（作者/路径/修订）。
3. 清点暴露的文件名能为后续攻击供什么料。

**protect（防护）**：
- **root（根治）**：关闭 `autoindex`（Nginx `autoindex off`）；上传图片**重编码**去 EXIF；文档导出前**清理元数据**。
- **harden（加固）**：目录放默认页（index.html）而非列表；敏感目录不放静态服务器。
- **fallback（兜底）**：定期扫描目录列举暴露。

**mistakes（易错点）**：
- 以为「目录里没敏感文件就没事」——文件名清单本身就是情报。
- 只清 EXIF 不清文档属性（Word/PDF 的作者、路径同算）。
- 混淆「目录列举」与「强制浏览」（4.4）：前者是配置暴露清单，后者是端点缺鉴权。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：访问 `/uploads/` 返回一个文件列表页，列出全部上传文件名。
问：这暴露了什么？
- A. 目录列举——把文件清单念给了访客 → ✔ 正确。解释：攻击面发现从「猜」变「读清单」，省一半功夫。
- B. 这是路径穿越 → ✘ 错误。没人走出目录，是清单被列出来了。
- C. 这是任意文件读取 → ✘ 错误。还没读到文件内容，只是看到名字。
- D. 这是 XSS → ✘ 错误。没有脚本执行。

*题 2 · 怎么防（protect）*｜材料（演示样例）：四种改法：① 关 autoindex + 图片重编码去 EXIF + 文档清元数据；② 把目录路径改长；③ 文件名加密；④ 加 WAF。
问：哪个是根治？
- A. ① 关列表 + 清元数据 → ✔ 正确。解释：不列清单、不留元数据，两个泄露面都收敛。
- B. ② 路径改长 → ✘ 错误。仍是隐晦式安全，可被扫到。
- C. ③ 文件名加密 → ✘ 错误。防了名单没防 EXIF/文档属性。
- D. ④ 加 WAF → ✘ 错误。WAF 不管响应列表。

*题 3 · 易错点（mistake）*｜材料（演示样例）：开发说「图片压缩过了，EXIF 一定没了」。
问：为什么还要验证？
- A. 压缩不一定重编码，看一步 EXIF 才算数；文档属性也要单独清 → ✔ 正确。解释：处理方式不等于结果，验证处理后的产物才算。
- B. 压缩一定会去 EXIF → ✘ 错误。保留元数据的压缩方式很多。
- C. 加 HTTPS 就行 → ✘ 错误。与传输无关。
- D. 只要目录放深一点 → ✘ 错误。路径深度不解决列举。

## 8.5 默认配置与默认口令　`危险度 ★★★★★`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: default-credentials` ｜ `chapter: 8` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web, 系统` ｜ `hazard: 5` ｜ `aliases: 默认口令, 默认密码, 出厂口令, 默认配置风险` ｜ `pinyin: {full: 'mo ren pei zhi yu mo ren kou ling', joined: 'morenpeizhiyumorenkouling', initial: 'mrpzmrkl'}` ｜ `related: debug-endpoint, hardcoded-secret` ｜ `source: demo` ｜ `templateId: 无（低档 card 形态，不涉及闯关）`

**难度判定**：三问法命中 0（三问均不中：试一组出厂口令即发现，属配置问题不属机制问题）→ **低**。与 06 §3.3 锚定示例「默认口令=低」一致。**危险度≠难度的活教材**：★5 满星（拿到就是管理权限）但学习门槛低——一个例子讲明白。

**oneLiner（一句话）**：中间件管理台、数据库、设备出厂口令没改，或服务压根没开认证——等于把管理权限写在了说明书上，说明书人人可查。

**cause（成因与位置）**：装完即用、没人改默认口令；数据库/缓存直接裸奔（无认证、端口对外）。**「为什么默认口令能直接进」**：出厂口令写在产品手册里、网上一搜就有——等于所有同款设备共享一把公开的钥匙，「装完没改」就是「没设锁」。

**where（高发位置）**：中间件管理台（Tomcat Manager、WebLogic Console、Jenkins）默认口令；数据库/缓存未授权（Redis 6379、MongoDB 27017、Elasticsearch 9200、Memcached）；设备出厂口令（摄像头、路由器、工控设备）。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 默认口令 | 出厂账号密码没改 | admin/admin 类组合可登录 |
| 未授权访问 | 服务压根没开认证 | Redis/MongoDB/ES 端口直连即进 |
| 默认配置 | 危险默认值没关 | 默认管理端口对外、默认目录可写 |

**signals（典型特征）**：中间件管理台默认口令可登录；数据库/缓存端口未授权可直连；设备出厂口令可登录。

**impact（危害）**：管理台失守（部署/配置/代码执行）；数据库全量数据失守（联动 8.2 之后的任意读取）；设备被控（摄像头、工控）。

**verify（挖掘与验证思路）**：
1. 资产清点管理端口（6379/27017/9200/8080 等），测试未授权直连与默认口令（演示样例，自有资产）。
2. 查产品手册/公开默认口令列表，逐台核对是否改过。
3. 检查服务认证开关（Redis `requirepass`、MongoDB auth 等）。

**protect（防护）**：
- **root（根治）**：安装即改默认口令；管理端口不对外（绑定内网/跳板机）。
- **harden（加固）**：开启认证与 TLS；定期基线核查（扫默认口令/未授权端口）。
- **fallback（兜底）**：弱口令/未授权登录告警。

**mistakes（易错点）**：
- 以为「端口没公布就没人找」（全网扫描常态化，联动 4.4 隐晦式安全教训）。
- 只改 Web 管理台不查数据库/缓存/设备。
- 以为「内网就不用认证」（内网失陷即全裸）。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：某 Redis 端口 6379 对公网开放且未设 `requirepass`，直连即可 `KEYS *`。
问：这暴露了什么？
- A. 默认配置与未授权访问——服务没开认证 → ✔ 正确。解释：裸奔的服务等于把数据放在门口。
- B. 这是弱口令 → ✘ 错误。连口令都没有，是未授权。
- C. 这是信息泄露 → ✘ 错误。这是权限失守，不只是信息。
- D. 这是注入 → ✘ 错误。没有数据被当指令。

*题 2 · 怎么防（protect）*｜材料（演示样例）：四种改法：① 改默认口令 + 端口绑内网 + 开认证；② 端口改非标准号；③ 把服务名藏起来；④ 加 WAF。
问：哪个是根治？
- A. ① 改口令 + 收网络 + 开认证 → ✔ 正确。解释：锁、门、钥匙三样都到位。
- B. ② 改端口号 → ✘ 错误。扫描会发现，仍是隐晦式安全。
- C. ③ 藏服务名 → ✘ 错误。指纹识别照样认出来。
- D. ④ 加 WAF → ✘ 错误。WAF 不管未授权端口。

*题 3 · 易错点（mistake）*｜材料（演示样例）：运维说「设备在内网，出厂口令不用改」。
问：为什么不行？
- A. 内网失陷即全裸，且设备口令手册公开可查——纵深防御要求内外一致 → ✔ 正确。解释：信任边界会破，口令是最后一道。
- B. 内网绝对安全 → ✘ 错误。内网横向移动是常规攻击路径。
- C. 改口令影响自动化脚本 → ✘ 错误。脚本同步更新口令即可。
- D. 只要监控端口就行 → ✘ 错误。监控不拦访问。

**terms / relatedTerms**｜terms: `default-credentials`（本条新增）、`password-policy`（复用，更早主题）；relatedTerms: `password-policy`、`debug-endpoint`（本章后条）

- **harden（加固）**：禁用危险端点（Spring Boot `management.endpoints.web.exposure.include` 白名单，只开需要的）；接口文档不进生产。

## 8.7 缓存与 CDN 配置缺陷　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: cache-cdn-misconfig` ｜ `chapter: 8` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web` ｜ `hazard: 4` ｜ `aliases: 缓存投毒, 缓存欺骗, CDN 回源绕过, Web Cache Poisoning` ｜ `pinyin: {full: 'huan cun yu cdn pei zhi que xian', joined: 'huancunycdnpeizhiquexian', initial: 'hcycpzqx'}` ｜ `related: xss, cors-misconfig, error-disclosure` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=缓存键边界→试可达=未入键的头注入→判影响=污染共享缓存害所有用户→选根治=缓存键完备+不缓存私有响应；06 §2.5 链式适用清单含「配置类」）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 2 项（问②：缓存键机制——哪些输入参与缓存身份判定，要理解一个机制；问③：构造带未入键 Header 的投毒请求验证）→ 判**中**。与 06 §3.3 锚定示例「缓存定中」一致。

**oneLiner（一句话）**：缓存键没包含所有影响响应的输入时，攻击者注入一次恶意响应就被缓存下来，**后面的每个用户拿到的都是它**。

**cause（成因与位置）**：缓存按「缓存键」（通常只有 URL/部分头）判断「是不是同一份响应」；如果某些输入（`X-Forwarded-Host` 等）影响了响应内容却**没进缓存键**，攻击者的恶意响应就会被当成「正常响应」存进公共缓存。**「为什么投毒影响所有人」**：缓存是共享的一份——一个人触发的坏响应被存下来，后面所有人拿到的都是它。**主类比：像在公共饮水机里投药——第一个接水的人没事，后面全中招。**

**where（高发位置）**：未纳入缓存键的 Header（`X-Forwarded-Host`、`X-Forwarded-Scheme`）；伪造静态后缀让 CDN 缓存隐私页（`/account/profile.css`）；源站 IP 直连绕过 CDN/WAF。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 缓存投毒 | 坏响应被缓存给所有人 | 一次构造后所有访客拿到恶意响应 |
| 缓存欺骗 | 隐私页被 CDN 当静态缓存 | `/account/profile.css` 被缓存公开 |
| 回源绕过 | 直连源站绕过防护 | 源站 IP 直接可达（绕过 WAF） |

**signals（典型特征）**：
- 响应里出现攻击者注入的内容（如链接指向恶意域名），且**多个用户**都拿到。
- 改 `X-Forwarded-Host` 后响应变化，且该响应被缓存（第二次不带该头也拿到注入内容）。
- `/account/profile.css` 这类含隐私的页面被 CDN 缓存。
- 源站 IP 可直接访问（绕过 CDN/WAF）。

**impact（危害）**：一次投毒影响所有后续用户（规模化 XSS——联动客户端攻击主题）；隐私页被公开缓存（用户资料泄露）；绕过 WAF 的防护。

**verify（挖掘与验证思路）**：
1. 找未入缓存键的输入（对每个影响响应的 Header 做「加头→响应变→不带头→仍变」的双请求验证，演示样例，自有资产）。
2. 测缓存欺骗：对含隐私的页面加静态后缀，看是否被缓存。
3. 测回源：解析源站 IP 直接访问，看是否绕过 CDN。

**protect（防护）**：
- **root（根治）**：缓存键包含**所有影响响应的输入**；不缓存含用户数据的响应（`Cache-Control: private, no-store`）。
- **harden（加固）**：源站只允许 CDN 回源 IP；校验 Host。
- **fallback（兜底）**：缓存内容异常监测；定期清理可疑缓存。

**mistakes（易错点）**：
- 缓存键只看 URL 不看影响响应的 Header（投毒入口）。
- 把含用户数据的页面当静态缓存（隐私页被公开）。
- 以为「有 CDN 就安全了」（回源绕过直接到源站）。

**演示样例材料**（language: plaintext）：


## 8.8 Host 头攻击　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: host-header-attack` ｜ `chapter: 8` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web` ｜ `hazard: 4` ｜ `aliases: Host 头攻击, Host 头注入, Host Header Attack, X-Forwarded-Host 注入` ｜ `pinyin: {full: 'host tou gong ji', joined: 'hosttougongji', initial: 'htgj'}` ｜ `related: reset-token, cache-poisoning, open-redirect` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=Host 头信任点→试可达=篡改 Host→判影响=链接劫持/令牌泄露→选根治=固定域名+白名单；06 §2.5 链式适用清单含「配置类」）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 2 项（问②：信任边界机制——应用把请求自带的 Host 当自己的域名，要理解一个机制；问③：改 Host 头构造请求验证）→ 判**中**。与 06 §3.3 锚定示例「Host 头定中」一致。

**oneLiner（一句话）**：应用用请求里的 `Host` 头拼链接（密码重置、邮件、跳转）时，攻击者篡改它就能把重置链接指向恶意域名、窃取令牌。

**cause（成因与位置）**：应用生成链接（密码重置、邮件、跳转）时用请求自带的 `Host` 头当域名——但 `Host` 头是**客户端请求带来的、攻击者可控**。**「为什么改 Host 能骗到人」**：应用以为「Host 头 = 自己的域名」，实际它是信封上的回邮地址——寄信人可以随便写。重置链接的域名一变，受害者点开链接时令牌就发到了攻击者手里。

**where（高发位置）**：密码重置邮件链接、通知邮件里的链接、跳转目标、缓存键（联动 8.7）、SSR 校验。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 重置链接劫持 | 邮件链接域名被改 | 改 Host 后重置邮件链接指向恶意域 |
| 缓存投毒联动 | Host 进缓存键面 | X-Forwarded-Host 影响缓存（联动 8.7） |
| 跳转劫持 | 跳转目标被改 | 跳转域名跟着 Host 变 |

**signals（典型特征）**：
- 改 `Host: evil.com` 后，密码重置邮件的链接域名变了。
- `X-Forwarded-Host` 同样生效（反代信任转发头）。

**impact（危害）**：重置令牌被窃（联动认证与会话主题 3.7 密码重置——令牌泄露即账号接管）；用户被导向恶意域名（钓鱼）；配合缓存投毒放大。

**verify（挖掘与验证思路）**：
1. 抓密码重置/通知邮件流程，改 `Host`/`X-Forwarded-Host` 后触发邮件，看链接域名（演示样例，自有资产）。
2. 看跳转目标是否跟着 Host 变。
3. 联动 8.7：Host 是否参与缓存键。

**protect（防护）**：
- **root（根治）**：用**配置中的固定域名**生成链接（不读 Host 头）；校验 `Host` 白名单。
- **harden（加固）**：`X-Forwarded-Host` 只在可信代理后使用（代理覆盖掉客户端值）。
- **fallback（兜底）**：邮件链接域名异常告警。

**mistakes（易错点）**：
- 以为「Host 头是服务器自己的」（它是请求带来的）。
- 只校验 `Host` 不校验 `X-Forwarded-Host`（反代后两者都可被带入）。
- 修了密码重置没修通知邮件/跳转（同一拼链接代码处处复用）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```

  发邮件给用户（用 Host 头拼链接域名）
```

## 8.9 日志与监控系统泄露　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: log-monitoring-leak` ｜ `chapter: 8` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: 系统, Web` ｜ `hazard: 4` ｜ `aliases: 日志泄露, 监控系统泄露, 日志脱敏缺失, Kibana 未授权` ｜ `pinyin: {full: 'ri zhi yu jian kong xi tong xie lou', joined: 'rizhiyujiankongxitongxielou', initial: 'rzyjkxtxl'}` ｜ `related: debug-endpoint, error-disclosure, info-leak` ｜ `source: demo` ｜ `templateId: 不挂（双面拼盘：监控台暴露面 + 日志内容脱敏，两类问题无单一攻击骨架，不硬凑；第二期若做闯关按「两面分别试」形态设计）`｜ `stages: []`（第二期补）

**难度判定**：三问法命中 1 项（问①：日志脱敏、监控鉴权、网络隔离等概念组合）+ **多变体补充规则**（≥3 变体：Kibana/Grafana/Prometheus/RabbitMQ 管理台暴露 + 日志含明文密码/Token/身份证号多类内容）→ 判**中**。

**oneLiner（一句话）**：监控系统未授权、日志里躺着明文密码与身份证号时，日志这个「记事本」成了攻击者的情报库。

**cause（成因与位置）**：两个面叠加：① 监控/管理系统（Kibana、Grafana、Prometheus、RabbitMQ）未鉴权或暴露公网；② 日志记录时未脱敏（明文密码、Token、身份证号、银行卡号被顺手记进日志）。**「为什么日志会泄密」**：日志为排障记录「一切细节」——密码、Token 被顺手记了进去，而日志系统又常常裸奔；记事本锁在抽屉里没事，放在桌上就是情报库。

**where（高发位置）**：Kibana/Grafana/Prometheus/RabbitMQ 管理台；应用日志（登录日志、请求日志、错误日志）；审计日志。

**kinds（分类）**（多变体补充规则依据）：

| 类型 | 白话 | 信号 |
|---|---|---|
| 监控台暴露 | 管理台未授权/公网 | Kibana/Grafana 可匿名访问 |
| 日志明文 | 敏感数据没脱敏 | 日志含明文密码、Token、身份证号 |
| 日志权限过宽 | 谁都能看日志 | 日志目录可读、日志接口无鉴权 |

**signals（典型特征）**：Kibana / Grafana / Prometheus / RabbitMQ 管理台未授权；日志中含有明文密码、Token、身份证号。

**impact（危害）**：监控台失守（看到全站流量、配置、内网拓扑）；日志里的明文密码/Token 直接可用（凭证泄露）；身份证/银行卡泄露（合规风险）。

**verify（挖掘与验证思路）**：
1. 探测监控系统端口/路径是否需鉴权（演示样例，自有资产）。
2. 检查日志内容：搜 `password`、`token`、身份证/银行卡模式。
3. 评估泄露内容可直接利用的程度（凭证可登录？）。

**protect（防护）**：
- **root（根治）**：监控系统鉴权 + 网络隔离（不暴露公网）；**日志脱敏**（手机号、身份证、银行卡、密码、Token）。
- **harden（加固）**：日志访问审计；日志最小权限。
- **fallback（兜底）**：日志敏感信息扫描告警。

**mistakes（易错点）**：
- 只防应用不防监控系统（监控台是另一个入口）。
- 「先记下来再说」——日志里记了明文密码，脱敏忘了做。
- 以为「日志是内部的」（内部系统未授权照样被扫到，联动 8.5「内网也要认证」教训）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```

攻击步骤：
1. 访问 Kibana（未授权）→ 看到全站请求日志
2. 在日志里搜 password 字段（演示样例，日志行）：
     POST /login {"user":"alice","password":"..."}

逻辑链自查（硬标准：日志中字段名与请求原文逐字符对上，密码值逐字符一致）：
输入（访问未授权监控台 + 检索日志）

逐字符核对：日志中 password 字段与登录请求原文的字段名逐字符一致 ✔
```
