## 章导语

**共同本质**：**代码没有 bug，但业务规则可以被「合法地」绕过。**前面六个主题的洞在技术机制里（解析、渲染、身份、权限、文件、请求），本主题的洞在**业务设计里**——流程少了一道检查、规则少了一次强制、操作少了原子与去重。这类漏洞自动化工具测不出来，最考验对业务的理解。

**与前六个主题的衔接**：注入类把数据变成指令（发生在服务器解析环节）；客户端攻击借浏览器执行内容（发生在受害者浏览器）；认证与会话攻击**身份证明**；访问控制与授权攻击**权限边界**；文件与服务端资源攻击**文件出入口**；数据解析主题让服务端**替攻击者干活**（发请求/解析数据结构）；本主题攻击的是**流程与规则的缺口**——身份是真的、权限够的、数据格式也对，但「这件事不该这么办成」。

**三处易混边界（本主题最大难点，逐条划清）**：
1. **7.3 业务竞态 vs 文件与服务端资源主题 5.6 临时文件竞争条件**：同属「先查后改」的时间窗机制家族，场景与修法不同——5.6 是**文件系统时序**（检查与使用之间文件被替换，根治是原子 rename + 私有临时目录），7.3 是**业务流程时序**（检查余额与扣款之间插入另一个请求，根治是行锁/原子 SQL/幂等）。机制讲过（5.6），场景新（本章）。
2. **7.2 业务流程绕过 vs 访问控制与授权主题 4.8 授权绕过技巧清单**：4.8 是**技术性绕过**（换方法/换路径/换身份载体，绕过鉴权的匹配规则）；7.2 是**逻辑绕过**（流程本身没约束合法迁移，跳步直达终态）——一个是「敲门姿势变了」，一个是「门与门之间没关」。
3. **7.1 参数篡改 vs 访问控制与授权主题 4.1/4.2 越权**：4.x 是**权限边界**（这东西是不是你的/你有没有资格用这功能）；7.1 是**业务规则**（服务端信了客户端上报的数值——钱算错了，不是权限错了）。

**通用挖掘方法（工具书口径）**：① 画出完整业务流程图（下单→支付→发货→退款）；② 对每一步问三个问题——**能不能跳过？能不能重复？能不能篡改参数？**；③ 关注「钱、权、量、状态」四类字段；④ 关注并发（同时发两个请求）。

**本主题的三条底线**（8 条都可对号入座）：
1. **金额与规则服务端算**：价格、折扣、运费、券规则由服务端按商品与规则计算，客户端只传标识（商品 ID、券 ID）。
2. **流程状态服务端站岗**：状态机约束合法迁移，关键步骤的完成状态存服务端，不靠前端参数与「当前请求」自证。
3. **关键操作原子 + 幂等**：检查与更新合并为一步原子操作；重复提交/重放不重复生效。

## 7.1 价格与数量篡改　`危险度 ★★★★★`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: parameter-tampering` ｜ `chapter: 7` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, API` ｜ `hazard: 5` ｜ `aliases: 价格篡改, 数量篡改, 金额篡改, 参数篡改` ｜ `pinyin: {full: 'can shu cuan gai', joined: 'canshucuangai', initial: 'cscg'}` ｜ `related: payment-logic, reward-abuse, permission-model` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=客户端上报数值的信任边界→试可达=篡改金额/数量字段→判影响=低价购买/负数套现→选根治=服务端计算+范围校验；06 §2.5 链式适用清单含「业务逻辑」）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 1 项（问③构造篡改请求验证）+「多个变体要分辨」（0/-1/0.01/科学计数法/超大值/负数数量）→ 按 06 §3.3 中档标准（多变体）判**中**。问①不命中：「服务端信任客户端数值」是一个机制（信任模型半边）；问②不命中：判断它存在只需看到请求里有金额字段，无需协议/状态机。**与 06 锚定的关系**：06 §3.3 锚定已拆分回写——「支付与退款逻辑=高（7.5 承载，状态机+计算信任模型完整口径），价格与数量篡改=中（7.1 承载信任模型半边，多变体补中）」。本条即后者，按中档判。

**oneLiner（一句话）**：服务端信任客户端提交的价格、数量、折扣等字段时，改一个数字就能低价购买，数量改负数还能套现。

**cause（成因与位置）**：下单/结算接口把请求体里的 `price`、`amount`、`total`、`discount`、`freight` 直接采信进订单。**「为什么改个数字就能改结果」**：价格本该是**服务端按商品与规则算出来的结论**，不是**客户端报上来的选项**——把结论的位置让给了客户端，客户端写什么就是什么。出问题的位置：一切「客户端上报数值、服务端直接用」的接口。

**where（高发位置）**：下单/结算请求体（`price`、`amount`、`total`、`discount`、`freight` 字段）、批量改价接口、运费/优惠计算参数。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 价格篡改 | 报低价直接成交 | 改 `price`/`total` 后订单金额异常 |
| 数量篡改 | 数量为负倒扣钱 | `quantity=-1` 总价变负（余额增加） |
| 折扣/运费篡改 | 改折扣率或运费 | `discount`/`freight` 字段可提交 |
| 数值形态绕过 | 换数值写法过校验 | `0.01`、`1e-10`、科学计数法、超大值 |

**signals（典型特征）**：
- 请求体里有 `price`、`amount`、`total`、`discount`、`freight` 字段。
- 改成 `0`、`-1`、`0.01`、超大值、科学计数法 `1e-10` 后订单金额异常。
- 数量改成负数，总价变负（余额增加）。
- 前端显示与后端计算不一致（只改前端不算，要改请求）。

**impact（危害）**：低价/零元购；负数数量套现（余额增加）；批量薅差价；财务对账失衡。

**verify（挖掘与验证思路）**：
1. 抓下单/结算请求，列出全部数值字段（钱、量、折扣、运费）。
2. 逐字段改值（0/负数/极小值/科学计数法/超大值）重放，核对订单金额（演示样例，测试环境）。
3. 注意只改请求不改前端（改前端不算）；核对前端显示与后端计算是否一致。
4. 关注数量为负时总价方向（加钱还是扣钱）。

**protect（防护）**：
- **root（根治）**：价格、折扣、运费**全部由服务端根据商品与规则计算**，客户端只传商品 ID 与数量；数量做范围校验（正整数、上限）。
- **harden（加固）**：金额用整数分存储（不走浮点，呼应数据解析主题的精度教训）；最终金额二次校验；订单快照（下单时价格定格）。
- **fallback（兜底）**：异常金额告警；对账脚本核差。

**mistakes（易错点）**：
- 只校验前端不校验服务端（抓包改请求即绕）。
- 只测 `price` 不测数量/折扣/运费（四类字段都算钱）。
- 数量没做正整数与上限校验（负数=套现）。
- 金额走浮点（精度丢失，联动数据解析主题 6.5 精度变体）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
场景（演示样例，站点 example.com 的下单接口）：
正常请求（演示样例）：
  POST /api/order

## 7.2 流程绕过（状态机缺陷）　`危险度 ★★★★★`　`本站难度：高`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: workflow-bypass` ｜ `chapter: 7` ｜ `difficulty: advanced` ｜ `format: interactive` ｜ `scene: Web, API` ｜ `hazard: 5` ｜ `aliases: 流程绕过, 状态机缺陷, 步骤跳过, 状态机绕过` ｜ `pinyin: {full: 'liu cheng rao guo', joined: 'liuchengraoguo', initial: 'lcrg'}` ｜ `related: approval-bypass, payment-logic, authz-bypass-checklist` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=状态机迁移边界→试可达=跳步/伪造状态参数→判影响=直达终态→选根治=服务端状态机约束合法迁移；06 §2.5 链式适用清单含「业务逻辑」）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 3 项——问①前置>2（状态机、合法迁移、前置状态三个新概念）；问②要理解**状态机**机制才能判断它存在（正中高档标准第三支「依赖协议/状态机/权限模型」）；问③要构造跳步/改状态请求验证 → **高**。与 06 §3.2（业务逻辑章=高，需理解钱/权/状态机）口径一致。

**oneLiner（一句话）**：服务端只按「当前请求」处理、不校验前置状态时，必要步骤（验证、支付、审核）可被跳过，直接到达终态。

**cause（成因与位置）**：业务流程有先后顺序（先验证、再支付、后完成），但服务端每接一个请求只看「这个请求本身合不合法」，不看「上一步做完没有」。**「为什么能跳步」**：流程顺序只画在流程图和前端页面上，服务端没站岗——「支付成功回调」接口不问订单付没付、「发布」接口不问审核过没过，谁来调都照办。**状态机**（复用机制词 `state-machine`：系统允许的状态与合法迁移的清单）的缺口就是：合法迁移没被写进代码，只写在纸上。

**where（高发位置）**：支付回调接口、实名/审核后置步骤、订单状态参数（`status=`）、步骤参数（`step=`）、发布/提现等终态操作。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 步骤跳过 | 不做前置步骤直接到终态 | 直接请求「支付成功回调」置已支付 |
| 状态参数篡改 | 改状态字段直达终态 | `status=paid` 直接提交 |
| 步骤回退 | 回到已过步骤覆盖确认 | `step=3` 重新提交覆盖已确认信息 |
| 前置条件缺失 | 关键前置没查 | 跳过实名直接下单/提现 |

**signals（典型特征）**：
- 直接请求「支付成功回调」接口即可把订单置为已支付。
- 跳过实名认证直接下单/提现；跳过审核直接发布内容。
- 修改订单状态参数（`status=paid`）生效。
- 步骤参数可回退（`step=3` 重新提交覆盖已确认信息）。

**impact（危害）**：未支付拿货（直接经济损失）；未实名提现（合规风险）；未审核内容上线；流程整体失控。

**verify（挖掘与验证思路）**：
1. 画出完整业务流程图，列出每个状态与合法迁移。
2. 对每步问「能不能跳过」：直接请求后一步接口，看前置状态是否被校验。
3. 改状态/步骤参数（`status`、`step`）重放，看是否直达终态。
4. 测回退：回到上一步改已确认信息，看是否覆盖生效。

**protect（防护）**：
- **root（根治）**：服务端维护**状态机**（`state-machine` 本条新增），明确合法状态迁移（`待支付 → 已支付 → 已发货`），**非法迁移一律拒绝**；关键步骤完成状态存服务端（不靠前端参数）。
- **harden（加固）**：支付以**支付网关异步通知 + 主动查询**为准并校验签名（与 7.5 联动）；步骤回退需显式授权。
- **fallback（兜底）**：状态迁移全量留痕；异常迁移告警。

**mistakes（易错点）**：
- 只在前端按顺序展示步骤（服务端没站岗）。
- 只校验「当前请求合法性」不校验「前置状态」。
- 支付结果信回调不主动查询（与 7.5 联动）。
- 状态参数由客户端提交（`status=paid` 直达终态）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```

合法流程：待支付 →（支付）→ 已支付 →（发货）→ 已完成

  POST /api/order/complete  { "orderId": 1001, "status": "done" }
  → 按 status 参数置订单状态（不查当前状态是否允许该迁移）

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「每一步之前，服务端查不查前置状态」。流程顺序必须**由服务端说了算**——状态机就是那张「允许怎么走」的清单，清单没写进代码，流程就是敞开的。**技术绕过 vs 逻辑绕过**（与访问控制主题 4.8 的边界）：4.8 是鉴权匹配规则被绕（敲门姿势变了），本条是流程本身没关（门与门之间没关）。

## 7.3 竞态条件（业务面）　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: business-race` ｜ `chapter: 7` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, API` ｜ `hazard: 4` ｜ `aliases: 业务竞态, 并发竞态, 竞争条件（业务面）, 超额提现, 超卖` ｜ `pinyin: {full: 'jing zheng tiao jian', joined: 'jingzhengtiaojian', initial: 'jztj'}` ｜ `related: toctou-race, idempotency-missing, payment-logic` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=「检查→更新」两步间的时间窗→试可达=并发双请求插队→判影响=超额/重复领取/超卖→选根治=原子 SQL/行锁/幂等；与文件主题 5.6 同骨架不同场景）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 1 项（问③构造并发验证）+「多个变体要分辨」（余额/库存/券/额度四面）→ 按「多变体」判**中**。问①不命中：时序窗口机制已由文件与服务端资源主题 5.6 讲过（前置概念计数规则不计）；问②的时序机制同理折价。**与 5.6 的边界**（本主题最大难点之一）：同属「先查后改」时间窗机制家族——5.6 是**文件系统时序**（检查与使用之间文件被替换，根治原子 rename+私有临时目录），本条是**业务流程时序**（检查余额与扣款之间插入另一请求，根治行锁/原子 SQL/幂等）；机制讲过、场景新。

**oneLiner（一句话）**：「检查余额→扣款」两步之间存在时间窗时，并发请求都能通过检查，导致超额提现、重复领券、库存超卖。

**cause（成因与位置）**：先查后改（查余额够不够→扣款）是两步操作，两步之间另一个请求也完成了检查——两个请求都以为钱够，都扣。**「为什么检查过还会超」**：检查和扣款不是一口气做的，中间的空隙里别人也过了检查——和文件主题 TOCTOU 同一个道理，只是「被调包的对象」从文件换成了余额/库存/券状态。高发位置：提现/支付（余额）、抢购（库存）、领券（券状态）、积分（额度）——一切「先查后改」处。

**where（高发位置）**：提现/转账（余额）、下单扣库存、优惠券核销、积分扣减、抽奖次数。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 余额竞态 | 并发提现超额 | 余额 100 并发 10 笔提现成功多笔 |
| 库存竞态 | 并发抢购超卖 | 库存 1 件卖出多件 |
| 券/额度竞态 | 并发重复使用 | 同一券被并发多次核销 |

**signals（典型特征）**：
- 余额 100 元，同时发 10 个提现 100 的请求，成功多个。
- 优惠券可被并发多次使用；库存 1 件卖出多件。

**impact（危害）**：超额提现（直接资金损失）；超卖（履约损失）；券/积分被重复薅；对账混乱。

**verify（挖掘与验证思路）**：
1. 用并发工具（如 Burp 的并发/Turbo Intruder）同一时间点发多个相同请求（演示样例，测试环境）。
2. 观察是否都成功；关注「先查后改」逻辑（余额、库存、额度、券状态）。
3. 对比串行执行（一个个来）与并发执行的结果差异。

**protect（防护）**：
- **root（根治）**：把「检查 + 更新」合并为**一条原子 SQL**（`UPDATE … WHERE balance >= ?`）；或数据库行锁（`SELECT … FOR UPDATE`）/乐观锁（版本号）。
- **harden（加固）**：唯一约束（幂等键，`idempotency` 本章后条）；分布式锁；关键操作幂等。
- **fallback（兜底）**：超卖/超额告警；对账脚本核差。

**mistakes（易错点）**：
- 只在应用层加锁（多实例/多进程下失效）。
- 检查与更新分两条 SQL（中间窗口就是竞态）。
- 以为「并发概率低」不处理（工具一发就是百十个）。
- 用「再查一次」缓解（不原子，同 TOCTOU 教训）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
场景（演示样例，站点 example.com 的提现接口）：
服务端逻辑（演示样例，两步不原子）：
  ① SELECT balance FROM account WHERE uid=1     → 100，检查「够提 100」
  ② UPDATE account SET balance=balance-100 …    → 扣款

攻击步骤（演示样例，并发两请求）：
1. 请求 A 与请求 B 同时到达，都执行 ①：余额都是 100 → 检查都通过
2. 都执行 ②：各扣 100 → 余额 -100，但提现出了 200

逻辑链自查（硬标准：余额数值/请求参数与服务端读取处逐字符对上）：
输入（两个并发提现 100 的请求）
→ 机制（检查与扣款两步之间有时间窗，两请求都通过检查——先查后改不原子）
→ 结果（余额 100 提出 200，超额成立）✔
逐字符核对：提现金额 100 与余额 100 数值逐字符一致（100 vs 100.0 类型差异需核对）✔
           uid=1 与账号标识逐字符一致 ✔
           （若服务端用一条 UPDATE … WHERE balance>=100 原子执行，第 2 步只有一笔成功——修法对照）✔
```

note：材料为演示样例，站点与数值为虚构，非现场运行、非真实系统。修法对照：原子 SQL（第二笔因余额不足被拒）+ 幂等键，窗口不存在。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「检查和更新是不是一口气做的」。两步之间的时间窗就是并发插队的缝隙——**检查的结论只对「检查那一刻」负责**，更新前必须让结论保鲜（原子化）。与 5.6 分工：机制在文件主题讲过（TOCTOU 时间窗），本条练的是业务面的「先查后改」四处（钱/库/券/额）。
- **how（下一步看什么、怎么判断）**：① 找所有「先查后改」逻辑；② 并发工具同时发多请求对比结果；③ 看 SQL 是否原子（`WHERE balance>=?` 形态）；④ 修复按「原子 SQL/行锁/乐观锁 + 幂等键」三件套。

**相关术语网**：`business-race` → 机制家族：`toctou`（复用，更早主题，时间窗概念）｜ 场景区分：文件主题 5.6 `toctou-race`（文件系统时序，根治原子 rename）vs 本条（业务流程时序，根治原子 SQL/锁）｜ 修复联动：`idempotency`（本章后条，重复提交面）｜ 高发面：7.5 支付与退款（金额）、7.4 优惠券（券状态）

## 7.4 优惠券 / 积分 / 邀请滥用　`危险度 ★★★☆☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: reward-abuse` ｜ `chapter: 7` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web` ｜ `hazard: 3` ｜ `aliases: 优惠券滥用, 积分滥用, 邀请滥用, 薅羊毛, 券规则绕过` ｜ `pinyin: {full: 'you hui quan lan yong', joined: 'youhuiquanlanyong', initial: 'yhqly'}` ｜ `related: parameter-tampering, business-race, limit-bypass` ｜ `source: demo` ｜ `templateId: 不挂（规则组合类——逐规则试用、无单一攻击骨架，同访问控制主题 4.8 方法清单先例；第二期按「逐规则试」设计，不硬套四关）`｜ `stages: []`（第二期补）

**难度判定**：三问法命中 1 项（问③构造规则变体验证）+「多个变体要分辨」（邀请自己/批量注册/叠加超限/过期可用/退款退回 6+ 规则变体）→ 按「多变体」判**中**。问①不命中：「规则要强制」是 7.1 已讲的信任模型（服务端算规则）的延伸，一个机制家族；问②不命中。

**oneLiner（一句话）**：券/积分/邀请的规则写了「每人一张」「不可叠加」「过期作废」，但规则没在领用处强制时，批量注册、重复使用、退款回刷都能薅。

**cause（成因与位置）**：营销规则声明在活动页（每人限领一张、券不可叠加、过期作废），但**领用接口没强制**——规则是声明，不是锁。**「为什么券会被薅」**：规则写在页面上给人看，接口没在「发券/核销」那一刻校验（谁领过、用过没有、过没过期、退没退款）——声明与强制是两回事，和 4.7「前端隐藏不算防护」同一教训的业务版。

**where（高发位置）**：领券接口、核销接口、邀请奖励发放、积分扣减、抽奖次数、退款退券逻辑。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 邀请滥用 | 邀请自己拿奖励 | 同设备/同手机号段自邀 |
| 批量注册薅券 | 新人券被批量领 | 短时间大量新号领新人券 |
| 叠加超限 | 不可叠加的券叠用 | 多券同单超出优惠上限 |
| 过期/退款回刷 | 作废券仍可用 | 过期券生效；退款后券退回可重复用 |

**signals（典型特征）**：
- 邀请自己（同设备/同手机号段）拿奖励。
- 批量注册领新人券；券可叠加超限；券与商品不匹配。
- 过期券仍可用；退款后券退回可重复用。

**impact（危害）**：营销成本被薅穿；积分套现；活动失效；财务损失。

**verify（挖掘与验证思路）**：
1. 列出全部营销规则（领取次数、叠加、过期、退款策略）。
2. 对每条规则问「能不能绕过/重复/篡改」：自邀、换号、并发（联动 7.3）、过期券重放、退款后重复用。
3. 关注券状态机（未用→已用→已退）迁移是否被约束（联动 7.2）。

**protect（防护）**：
- **root（根治）**：券规则**服务端计算**；一人一券**唯一约束**；券状态机（`state-machine` 本章前条）与幂等（`idempotency` 本章后条）。
- **harden（加固）**：设备指纹 + 手机号 + 实名多维风控（与 7.6 联动）；退款策略明确（券退回后不可重复用或降额度）。
- **fallback（兜底）**：异常领取告警；营销预算熔断。

**mistakes（易错点）**：
- 规则只展示不强制（接口没校验领取/使用记录）。
- 只防单点不防组合（批量注册+自邀+并发一起上）。
- 退款退券不改状态（退回即可重复用）。
- 风控只绑账号（换号即绕，与 7.6 联动）。

## 7.5 支付与退款逻辑　`危险度 ★★★★★`　`本站难度：高`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: payment-logic` ｜ `chapter: 7` ｜ `difficulty: advanced` ｜ `format: interactive` ｜ `scene: Web, API` ｜ `hazard: 5` ｜ `aliases: 支付逻辑, 退款逻辑, 支付金额篡改, 支付回调伪造, 支付重放` ｜ `pinyin: {full: 'zhi fu tui kuan luo ji', joined: 'zhifutuikuanluoji', initial: 'zftklj'}` ｜ `related: parameter-tampering, workflow-bypass, idempotency-missing` ｜ `source: demo` ｜ `templateId: TPL-CHAIN`（认边界=回调入口的信任边界→试可达=伪造回调/重放/改金额→判影响=伪造支付/重复发货/1 分钱买大额→选根治=验签+金额校验+幂等；06 §2.5 链式适用清单含「业务逻辑」）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 3 项——问①前置>2（回调验签、幂等、对账三个新概念）；问②要理解**业务状态机**（订单状态迁移）与**服务端计算信任模型**（金额以服务端为准）才能判断它存在——**06 §3.3 锚定已拆分回写——「支付与退款逻辑=高」即本条（状态机+计算信任模型完整口径）**；问③要构造伪造/重放回调验证 → **高**。

**oneLiner（一句话）**：支付回调不验签或金额不校验时，一分钱能买大额商品；回调可重放时，一次支付多次发货。

**cause（成因与位置）**：支付完成与否，**权威在支付网关**，服务端只该「收通知→验签→核金额→改状态」。四个环节各有缺口：① 不验签——谁都能 POST 一句「已支付」；② 金额不校验——回调说 1 分就是 1 分；③ 不幂等——同一回调处理多次，重复发货；④ 退款金额客户端可改、可重复退。**「为什么伪造回调能成功」**：服务端把「收到一条支付成功消息」当成了「支付真的成功了」——消息可以伪造，**验签才是「消息来自网关」的证明**；金额要自己核（服务端算的钱为准），不能信消息里说的数。

**where（高发位置）**：支付回调接口（`/pay/notify`）、退款接口、金额单位转换处（分/元）、部分退款逻辑。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 回调伪造 | 假装支付成功 | 回调不验签/验签可绕过 |
| 回调重放 | 一次支付多次发货 | 同一回调多次生效 |
| 金额不核 | 1 分钱买大额 | 回调金额未与订单金额比对 |
| 退款失控 | 退款可改可重复 | 退款金额客户端上报；部分退款超原额 |

**signals（典型特征）**：
- 支付回调不验签/验签可绕过 → 伪造支付成功。
- 回调可重放 → 重复发货。
- 金额以分为单位但回调金额未校验 → 1 分钱买大额商品。
- 退款金额可改、可重复退款；部分退款后总退款额超过原订单。

**impact（危害）**：伪造支付（直接资金损失）；重复发货；1 分钱买大额（薅穿）；重复退款；财务对账失衡。

**verify（挖掘与验证思路）**：
1. 抓支付回调请求，测不带签名/带错签名是否仍被接受。
2. 同一回调重放，看订单/发货状态是否重复推进。
3. 构造金额不一致的回调（演示样例，测试商户），看服务端是否核对订单金额。
4. 退款：改退款金额、重复退款、部分退款累计超原额。

**protect（防护）**：
- **root（根治）**：回调**验签** + **校验订单金额与状态**（金额以服务端订单为准）+ **幂等**（同一流水号只处理一次，`idempotency` 本章后条）。
- **harden（加固）**：主动查询对账（不只信通知）；退款金额服务端计算且不超过可退余额；金额整数分（联动 7.1）。
- **fallback（兜底）**：对账脚本核差；异常支付告警。

**mistakes（易错点）**：
- 只信异步通知不主动查询（通知可伪造/丢失）。
- 验签了但不核金额（签名真的、金额假的照样中招）。
- 回调没做幂等（重复通知=重复发货）。
- 退款金额信任客户端（联动 7.1 同教训）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
场景（演示样例，站点 example.com 的支付回调）：
服务端逻辑（演示样例）：
  POST /pay/notify  { "orderId": 1001, "amount": 1, "status": "paid" }
  → 置订单为已支付（不验签、不核金额、不幂等）

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「钱的结论听谁的」。支付完成与否**只听支付网关的（验签）**，金额多少**只听服务端订单的（比对）**——两个都不信回调自己说的。回调重放面盯幂等（同一流水号只处理一次）。

## 7.6 限购 / 风控绕过　`危险度 ★★☆☆☆`　`本站难度：低`　【形态 A · 知识卡 + 3 题】

**元数据**｜`id: limit-bypass` ｜ `chapter: 7` ｜ `difficulty: beginner` ｜ `format: card` ｜ `scene: Web` ｜ `hazard: 2` ｜ `aliases: 限购绕过, 风控绕过, 限购刷单, 换壳绕过` ｜ `pinyin: {full: 'xian gou rao guo', joined: 'xiangouraoguo', initial: 'xgrg'}` ｜ `related: reward-abuse, idor, business-race` ｜ `source: demo` ｜ `templateId: TPL-AUTHZ`（低档 card 不涉及闯关；若升级交互挂 AUTHZ：认对象=限购绑定的维度→换标识=换账号/IP/设备→证明越权=突破限购→选根治=多维绑定——换标识骨架字面贴合）

**难度判定**：三问法命中 0（三问均不中：前置 0——「绑错维度换维度绕」一句话；无协议机制；换账号即演示、无需构造载荷）→ **低**。

**oneLiner（一句话）**：限购绑在最容易换的东西上（账号、IP、前端上报的设备 ID）时，换一个就是新用户，限购形同虚设。

**cause（成因与位置）**：限购/风控的「身份维度」选错了——按账号限购（换账号）、按 IP（换代理）、信前端 `X-Forwarded-For`（可伪造）、信前端生成的设备 ID（可改）。**「为什么换账号就绕过」**：限购绑在**外壳**上而不是**人**上——账号/IP 都是可以换的外壳，实名、设备指纹、支付账户才是换不动的里子。

**where（高发位置）**：限购接口、抢购资格判断、新人资格判断、风控字段（`X-Forwarded-For`、设备 ID）。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 账号维度 | 换账号即新用户 | 限购按账号计数 |
| IP 维度 | 换代理即新 IP | 限购按 IP，代理池绕过 |
| 前端字段 | 改上报字段即绕 | 信 `X-Forwarded-For`/前端设备 ID |

**signals（典型特征）**：
- 限购按账号，换账号即可；限购按 IP，换代理即可。
- 风控依赖 `X-Forwarded-For`（可伪造）；设备 ID 由前端生成（可改）。

**impact（危害）**：限购被刷（黄牛囤货）；新人福利被薅；风控失效。

**verify（挖掘与验证思路）**：
1. 确认限购/风控绑定了哪些维度（账号/IP/设备/实名/支付账户）。
2. 逐维度替换验证（换账号、换代理、改前端字段）。
3. 检查设备标识由谁生成（前端可改）。

**protect（防护）**：
- **root（根治）**：**多维度绑定**（实名、设备、支付账户、收货地址）；服务端生成设备标识。
- **harden（加固）**：不信任任何客户端上报的风控字段（`X-Forwarded-For` 仅参考）；多维交叉验证。
- **fallback（兜底）**：异常下单模式告警。

**mistakes（易错点）**：
- 限购绑单一维度（换壳即绕）。
- 信前端上报的设备 ID/XFF（抓包可改）。
- 以为「一个账号一个」就够（黄牛就是多账号）。

**quiz（3 题：认出它 / 怎么防 / 易错点）**：

*题 1 · 认出它（identify）*｜材料（演示样例）：某限购活动「每人限 1 台」，换账号再下一单即成功。
问：这说明什么？

- B. 这是竞争条件 → ✘ 错误。没有并发，是换身份重试。
- C. 这是越权 → ✘ 错误。每个账号都是自己下单，不涉及他人数据。

问：哪个是根治？
- A. ① 多维度绑定换不动的「里子」 → ✔ 正确。解释：实名/设备/支付账户换不动，交叉绑定才拦得住换壳。
- B. ② 按 IP → ✘ 错误。代理池即绕。
- C. ③ 前端设备 ID → ✘ 错误。前端字段可改。
- D. ④ 加 WAF → ✘ 错误。WAF 不管业务维度。

问：为什么不行？

- B. 设备 ID 长度不够 → ✘ 错误。长度不是问题，来源才是。
- C. 加密一下就行 → ✘ 错误。加密不改变「客户端可控」。
- D. 加 HTTPS 就行 → ✘ 错误。与传输无关。

## 7.7 越权审批与工作流缺陷　`危险度 ★★★★☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: approval-bypass` ｜ `chapter: 7` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web` ｜ `hazard: 4` ｜ `aliases: 越权审批, 审批流缺陷, 工作流缺陷, 自审自批` ｜ `pinyin: {full: 'yue quan shen pi', joined: 'yuequanshenpi', initial: 'yqsp'}` ｜ `related: workflow-bypass, vertical-escalation, workflow-defect` ｜ `source: demo` ｜ `templateId: TPL-AUTHZ`（认对象=审批节点与发起人关系→换标识=自审/替审/改节点→证明越权=越权审批通过→选根治=职责分离+审批流服务端固定；换标识骨架字面贴合）｜ `stages: []`（第二期补，templateId 预留）

**难度判定**：三问法命中 2 项——问①新概念 2 个（职责分离、审批流固定）；问③构造自审/替审请求验证 → **中**。问②不命中：审批权限模型判断存在只需一次自审请求，无需协议级理解。

**oneLiner（一句话）**：审批人能审批自己的单据、能替他人审批、审批通过后还能改内容时，审批这道「制衡」只画在流程图上，服务端没站岗。

**cause（成因与位置）**：审批的本意是**制衡**（发起人≠审批人、审过即锁定），但服务端没强制：① 不查发起人与审批人是否同一人（自审）；② 审批流节点可被修改（改审批人/跳节点）；③ 审批通过后内容仍可改（先审后改——审的是 A 版，放行的是 B 版）。**「为什么能自己批自己」**：制衡只画在流程图上给人看，服务端没校验「发起人≠审批人」——又是「声明不等于强制」的同款教训（联动 4.7、7.4）。

**where（高发位置）**：审批接口、审批流配置、审批后内容编辑接口、代审批/转审功能。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 自审自批 | 自己批自己的单 | 发起人=审批人仍可通过 |
| 替他人审批 | 冒用审批人身份 | 可替他人点通过 |
| 审批流篡改 | 改节点/改审批人 | 审批流节点参数可提交 |
| 先审后改 | 审过再改内容 | 审批通过后内容仍可编辑 |

**signals（典型特征）**：
- 审批人可审批自己的单据。
- 可修改审批流节点；可替他人审批。
- 审批通过后仍可修改内容（先审后改）。

**impact（危害）**：虚假报销/违规放行；制衡机制失效（审批形同虚设）；合规风险（审批留痕与实际不符）。

**verify（挖掘与验证思路）**：
1. 用同一账号发起并审批自己的单据，看是否被拦。
2. 改审批流节点/审批人参数（演示样例），看是否生效。
3. 审批通过后编辑内容，看是否需重新审批。
4. 测替他人审批（换审批人身份参数）。

**protect（防护）**：
- **root（根治）**：**审批人与发起人强制分离**（服务端校验）；审批流由**服务端固定**（不接受客户端提交的节点）。
- **harden（加固）**：审批后内容**锁定**（修改需重新审批）；所有审批操作留痕。
- **fallback（兜底）**：异常审批模式告警（同人高频自审等）。

**mistakes（易错点）**：
- 只在前端隐藏「自己的单据的审批按钮」（抓包即调）。
- 审批流节点由客户端提交（改节点即绕）。
- 审批后不锁内容（先审后改）。
- 以为「有审批环节」就等于有制衡（强制才算）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```

## 7.8 数据一致性与幂等缺失　`危险度 ★★★☆☆`　`本站难度：中`　【形态 B · 知识卡 + 案例演示 + 指导】

**元数据**｜`id: idempotency-missing` ｜ `chapter: 7` ｜ `difficulty: intermediate` ｜ `format: interactive` ｜ `scene: Web, API` ｜ `hazard: 3` ｜ `aliases: 幂等缺失, 重复提交, 重复扣款, 幂等键缺失` ｜ `pinyin: {full: 'mi deng que shi', joined: 'midengqueshi', initial: 'mdqs'}` ｜ `related: business-race, payment-logic, workflow-bypass` ｜ `source: demo` ｜ `templateId: 不挂（幂等是设计约束而非攻击骨架——「重复触发→重复生效」验证形态单一，第二期按「触发-去重」设计，不硬套四关）`｜ `stages: []`（第二期补）

**难度判定**：三问法命中 1 项（问③构造重复提交验证）+「多个变体要分辨」（表单重复提交/接口重试/消息重复消费三面）→ 按「多变体」判**中**。问①不命中：幂等是一个机制（与 7.3 的原子性同族）；问②不命中。

**oneLiner（一句话）**：同一操作重复到达却重复生效时——重复提交生成多笔订单、接口重试重复扣款、消息重复消费重复发货——缺的是「同一件事只算一次」的幂等约束。

**cause（成因与位置）**：服务端把「每次请求」当成「一件事」——但用户点两次、网络重试一次、消息队列投递两次，都是「同一件事的多份副本」。**「为什么重复提交会重复生效」**：服务端没给「同一件事」发身份证（**幂等键**，`idempotency` 本条新增：同一操作的唯一标识，处理过就不再处理）——同一张票不能剪两次，再递也不剪，缺了剪票口的记性，每张都剪。高发位置：下单表单、支付/扣款接口、消息消费者。

**where（高发位置）**：下单/支付/扣款接口、表单提交、消息队列消费者、回调处理（与 7.5 联动）。

**kinds（分类）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 表单重复提交 | 点两次生成两单 | 重复提交生成多笔订单 |
| 接口重试重复 | 重试导致重复扣款 | 网络重试后重复扣款 |
| 消息重复消费 | 重复消息重复发货 | 消息重复消费导致重复发货 |

**signals（典型特征）**：
- 重复提交表单生成多笔订单。
- 接口重试导致重复扣款；消息重复消费导致重复发货。

**impact（危害）**：重复扣款/重复发货（资金损失）；数据不一致（订单/库存/账目对不上）；用户投诉。

**verify（挖掘与验证思路）**：
1. 同一请求连发两次（演示样例，测试环境），看是否产生两笔效果。
2. 三面都测：表单提交、接口调用、消息消费。
3. 检查幂等键是否存在（`requestId`/流水号）、服务端是否去重。

**protect（防护）**：
- **root（根治）**：**幂等键**（客户端生成 `requestId`，服务端去重，`idempotency` 本条新增）；数据库唯一约束。
- **harden（加固）**：消息消费去重表；关键操作状态机保护（已处理即终态）。
- **fallback（兜底）**：前端防重复提交**只是体验优化**，服务端必须兜底。

**mistakes（易错点）**：
- 只靠前端防重复提交（抓包重放即绕）。
- 幂等键不与业务绑定（换 key 即重复）。
- 只做接口幂等不做消息幂等（队列重复投递照样重复）。
- 以为「低概率」不处理（重试与双击是常态）。

**▶ 案例演示（caseDemo，第一期交付）**

**演示样例材料**（language: plaintext）：

```
场景（演示样例，站点 example.com 的下单接口）：
服务端逻辑（演示样例）：
  POST /api/order  { "productId": 1001, "quantity": 1 }
  → 创建订单（无幂等键，收到几次创建几单）

攻击/触发步骤（演示样例，同请求连发两次）：
1. 请求 A：POST /api/order { "productId": 1001, "quantity": 1 } → 订单 1
2. 请求 B（同参数再发）：POST /api/order { "productId": 1001, "quantity": 1 } → 订单 2
   → 两笔订单（重复生效）；用户双击/网络重试即触发

逻辑链自查（硬标准：请求参数与服务端读取处逐字符对上，两次请求参数完全一致）：
输入（同一操作的两个副本请求，参数逐字符相同）
→ 机制（服务端无幂等键去重，每次请求都当新事件处理）
→ 结果（重复生成订单/重复扣款）✔
逐字符核对：两次请求的 productId/quantity 逐字符一致（副本判定依据）✔
           请求字段名与服务端读取的键名逐字符一致 ✔
           （若服务端按 requestId 去重/唯一约束，第 2 步被拒——修法对照）✔
```

note：材料为演示样例，站点与订单为虚构，非现场运行、非真实系统。修法对照：幂等键（`requestId` 去重）+ 数据库唯一约束，第 2 步不产生新订单。

**▶ 指导模式（guide，静态文字，默认展开可折叠）**

- **why（为什么盯这里）**：盯「同一件事，服务端认几次」。用户双击、网络重试、消息重投都是**同一件事的多份副本**——服务端必须认出「这是同一件事」（幂等键）并只办一次。**同一张票不能剪两次，再递也不剪**——缺的就是剪票口的记性。
- **how（下一步看什么、怎么判断）**：① 三面测重复（表单/接口/消息）；② 查幂等键与唯一约束；③ 看前端防重是否被当成唯一防线；④ 修复按「幂等键+唯一约束+消费去重表」三件套。

〔本条术语锚点〕`idempotency`、`replay-attack`（均为本条新增）｜ `type-validation`（复用，更早主题）

**与 7.5 的分工**：7.5 聚焦支付回调的信任边界（验签+核金额+回调幂等），本条聚焦通用幂等约束（表单/接口/消息三面）。回调重放是幂等缺失在支付场景的具体表现，已在 7.5 讲过，本条不重复。

**相关术语网**：`idempotency-missing` → 机制：`idempotency`（本条新增，幂等键）｜ 近亲：`replay-attack`（本条新增，重放是「同一件事的副本再投」）｜ 联动：7.3 业务竞态（并发面 vs 重复面）、7.5 支付回调（回调重放）、7.2 流程绕过（状态机终态保护）｜ 同教训：访问控制主题 4.7（前端防重只是体验优化，服务端才是决定）
