### 0.4 技术约束（v1.3，主理人实读核实，写死口径）

## 1. 产品定位与成功标准

### 1.1 一句话定位

**8 级主线是敲门砖：让零基础同学第一次看懂「一个输入怎么把一个程序搞崩」；系统学习库是真正的主体：让同一个人在 16 章、82 类漏洞里，想学哪类学哪类，每类都能读到「它是什么、怎么认、怎么防」，并做几道题确认自己真懂了。**

两者关系像「驾照科目一入门课」和「一本随身查的交规手册」：主线给方法和信心，学习库给覆盖面和长期可用性。主线讲过的词，学习库直接复用；学习库里出现的每个新词，都在知识库（glossary.ts）里有一句白话兜底。

### 1.2 分工边界（严格）

| | 8 级主线 L0~L7 | 沙箱系统学习库（本次新增） |
|---|---|---|
| 角色 | 敲门砖、演示动线、老师看到的「一条线」 | 系统学习、工具书式查用、学生自主逛 |
| 顺序 | **严格线性**，解锁、next 不越界 | **完全无顺序**，任意条目直达、无解锁 |
| 内容 | 单一漏洞链：缓冲区溢出 → 危险调用 → 限长修复 → 条件 → 崩溃 → 栈保护 → 综合实践 | 16 章 / 82 类，覆盖应用、系统、网络、云、API、AI |
| 难度 | 8 级递进，每级 ≤1 个新概念 | 低 / 中 / 高三档，条目之间**不构成前置关系**；难度=学习复杂度（§3.3） |
| 条目形态 | 交互关卡 + 沙箱 | **按难度分档 + 分两期**：低=知识卡+3 题自测；中/高=知识卡+案例演示+指导（第一期），闯关为第二期增量（§2，用户已定稿） |
| 现状 | 已完成，**本次不动** | 本次规划，逐章交付；**批 0 = 最小可用版本（能查能读、不闯关）** |

### 1.3 零基础读者进入学习库的心智路径（设计目标，不是强制路径）

```
1) 从主线 L7 走出来，手里有 4 个词：输入、盒子装不下、call、防护
        ↓
2) 先读「第 0 章 坐标系」：把「输入」升级成 Source，把「危险调用」升级成 Sink，
   把「程序把输入放错位置」升级成「信任边界被穿越」      ← 只多 3 个词，3 分钟
        ↓
3) 按自己兴趣/老师布置，直奔任意一章的任意一条（推荐从「低」档开始，但不锁）
        ↓
4) 按难度进入对应形态（用户已定稿，v1.2 第一期）：
   - **低难度** → 读知识卡（8 段，白话，不懂的词点一下出解释）→ 做 3 道自测题（认出它 / 怎么防 / 易错点），只读不做也算学完
   - **中/高难度** → 读知识卡 → 看案例演示 → 指导模式带着走（第一期到为止）
   - **第二期起**：中/高档再补交互闯关（材料→提问→全选项解释），第一期不闯关也能查能读
        ↓
5) 想动手的二进制条目：进入现有 SandboxPlayer 实战沙箱（4 个中/高难度案例，已存在，照常可用）
```

**防迷路的底线**：学习库的任何页面都不能出现「未解锁」「请先学完第 N 章」这类主线式提示。用户明确要求「想学哪个都行」，这条是硬约束，优先级高于「循序渐进」。

## 2. 沙箱条目形态 —— 已定稿：按难度分档的混合方案

### 2.1 决策结论（用户已拍板，v1.2 含两期拆分）

本库采用**混合方案，阈值=难度档**，且**闯关分两期**（决策变更 A）：

- **低难度 → 知识卡 + 3 道自测题**（认出它 / 怎么防 / 易错点），**不做闯关**。
- **中 / 高难度 → 第一期：知识卡 + 案例演示 + 指导模式；第二期：再补交互闯关**（复用并扩展现有 `SandboxStage`）。

当初评估过的三种候选（A 全知识卡 / B 全量闯关 / C 混合）中，用户选择的是 C。v1.2 的用户新口径进一步把 C 的「交互」部分推到第二期，先交付「最小可用版本：能查、能读」。取舍理由留存如下：

| 方案 | 致命问题（为什么不选） |
|---|---|
| A 全知识卡 | 中/高难度漏洞只有读没有「动手找线索」，用户要求这类第二期要有交互 |
| B 全量闯关 | 82 类 × 5 阶段 × 4 选项 ≈ 1600 道题，一个人做不完；Web/云/AI 类硬套 `terminal/disasm` 会失真 |
| **C 混合 + 两期（已定稿）** | 第一期知识卡覆盖 82 类、零基础只读也能学完，先把可用版本交出来；第二期再为中/高档补闯关，深度与覆盖分期兑现 |

### 2.2 两种形态的完整定义（第一期 / 第二期）

**形态 A · 知识卡 + 3 道自测题（仅低难度，第一期即完整交付）**

```
┌───────────────────────────────────────────────────────────┐
│ 8 段知识卡：一句话 / 成因与位置 / 分类(可选) / 典型特征 /   │
│   危害 / 验证思路 / 防护 / 易错点                          │
│   → 每段白话化 + 主线术语锚点 + 高频专业词 TermButton      │
│   → 低频词只在首次出现给 inline 白话（R7，见 §5.3）        │
├───────────────────────────────────────────────────────────┤
│ 自测题：固定 3 题（每题 material + question + 4 选项全解释）│
│   ① 认出它：考「识别信号」                                 │
│   ② 怎么防：考「防护思路」                                 │
│   ③ 易错点：考「常见误区」                                 │
│   → 只确认「读懂了」，不是闯关：不锁关、不扣分、可重看      │
└───────────────────────────────────────────────────────────┘
```
**典型条目**：SQL 注入（8.1）、ORM/HQL（8.7）、CRLF（8.8）、日志注入（8.9）。完整示例见 **8.1 SQL 注入**（3 题 + 术语网 + 真实案例参考三示范集中在此）与 **8.8 CRLF 注入**（纯形态 A 样板）。

### 2.5 闯关模板库（R5，给架构师/工程师的输入）

**目的**：同类漏洞复用同一套闯关结构，只换材料与选项，减少重复设计。第二期补闯关时，先选模板再填内容。

| 模板 id | 适用漏洞类型 | stage 骨架（固定套路，4 关） | tool 序列 |
|---|---|---|---|
| `TPL-INJECT` | 注入类（SQL/NoSQL/命令/表达式/SSTI/LDAP/ORM/CRLF） | ① 认信号（输入异常→identify）→ ② 认引擎/类型（定位具体机制）→ ③ 判严重（证明能读到内部数据）→ ④ 选根治（四选一辨根治 vs 兜底） | observe → observe → observe → code |
| `TPL-AUTHZ` | 认证/授权类（IDOR/越权/密码重置/JWT） | ① 认对象（哪个 id/角色可控）→ ② 换标识（改成他人）→ ③ 证明越权（读到他人数据）→ ④ 选根治（服务端对象级鉴权） | request → request → result → code |
| `TPL-FILE` | 文件类（上传/包含/读取/路径穿越） | ① 认控制点（路径/类型/内容谁可控）→ ② 试绕过（后缀/MIME/双写）→ ③ 验证执行（是否被解析）→ ④ 选根治（白名单+重命名+隔离存储） | observe → request → result → code |
| `TPL-CHAIN` | 链式/配置类（SSRF/云元数据/漏洞链/业务逻辑） | ① 认边界（哪一步跨了信任边界）→ ② 试可达（能否打到内部）→ ③ 判影响（能拿到什么）→ ④ 选根治（分层+最小权限） | observe → request → result → code |
| `TPL-CLIENT` | 客户端类（postMessage/跨窗口、DOM 覆盖等浏览器端机制类） | ① 认入口（哪个输入点可控）→ ② 试触发（构造无害验证）→ ③ 判影响（能做什么）→ ④ 选根治（编码/校验/白名单） | observe → request → result → code |

**每个 stage 的固定字段骨架**（沿用现有 `SandboxStage`）：

```
{ tool, mission（本关小目标，一句话）,
  material（演示样例材料，含 source:'demo'）,
  question, options:[{text, correct, explain}×4]（1 对 3 错，错项逐个解释）,
  guideWhy, guideHow, verdict（过关/重来的判定与提示） }
```

**示范：8.3 命令注入与 8.5 SSTI 共用 `TPL-INJECT`**

| 关 | TPL-INJECT 固定套路 | 8.3 命令注入填入 | 8.5 SSTI 填入 |
|---|---|---|---|
| ① 认信号 | 输入异常载荷，问「说明什么」 | `; sleep 5` 变慢 → 命令被执行 | `{{7*7}}`→49 → 被模板求值 |
| ② 认引擎/类型 | 定位具体机制，问「是哪一种」 | 有回显/无回显-延时/外带 | Jinja2/Twig/Freemarker 语法 |
| ③ 判严重 | 证明能读内部数据，问「严重吗」 | 能执行命令=服务器沦陷 | 带出配置项=可读内部数据 |
| ④ 选根治 | 四个改法，问「哪个根治」 | 参数数组、shell=False | 模板固定、数据只作变量 |

> 骨架、字段、关数、判定逻辑完全复用；只有 material 和 options 的文案随漏洞替换。这就是模板库的价值——第二期补一批中/高档闯关时，设计成本从「每类重新想 4 关」降到「套模板填内容」。

### 2.8 类比库 + 反例库（R13）

写新卡时最费时的两件事：想一个好类比、避免踩前人踩过的类比坑。建两个库跨章复用。样章示范见 §8.0.3。

**类比库 · 数据结构**（每条一行）：

| 字段 | 说明 |
|---|---|
| `analogyId` | 稳定 id，如 `ANA-INJ-PEN` |
| `analogyText` | 类比正文，如「把用户输入拼进 SQL，等于把笔交给了陌生人」 |
| `appliesTo` | 适用漏洞 id 数组，如 `[sql-injection, command-injection]` |
| `whyFit` | 为什么贴切——类比映射到的技术点，如「数据位→笔、命令→陌生人的话」 |
| `theme` | 主题分类：注入类 / 越权类 / 配置类 / 认证类 / 文件类 / 通用 |
| `verifiedBy` | 验证来源：哪章评审通过 / 哪次读者验证（§6.4）反馈好 |

**反例库 · 数据结构**（每条一行）：

| 字段 | 说明 |
|---|---|
| `badId` | 稳定 id，如 `BAD-INJ-VIRUS` |
| `badText` | 看起来形象但误导的类比原文 |
| `whyMislead` | 为什么误导——错在技术映射的哪一步 |
| `fix` | 建议改法（改成什么类比 / 直接删掉用术语） |
| `appliesTo` / `theme` | 同类比库，便于按主题检索避坑 |
| `source` | 哪章评审 / 哪次读者验证发现的问题 |

**维护规则（随章节复用）**：
1. 每章交付时，评审表 A2（§3.5.1）判定「类比贴切 ✔」的进类比库，「✘ 误导」的进反例库。
2. 写新章时按 `theme` 检索：先查反例库避坑，再查类比库找可复用项；复用时 `appliesTo` 追加新漏洞 id，`verifiedBy` 累加。
3. 两个库随章增量、不一次性建；不新增 npm 依赖，作为文档/数据文件维护即可。

> 类比库/反例库与 §5.3 术语网络互补：术语网解决「词与词的关系」，类比库解决「这个漏洞像什么、别像错成什么」。

### 2.9 每张卡底部「相关漏洞」推荐区（R16）

每张知识卡底部放一个**相关漏洞**推荐区，帮读者横向逛，但**不制造学习路径压力**：

**推荐来源（三类，可叠加）**：
1. **同章相邻**：同一章里编号相邻的 2~3 条（如 8.1 SQL 注入 → 8.7 ORM/HQL 注入）。
2. **跨章同类**：按 `family` 标签跨章聚合（如所有「注入类」：SQL/NoSQL/命令/SSTI/LDAP/CRLF）。
3. **方法论提及**：方法论卡正文提到的漏洞（如 M01 三条铁律提到 SQL 注入、命令注入 → 互相挂链）。

**数据结构实现**：`related: string[]`（§2.3 已加），存计算好的漏洞 id 数组；生成时按上面三类各取若干、去重。可用 `chapter` / `family` / `mentionedByMethodCard` 标签辅助预计算，但**最终以预计算好的 `related` 数组为准**（静态站运行时不做复杂图计算）。

**弱化引导感（硬规则）**：
- 栏目标题用「相关漏洞，随便看看」，**不用**「下一步」「建议学习」「未学」等词。
- 卡片样式与正文区分（浅色小卡片），不带进度勾、不带锁、不带顺序号。
- 文案固定一句：「这些和本条有点关系，想看哪个点哪个，没有先后顺序。」

> 与 §4.3「不迷路」一致：推荐是**横向跳转**，不是**纵向路径**。

### 2.10 社区纠错通道（R17，静态站外部渠道）

每张卡底部放一个「报告错误」入口，让学生反馈技术错误或过时信息。**静态站无后端（TC1），不能站内提交**——采用两种外部渠道：

| 方案 | 做法 | 适用 |
|---|---|---|
| **方案 A（推荐，零门槛）** | `mailto:` 链接，预填收件人、主题「[BinInsight 纠错] <漏洞名>」、正文模板（错误位置 / 错误内容 / 建议改法 / 你的身份） | 无需 GitHub 账号，课程作业演示最省事 |
| **方案 B（可选）** | 跳转公开 GitHub Issues，带 issue 模板（同样四个字段） | 若以后把学习库开源则更合适 |

**文案与标注（写死）**：
- 链接文字：「发现错误？报告一下（外部渠道）」。
- 链接旁固定小字：「点击会打开你的邮件客户端 / 外部网页；本站是静态页面，不收集、不存储你的信息。」

### 3.3 本站难度档判定规则（难度=学习复杂度，用户已定稿）

**口径（写死）**：难度只回答一个问题——「**零基础要花多大力气才学会它**」。它不看危害大小（★危险度，见 §3.4），只看理解与实践的复杂度。这是用户原话「难度是指学习的复杂度」的落地。

**可判定标准（每档给足条件，可复核）**：

| 难度档 | 可判定标准（满足即可归此档） | 现有 `SandboxDifficulty` 映射 | 卡片颜色 | 条目形态（v1.2 两期） |
|---|---|---|---|---|
| **低** | ① 单一输入点就能演示；② 能用一个生活例子讲明白；③ 无前置知识（主线 8 级之外不用先学别的）。三条全满足 | `beginner` / `beginner-plus` / `basic` 合并展示为「低」 | 绿 | 知识卡 + 3 题自测（**不闯关**） |
| **中** | 命中任一条：需要理解**一个机制**（如对象型查询、表达式求值），或**有多个变体**要分辨（如盲注的几种形态），或需要构造一次请求才能验证 | `intermediate` | 橙 | 第一期：知识卡+案例演示+指导；第二期补闯关 |
| **高** | 命中任一条：需要**组合多个概念**、**链式利用**，或依赖**底层原理 / 协议 / 状态机 / 权限模型**才能判断它存在 | `advanced` | 红 | 第一期：知识卡+案例演示+指导；第二期补闯关 |

**判定辅助三问**（与上面标准一致，用于拿不准时复核）：

1. 学会它需要理解的前置概念是否 **>2 个**？
2. 是否需要理解**协议 / 状态机 / 权限模型 / 底层原理**才能判断它存在？
3. 是否需要**自己构造请求或代码**才能验证？

命中 0~1 项 → 低；命中 2 项 → 中；命中 3 项 → 高。

> **前置概念计数规则（v1.2 增补）**：前置概念只统计**前序章节未讲过的概念**；已在主线或前序章节讲过的不计入。这正是访问控制与授权主题 4.5/4.6 判「中」时的隐含标准（CORS 只新增「同源放行清单」一个新概念、权限模型各变体机制均一句话可讲），写进规则让复评人对齐。

### 3.4 ★危险度 ≠ 本站难度档（务必分开讲）

| | ★危险度 | 本站难度档（低/中/高） |
|---|---|---|
| 回答的问题 | 「**它一旦被利用，有多惨？**」 | 「**零基础要花多大力气才学会它？**」 |
| 视角 | 行业 / 防守方 / 通用场景 | 学生 / 教学方 |
| 来源 | 工具书（1~5 星） | 本站三问法（§3.3） |
| 会不会变 | 随业务环境变（内网 SQL 注入可能比公网信息泄露更致命，工具书第 0.4 节原话） | 随学生基础变，但本库一期固定 |
| 在卡片上怎么放 | 右上角小标记 `危险度 ★★★★☆`，**不参与筛选排序** | 卡片主标签（绿/橙/红），**参与筛选** |

**用三个反例讲清区别**（写进第 0 章样章）：

- **SQL 注入 ★★★★★ 但难度「低」**：危害是拖库（星最高）；但概念只要一句「把用户输入拼进问话」，信号是引号报错，零基础十分钟能懂。→ 高危险、低难度（决策 1 原例）。
- **命令注入 ★★★★★ 但难度「中」**：危害同样是服务器沦陷；但无回显时要理解延时/外带两种验证机制，还要懂 shell——概念好懂、验证要绕一圈。→ 高危险、中难度。
- **密码重置逻辑缺陷 ★★★★☆ 且难度「高」**：危害是账号任意接管；要理解 token 生成、时效、绑定、服务端状态机四件事，零基础读起来吃力。→ 中高危险、高难度。
- **日志注入 ★★☆☆☆ 但难度「低」**：危害很小（干扰审计），概念只是「把带控制字符的输入写进日志」，一句话能懂。→ 低危险、低难度。

结论：**★ 告诉你「值不值得重视」，难度档告诉你「现在学它合不合适」。两者不可互相推导。**

### 3.5 难度评审机制（R3：两人独立评估 + 对齐 + 裁决）

**为什么要评审**：难度判定直接决定形态与分期（低=3 题、中/高=案例演示+指导+第二期闯关），一人判定容易偏松或偏紧。用户要求每章难度由**两人独立评估**，不一致时讨论对齐。

**流程（每章交付前走一遍）**：

```
PM 初评（填评审表左半） ──┐
                          ├─→ 结果一致 → 采用，写入样章 §x.0.1 判定表
架构师/QA 复评（右半） ──┘   │
                          └─→ 不一致 → 讨论对齐 → 仍不一致 → 裁决人拍板 → 记录结论
```

**两人角色**：
- **初评：产品经理（许清楚）**——从「零基础读者要迈多高台阶」视角，按 §3.3 三问法判。
- **复评：架构师（或用户指定的 QA / 授课老师）**——从「这条内容做出来要多少前置、验证要构造到什么程度」视角独立判，**初评时互不参照对方结论**，避免从众。

**评审记录字段**（每条一行）：

| 字段 | 说明 |
|---|---|
| 条目 id / 名称 | 如 `inj-command` / 命令注入 |
| 初评难度 | 低 / 中 / 高 |
| 初评三问命中 | 命中数 0~3 + 命中哪几问 |
| 初评理由 | 一句话（引用 §3.3 标准或锚定示例） |
| 复评难度 | 低 / 中 / 高 |
| 复评三问命中 / 理由 | 同上 |
| 是否一致 | 是 / 否 |
| 分歧点 | 不一致时写清楚卡在哪一问 |
| 对齐结论 | 讨论后的最终难度 |
| 裁决人 | 仅在不一致且讨论未果时填（默认：用户；日常可由主理人代裁） |

**对齐规则**：
1. 先看**三问命中数**差异——多数分歧是「某问算不算命中」，逐问对照 §3.3 的标准与锚定示例即可收敛。
2. 仍不一致时，以「**零基础读者能不能靠一个例子读懂**」为最终标尺。
3. 实在难判 → **就低不就高**（宁可多给一人只读知识卡，也不要让零基础一上来撞高难度）。这条与「零基础友好最高优先」一致。
4. 裁决人：用户为最终裁决人；日常不一致由主理人代裁并记录。评审结论写入样章判定表，alinment 后不再反复改。

> 本文档的评审是**流程设计与示范**：我在样章里给出「第 1 章两人评审记录表」的**格式示范**（§8.0.2），初评由我完成，复评栏位留空/示例填写，待团队实际评审时补全。不需要我此刻真的去找第二个人评。

### 3.5.1 每章交付前的三张评审表（R12）

每章交付时随附**三张轻量评审表**，并列放在章末（样章示范见 §8.0.2）：

- **表 C（已有）· 难度评审表** = §3.5 的两人独立难度判定表（字段见上）。
- **表 A（新增）· 白话质量表**：3 项，逐条打勾 + 问题条目号。
- **表 B（新增）· 技术准确性表**：3 项，逐条打勾 + 问题条目号。

**表 A · 白话质量（3 项）**

| # | 检查项 | 判定 | 不通过时记什么 |
|---|---|---|---|
| A1 | 能否**不看术语表**读懂「一句话」？ | ✔ / ✘ | 记下读不懂的条目 id + 卡在哪半句 |
| A2 | 类比是否贴切？（如「把笔交给了陌生人」是否准确传达「数据被当命令」） | ✔ / ✘ | 记下不贴切的类比 + 为什么误导（进 §2.8 反例库） |
| A3 | 是否有「读了三遍还不懂」的段落？ | ✔ / ✘ | 记下段落号，交给 §6.4 读者验证复核 |

**表 B · 技术准确性（3 项）**

| # | 检查项 | 判定 | 不通过时记什么 |
|---|---|---|---|
| B1 | 示例代码是否可运行？（语法正确、逻辑自洽；**硬标准：代码/参数与目标文件路径必须逐字符对上，包括前缀、后缀、包装器位置**——写作模板逻辑链自查块的逐字符核对项） | ✔ / ✘ | 记下条目 id + 错在哪行 |
| B2 | 防护建议是否可落地？（不是空泛的「加强校验」） | ✔ / ✘ | 记下条目 id + 哪条防护太泛 |
| B3 | 术语使用是否符合业界规范？（不生造、不误用） | ✔ / ✘ | 记下条目 id + 用词 + 正确说法 |

**填写规范**：
1. 三张表都由**初评人（PM）先填**，复评人（架构师/QA）对表 B 技术准确性**复核签字**（技术项更适合技术角色把关），表 A 可由读者验证（§6.4）交叉印证。
2. 只在「✘」时写问题条目号与说明，「✔」留空即可——保持轻量，不写长篇。
3. 任一表出现 ✘ 且不修复，该章不得进入下一章。修复后在表尾记「已修 + 条目号」。

> **口径澄清（用户补充，与 R7 一致）**：**专业术语本身已足够明确的，不需要全部转成白话解释**。R7 已定「低频词 inline 白话、高频词 TermButton/related」，表 A 的白话检查针对的是「一句话」和类比，**不是要求把每个术语都改写成大白话**。避免过度白话化导致内容啰嗦、专业失真。贴切且已被读者验证的类比，收入 §2.8 类比库复用。

### 4.1 导航形态：三件套

### 4.2 卡片上要有的信息（一屏看懂）

```
└────────────────────────────────────────────────┘
```

### 4.3 如何避免新手迷路（软引导，不强制）

1. **默认排序 = 难度低→中→高**（同一难度内按章号），用户可切「按章」「按名称」。默认排序本身就是一条建议路径，但不产生任何锁定。
2. **第 0 章作为唯一软引导**：学习库页头固定一条横幅「第一次来？花 3 分钟看『漏洞分类坐标系』，不看也能直接逛」。点击进第 0 章；不点不影响任何操作。
3. **「先修词」提示而非门槛**：每张卡底部列出「读这张卡会用到：SQL、参数化查询」，每个词都是 TermButton，点开即白话解释；**没有"必须先掌握"的锁**。
4. **术语浮层全局可用**：任何页面的任何专业词点一下出白话解释（复用现有 `TermButton` + `GlossaryProvider`），避免「读到一半出去查」。
5. **不与主线的进度系统混用**：主线有 localStorage 解锁进度，学习库**不显示解锁态**；唯一记录是「已读/已测」的轻量标记，仅用于卡角小勾，不控制可达性。
6. **危险度不参与默认排序**：否则零基础第一眼全是 ★★★★★，反而劝退。

### 4.5 搜索三件套：拼音 / 高亮 / 建议（R14，第一期「能查」）

用户在 §4.1 的搜索框基础上明确要三件事。三项都属**第一期「能查」**，静态前端实现，不依赖服务器（TC1）。

#### 4.5.1 拼音搜索（零依赖，TC2）

**需求**：输入「sql zhu ru」命中「SQL 注入」。

**方案（零 npm 依赖）**：不引入拼音库；在内容创作阶段，给每张卡的 `pinyin` 字段（§2.3）预存三种串：

```json
// 8.1 SQL 注入的 pinyin 字段样例
"pinyin": {
  "full": "sql zhu ru",     // 全拼带空格
  "initial": "sqlzr",        // 首字母连写
  "joined": "sqlzhuru"       // 全拼连写
}
```

**匹配规则**：
1. **匹配字段**：标题（`title`）、别名（`aliases`）、识别信号（`signals`）——三者都做拼音匹配。
2. **支持形式**：全拼带空格（`sql zhu ru`）、全拼连写（`sqlzhuru`）、首字母（`sqlzr`）、中文直接搜、英文直接搜；输入串去掉空格后与三个 pinyin 串做包含匹配。
3. **运行时**：纯字符串 `includes()` 匹配，零依赖、零网络请求。
4. **创作成本**：每张卡多写一个 `pinyin` 字段（3 串），在逐章交付时随卡片一起产出、一起评审（表 B 核对拼音是否正确）。

> 为什么不用拼音库：TC2——不新增 npm 依赖；且预存串的匹配比运行时转换更快、更符合静态站「数据先行」的思路。

#### 4.5.2 搜索结果高亮

**需求**：搜「引号报错」后，在结果卡片上高亮命中文字，让学生看到「为什么命中」。

**前端实现要点**：
1. 搜索时对命中字段取**命中片段**（前后各留 ~20 字，`…` 省略），不整段显示。
2. 用 `<mark>` 包裹命中词；**先对文本做 HTML 转义再插入标记**，避免把用户输入的 `<script>` 当 HTML 执行（防 XSS）。
3. 高亮匹配要同时覆盖：中文命中、英文命中、拼音命中（拼音命中时高亮中文标题，因为那是读者真正要看到的）。
4. 每个结果显示「命中原因」小标：`标题` / `别名` / `信号` / `拼音`，帮助理解。

#### 4.5.3 搜索建议 / 自动补全

**需求**：输入「SQL」下拉提示「SQL 注入」「SQL 盲注」「NoSQL 注入」。

**候选来源**：所有卡的 `title` + `aliases` + `pinyin`（去重后作为候选词库，静态数据、随导出打包）。

**排序规则**：
1. 前缀匹配优先（`SQL` 开头）> 包含匹配（`NoSQL` 含 SQL）> 拼音匹配。
2. 同优先级内：卡片点击量（§4.6 的「已探索」不计入排名，这里的点击量仅用于**建议排序**、不展示给用户，不违反 R15「不排名」——R15 禁的是对用户展示排名） > 标题短者优先。
3. 下拉最多 6 条，超出提示「按回车查看全部结果」。
4. 键盘上下键可选、回车直达，鼠标点击直达；搜索建议**不锁关、不引导路径**。

### 4.6 学习库首页个人进度条（R15，仅自己可见）

首页放一个轻量进度条，只记录「我探索过什么」，给一点点成就感，**不制造学习压力**。

**显示样式**（文案示例）：

```
你已探索：12 / 82 类漏洞 ｜ 3 / 9 张方法论卡
低难度：8/18  ｜  中难度：3/33  ｜  高难度：1/31   ← 分母用 §3.2.2 本文档判定
[隐藏进度] 开关
```

**三条硬规则（写死，违反即失败）**：
1. **不显示「未完成」**：只显示「已探索」，**绝不写**「还剩 70 类未学」「完成度 15%」这类反向/百分比文案。
2. **不做排名**：**不显示**「超过 X% 同学」「你排第 N」——这是给自己的记录，不是社交比较。
3. **可隐藏**：提供「隐藏进度」开关，一键关掉整个进度条；状态存 localStorage，关了就不再显示。

**「已探索」定义（低门槛）**：**点开卡片即计入**（进入详情页就算，不要求做完自测/读完/答对）。理由：门槛越低越不制造压力，与「想学哪个都行」一致。

**技术口径（TC1 静态站）**：
- 用 **localStorage** 存「已探索」的 id 集合，纯本地、**不跨设备同步**（换浏览器/设备会重置，文案不承诺同步）。
- 与主线的 `useProgress` **明确隔离**：用独立 storage key（如 `bininsight-explored-v1`），主线解锁进度与学习库探索记录**互不读写、不混用**；学习库永不用「已探索」控制任何可达性（仍是无顺序、无锁）。
- 隐藏开关同样存 localStorage 独立 key（如 `bininsight-progress-hidden`）。

> 与 §4.3 第 5 条呼应：学习库不显示解锁态；进度条只是「我看过哪些」的本地小抄，不是进度系统。

## 5. 术语表策略（工具书词汇系统性进 glossary.ts）

### 5.1 策略：**随章增量，不一次性导入**

理由：① 用户要求逐章确认，术语必须跟着该章一起给用户过目；② 一次性塞 100+ 词条，白话质量无法逐条把关；③ `glossary.ts` 是单一数据源，追加不覆盖，可按章回溯。

### 5.2 每章提取规则（可执行）

1. **提取范围**：该章正文里所有专业词、英文缩写、代号、函数名、状态码（如 `alg:none`、`$ne`、`{{7*7}}` 这类载荷模式，作为 alias 挂在母词下，不单列）。
2. **优先级**：工具书附录 F 的 18 条术语优先落地 → 该章加粗/代码/表格中出现的词 → 该章「一句话」里不得不解释的词。
3. **每章数量**：建议 **15~25 条**。超出的低频词不单列，并入上位词条的 `detail` 字段（例：各种模板引擎语法并入 `ssti` 的 detail）。
4. **去重**：先查 `glossary.ts` 现有 45 条（含上一轮新增 10 条），已有 id 直接复用，**不改既有 plain**（除非该词白话明显不够用，需用户确认）；新增词条 id 用小写中划线，例：`sql-injection`、`parameterized-query`。
5. **字段对齐**（严格按现有 `GlossEntry`）：

| 字段 | 填法 | 示例 |
|---|---|---|
| `id` | 小写中划线，全局唯一 | `'sql-injection'` |
| `term` | 中文主名（英文缩写放括号） | `'SQL 注入'` |
| `plain` | **≤2 句白话**，先类比后术语，不出现未解释的新词 | 「把用户输入拼进 SQL 语句，等于把笔交给了陌生人。原本该是『数据』的输入被当成了『命令』。」 |
| `level` | **一律 `'l8'`** | `'l8'` |
| `aliases` | 2~5 个，含英文缩写与常见写法 | `['SQL注入', 'SQLi', 'sql injection']` |
| `anchor` | `/reference/glossary#<id>` | `'/reference/glossary#sql-injection'` |
| `detail` | 可选；放载荷模式、边界条件、易混点 | — |

6. **`level` 为什么一律 `'l8'`**：该字段含义是「属于主线第几级，`l8` = 不属主线任何一级、不考核」。系统库所有词都不在 L0~L7 主线里，因此统一 `l8`。**不需要、也不允许为此改 `lesson.ts` 的 `LevelId`**（上一轮红线）。
7. **交付校验**：每章交付时附「本章术语清单」表（与 Part 2 §9 同格式），用户确认后才追加进 `glossary.ts`； TermButton 挂载点同步列出（哪一章哪一节第一次出现该词）。
8. **附录 F 的覆盖检查**：18 条里与本库阶段相关的（Source/Sink、攻击面、信任边界、POC、盲注、WAF/RASP、IDOR/BOLA、CSP、SRI、IMDS、TOCTOU、AEAD、CSPRNG）应在对应章节各自落地；Gadget Chain、CWPP/CNAPP 等低频词在用到的章再落。

### 5.3 术语网络：低频词 inline、高频词建 related（R7）

**问题**：一张卡片的「分类表 / 典型特征」里常塞十几个专业词，如果每个都挂 TermButton，读者一路点开十几个浮层，反而读不下去；而真正高频、贯穿全库的核心词又缺少横向关联。

**规则 1 · 低频词只首次给 inline 白话，不做 TermButton**：
- 判定「低频」：工具书里只在这一条/这一章出现、全库复用率低的词（如各种具体模板引擎语法、某数据库特有参数、载荷变体名）。
- 做法：在该词**首次出现处**用括号给一句 inline 白话（如「堆叠注入（一次执行多条 SQL，用分号隔开）」），之后同章再用就不解释、也不挂浮层。
- 好处：卡片上 TermButton 数量可控（一张卡建议 ≤5 个），读起来顺。

**规则 2 · 高频词加「相关术语」链接，形成术语网络**：
- 判定「高频」：跨 ≥3 章复用的核心词（如 SQL 注入、参数化查询、盲注、Source/Sink、WAF、权限模型）。
- 做法：`GlossEntry` 增加可选字段 `related?: string[]`（存相关词 id 数组）；TermPopover 浮层底部显示「相关术语」小链接，点一下跳到另一个词。这样学生从一个词能走到一张网。
- 示例网络（详见 §9.1）：`sql-injection` → `parameterized-query`（根治手段）、`orm`（常见误用）、`blind-injection`（变体）、`waf`（兜底）。

**规则 3 · 字段对齐（给架构师）**：`related` 是**可选新增字段**，不改现有 45 词条也能上线（老词没有 related 就不显示相关区）；新增词条按 §9 草案带 related。`GlossEntry` 追加：

```ts
related?: string[];   // 相关术语 id 数组，形成术语网络（R7）
```

**示范**：8.1 SQL 注入正文已按此改写——高频词（SQL 注入/参数化查询/盲注/ORM）挂 TermButton，低频词（报错注入/堆叠注入/二次注入/宽字节注入）用 inline 白话；卡片末尾给出「相关术语网」。见 Part 2 §8.1。

## 7. 第 0 章 · 漏洞分类框架（沙箱开篇）

### 7.0 一句话 + 与主线的连接

**一句话**：漏洞名字有几千个，但「信任边界」只有一个——学会认边界，比背名字有用。

**和 8 级主线的连接**：主线 L0 教「程序读你的输入，放进固定大小的盒子」，L1 教「盒子装不下会洒到旁边」，L2 教「先找 call，再看名字里有没有 strcpy」。这一章只把这三句话升级成三个通用词：

| 主线已经会的（白话） | 系统库里的正式说法 | 升级了什么 |
|---|---|---|
| 你敲进去的东西 | **Source〔T: source〕**（输入源） | 不只有键盘输入，还有 Header、Cookie、文件名、上传内容、第三方回调 |
| 那个不检查长度的 strcpy | **危险汇聚点 / Sink〔T: sink〕**（危险操作发生的位置） | 不只有 strcpy，还有 SQL 执行、命令执行、文件读写、模板渲染、发起请求 |
| 输入被放错了地方 / 盖住了旁边 | **信任边界被穿越〔T: trust-boundary〕** | 不只有「数据盖住了返回地址」，还有「数据被当成了指令、当成命令、当成查询条件」 |

> 一句话记法：**漏洞 = 一条从「不可信的输入」到「危险的操作」之间、没有被好好检查的通路。**（这就是 Source → Sink 模型〔T: source-sink〕）

### 7.1 五个分类维度（同一漏洞可以同时属于多个维度）

| 维度 | 白话问法 | 用途 | 举例 |
|---|---|---|---|
| 按**成因** | 这是谁的责任？（设计 / 写代码 / 配环境 / 运维 / 第三方组件） | 决定「该谁改」 | SQL 注入是写代码的问题；默认口令是配置问题 |
| 按**位置** | 它发生在哪一层？（客户端 → 传输 → 服务端 → 数据 → 主机 → 网络 → 云 → 供应链） | 决定「去哪找」 | XSS 在浏览器；命令注入在服务器 |
| 按**触发前提** | 要什么条件才能利用？（无需登录 / 低权限 / 需要受害者点一下 / 需要能在机器上操作） | 决定「有多急」 | 无需认证的漏洞最危险 |
| 按**影响** | 破坏了什么？（机密性 / 完整性 / 可用性；影响一个人还是一个系统） | 决定「值多少」 | 读到一个人的手机号 vs 拖走全站用户表 |
| 按**行业标准** | 业界怎么称呼它？（OWASP〔T: owasp〕、CWE〔T: cwe〕、CVE〔T: cve〕、CVSS〔T: cvss〕） | 决定「怎么沟通」 | 报告里写 CWE-89 比写「那个引号洞」专业 |

**本站怎么用**：本库章节按「位置」（第二维度）组织，卡片标签显示「难度」（本站自定义）和「危险度★」（工具书口径），术语里保留行业标准编号作知识锚点（与主线一致：编号只作拓展知识锚点，不要求背）。

### 7.3 三条铁律（比背名字重要）

**铁律一：漏洞的本质是「信任边界被穿越」。**
程序默认信任了不该信任的东西。主线里是「信任了一段输入，结果它比盒子长」；到了 Web 世界，可能是「信任了 URL 里的 id，结果它指向别人的订单」「信任了请求头里的 Host，结果它拼进了邮件链接」。**找漏洞 = 找「哪里把不可信当成了可信」。**

**铁律二：一切外部输入都不可信（Source → Sink）。**
- Source〔T: source〕举例：URL 参数、表单、Header、Cookie、文件名、上传内容、第三方回调、消息队列，甚至数据库里的历史脏数据。
- Sink〔T: sink〕举例：SQL 执行、系统命令、文件读写、反序列化〔T: deserialization〕、模板渲染、发起 HTTP 请求、重定向、写日志。
- 漏洞 = 两者之间那条**没被好好检查**的通路。
- **和主线的对应**：L2 的「先找 call、再看名字」就是在找最小版的 Sink；L4 的「两道关」就是在 Source 和 Sink 之间加检查。

**铁律三：单点漏洞价值有限，漏洞链才是杀伤力。**
一个信息泄露本身可能只算「低危」，但它给出的数据库口令可以打开 SQL 注入，SQL 注入又可能读到管理员 token，token 又能进后台——这就是附录 E 讲的「漏洞链」。**评估一个漏洞时要问：它能把我送到哪一步？**

### 7.4 危险度 ★ 与难度档（先看这里的区别）

- ★危险度回答「**它一旦被利用有多惨**」，是工具书给的通用场景参考（1~5 星）。同一漏洞在不同业务里严重程度会变：内网系统的 SQL 注入可能比公网一个低危信息泄露更致命。
- 难度档（低/中/高）回答「**零基础学会它要迈多高台阶**」，是本站的教学标注，三问法判定（Part 1 §3.3）。
- **两者不能互相推导**。三个真实反例：
  - SQL 注入：危险度 ★★★★★（可拖库），但难度「低」——概念就一句「把输入拼进问话」，信号是引号报错。
  - 命令注入：危险度 ★★★★★，难度「中」——概念好懂，但无回显时要理解延时/外带两种验证机制。
  - 密码重置逻辑缺陷：危险度 ★★★★☆，难度「高」——要懂 token 生成、时效、绑定和状态机四件事。
- 卡片上两者分开放：难度是主标签（决定筛选），★是右上角小标记（只做提醒）。

### 7.5 第 0 章微自测（3 题，演示样例）

**题 1 · 认出它**｜材料：某登录接口把用户输入的用户名直接拼进一条数据库查询语句；另一个系统把用户输入的文件名直接拼进一条压缩命令。
问：这两个场景的共同点是什么？
- A. 都是把「用户数据」放到了「指令/命令」的位置 → ✔ 正确。解释：这就是信任边界被穿越——数据本该待在数据位，结果被当成指令解析。前者是 SQL 注入，后者是命令注入，本质同一条。
- B. 都一定会导致服务器被完全控制 → ✘ 错误。危害取决于数据库/命令的权限，不能一概而论；但「本质相同」这个判断是对的。
- C. 都是因为没用 HTTPS → ✘ 错误。HTTPS 保护传输过程，不阻止应用把输入拼进指令。这是两件不同的事。
- D. 都只影响当前用户自己 → ✘ 错误。影响范围取决于系统怎么用这些数据，常见情况是能读到别人的数据。

**题 2 · 怎么防**｜材料：开发说「我在输入框里过滤了 `union`、`;`、`'`，把危险词都挡住了，肯定安全」。
问：按第 0 章的思路，这个防法的根本问题在哪？
- A. 它在「输入黑名单」上打转，没做到「数据与指令分离」 → ✔ 正确。解释：根治是让数据永远待在数据位（参数化/白名单），黑名单永远在追新写法，追不完。对应注入类四层防护的第一层「分离」。
- B. 过滤的词还不够多 → ✘ 错误。加再多词也是在打补丁，不是根治。
- C. 应该改HTTPS → ✘ 错误。HTTPS 保护传输，不解决输入被当指令。
- D. 没问题，过滤就够了 → ✘ 错误。这是把「减少攻击面」误当成「阻断执行」。

**题 3 · 易错点**｜材料：某漏洞危险度 ★★★★★，但概念只要一句「把输入当命令」；另一漏洞危险度 ★★☆☆☆，但要理解一套业务流程才能发现。
问：按本站口径，哪个更适合零基础先学？
- A. 第一个 —— 危险度高不代表学习难度高 → ✔ 正确。危险度和难度是两个维度；第一个概念简单、信号直观，适合入门，虽然它一旦被利用很严重。
- B. 第二个 —— 危险度低更安全，先学它 → ✘ 错误。危险度低只是危害小，不代表好学会；「先学危害小的」不是本站的分档逻辑。
- C. 都先别学，先看完全部 16 章 → ✘ 错误。本库无顺序、无门槛，按兴趣选即可。
- D. 先看 ★ 数量决定 → ✘ 错误。★不参与难度筛选，它只是右上角的小提醒。

## 8. 第 1 章 · 注入类漏洞（9 条样章）

### 8.0 章导语

**共同本质（一句话）**：程序把「用户数据」当成了「代码 / 指令 / 结构」来解析。数据与指令的边界一旦消失，注入就成立。

**和主线的连接**：主线 L1 的溢出是「输入太长，盖住了旁边」——数据**物理上**越界；注入是「输入被当成命令」——数据**语义上**越界。两者都是「输入被放错了位置」，只是放错的地方不同。记住主线 L2 的动作「先找危险调用」，在 Web 世界就是把 Sink 从 `strcpy` 换成 `SQL 执行 / 命令执行 / 模板渲染 / 发起请求`。

**共同防护思路（四层，缺一不可）**：

1. **分离（根治）**：参数化 / 预编译〔T: parameterized-query〕，让数据永远待在数据位。
2. **白名单〔T: whitelist〕**：实在没法参数化的位置（表名、列名、排序方向、文件名、命令名），只允许从枚举里选。
3. **收敛**：错误信息不对外、最小权限运行、危险函数禁用。
4. **兜底**：WAF〔T: waf〕/ RASP〔T: rasp〕/ 运行时监控——只做兜底，绝不当主防护。

### 8.1 SQL 注入　`危险度 ★★★★★`　`本站难度：低`

**难度判定**：三问法命中 0~1 项——概念可用「把用户输入拼进问话」一句话讲清（主线 L2 危险调用的近亲），信号是引号报错与真假条件差异，不需要懂协议/状态机，也不需要写完整利用代码。

**一句话**：把用户输入拼进 SQL 语句〔T: sql〕，等于把笔交给了陌生人——原本该是「数据」的输入被当成了「命令」，攻击者能改写整句问话，读走、改掉甚至删掉数据。

**成因与位置**：
程序要查数据库，得先写一句 SQL。偷懒的写法是把用户输入直接用 `+` 拼进去：

```python
# 演示样例：危险写法
sql = "SELECT * FROM users WHERE name = '" + name + "'"
```

如果用户乖乖输入 `alice`，语句是查 alice；如果输入 `alice' OR '1'='1`，拼出来的句子就变成了「查 alice，或者 1 等于 1」——1 永远等于 1，于是整张用户表都被查出来了。**和主线的对应**：这行 `+` 拼接就是 Web 版的 `strcpy`——它不检查「输入里有没有不该出现的字符」，就像 strcpy 不检查长度。

常出问题的位置：登录、搜索、排序（`ORDER BY`）、分页（`LIMIT`）、筛选、导出、报表、老版本接口，以及 ORM〔T: orm〕里的「原生 SQL 逃生口」（`Raw()`、`whereRaw()`、`createNativeQuery()`）。

**分类（按能不能看到结果）**：

| 类型 | 白话 | 判断信号 |
|---|---|---|
| 联合查询〔T: union-injection〕 | 直接把数据库里的数据显示在页面上 | 页面出现本不该出现的值 |
| 报错注入（故意让数据库报错，把数据藏在报错信息里带出来） | 靠报错文本回显数据 | 构造非法表达式后返回数据库报错文本 |
| 布尔盲注〔T: blind-injection〕 | 页面只会「正常 / 异常」，靠真假两种状态一点点猜 | `and 1=1` 与 `and 1=2` 返回不同 |
| 时间盲注（连正常异常都没差别，靠「慢不慢」猜） | 让条件为真时故意延迟 | 条件为真时响应明显变慢几百毫秒 |
| 堆叠注入（一次执行多条 SQL，用分号隔开） | 取决于数据库和驱动是否支持 | 能否用 `;` 追加第二条语句 |
| 二次注入（坏数据先存起来，取出时才炸） | 输入时被转义、取出时忘了检查 | 改完资料、再访问另一个页面才异常 |
| 宽字节注入（某种编码下反斜杠被「吃掉」） | 转义符失效导致引号仍能闭合 | 单引号明明转义了仍能闭合 |

> 按 §5.3 术语网络规则：联合查询、盲注是全库高频词，挂 TermButton（点开还有「相关术语」）；报错注入、时间盲注、堆叠注入、二次注入、宽字节注入是本条低频词，**只在首次出现给 inline 白话**（上表括号里），不再逐个做浮层。

**典型特征（怎么发现）**：
- 输入一个单引号 `'` 或双引号 `"`，页面报错或 500。
- 输入 `' and '1'='1` 与 `' and '1'='2`，两次结果不一样。
- 数字型参数做加减：`id=2-1` 如果返回的是 id=1 的内容，说明输入被当算术表达式执行了。
- 同样的请求，真假条件下耗时差几百毫秒以上（时间盲注）。

**危害**：拖库（用户表、订单、密钥）；篡改与删除数据；条件合适时写文件拿到 WebShell〔T: webshell〕，甚至通过数据库扩展执行系统命令；再借数据库权限往内网横向。

**挖掘与验证思路**（顺序即安全练习的顺序）：
1. **列出所有输入点**：不止表单，还有 Cookie、请求头、JSON 字段、文件路径参数、批量接口的数组元素。
2. **先做无害探测**：`'`、`"`、`)`、`\`，看是否报错或行为变化。到这一步就停也已经有结论。
3. **确定是数字型还是字符型**：用 `and 1=1` / `and 1=2` 看差异，判断闭合方式。
4. **确定能不能回显**：能回显就看能不能并查出数据；不能回显就看真假差异；连差异都没有再看时间差。
5. **确认权限边界**：只读是谁、能不能跨库、能不能读写文件——这决定危害评级，不要一上来就往最坏处做。
6. **别漏掉「看起来安全」的地方**：ORM 项目里的原生 SQL、报表模块、后台管理、旧版本接口。

**防护**（四层，由根治到兜底）：
- **根治**：全部改成参数化查询/预编译（`PreparedStatement`、`?` 占位符、ORM 参数绑定）。数据就待在数据位，拼接的路被堵死。
- **加固**：表名、列名、排序方向这类「没法参数化」的位置，用白名单枚举；Web 应用用独立的低权限数据库账号；关掉详细报错（统一错误页）；收紧数据库扩展与文件写入权限。
- **兜底**：WAF 规则 + 参数长度/类型强校验。只做兜底。

**易错点**：
- 只过滤 `union select`、`sleep` 这几个词——注释、编码、大小写变体都能绕开。
- 以为用了 ORM 就安全：`whereRaw` / `orderBy(request('sort'))` 一样会注入。
- 只测 GET/POST，不测请求头和 JSON。
- 以为预编译什么都能保护——它只保护「值」，保护不了「表名、列名」这类标识符。

**微自测（演示样例，3 题：认出它 / 怎么防 / 易错点）**

*题 1 · 认出它*｜材料：某搜索接口把关键词直接拼进 `WHERE name LIKE '%关键词%'`。输入 `x' OR '1'='1` 后，页面列出了全部用户。
问：最贴切的解释是？
- A. 输入里的引号提前结束了字符串，后面的 `OR` 被数据库当成命令 → ✔ 正确。解释：原本用户输入只是「要搜的词」，引号让它跳出了数据位，`OR '1'='1'` 让条件恒真。这正是「数据被当成指令」。
- B. 数据库坏了，返回了缓存 → ✘ 错误。返回全部用户是条件被改写成恒真的典型表现，不是缓存问题。
- C. 前端把搜索框内容显示出来了 → ✘ 错误。前端显示不等于数据库返回；这里是后端查询被改变。
- D. 因为没做输入长度限制 → ✘ 错误。长度限制不是根治手段；即使限制长度，引号仍能闭合语句。

*题 2 · 怎么防*｜材料：同一个搜索接口，开发给出四种改法：① 用参数化查询/预编译绑定关键词；② 把 `'` 和 `OR` 过滤掉；③ 给关键词限制 20 个字符；④ 加一层 WAF。
问：哪个是根治？
- A. ① 用参数化查询，让关键词永远待在数据位 → ✔ 正确。解释：数据与语句分离，输入再含引号也只是「要搜的字符串」，拼不出新条件——这是根治。
- B. ② 过滤 `'` 和 `OR` → ✘ 错误。有编码、注释、大小写等多种绕过方式，黑名单追不完，只能算减少攻击面。
- C. ③ 限制长度 → ✘ 错误。短 payload 也能闭合语句（如 `'--`），长度挡不住注入。
- D. ④ 加 WAF → ✘ 错误。WAF 是兜底，不能替代正确的代码写法；规则不全时会被绕。

*题 3 · 易错点*｜材料：开发说「我们用了 ORM，所以不会有 SQL 注入」。代码中有一行 `orderBy(request('sort'))`。
问：这句话对吗？
- A. 不对，排序字段拼进了语句，需要白名单枚举 → ✔ 正确。解释：ORM 能绑定「值」，但 `order by` 后面是「标识符」（列名），多数 ORM 不对它做参数绑定，必须用白名单。
- B. 对，ORM 会自动转义所有输入 → ✘ 错误。这是最常见的误解，ORM 的原生 SQL 与动态排序/筛选是注入高发区。
- C. 对，因为 `request('sort')` 来自服务器 → ✘ 错误。它来自请求参数，是用户输入。
- D. 无法判断，要看数据库版本 → ✘ 错误。不看数据库也能判断：动态标识符拼接本身就是风险点。

### 8.2 NoSQL 注入　`危险度 ★★★★☆`　`本站难度：中`

**难度判定**：三问法命中 2 项——需要先理解「查询条件可以是对象而不只是字符串」，以及 JSON 请求体的结构；验证时要构造对象结构。

**一句话**：一些非关系型数据库〔T: nosql〕（如 MongoDB）的查询条件是「对象」而不是一句话。如果程序把用户输入原样塞进查询对象，攻击者就能塞进「操作符」〔T: query-operator〕改变查询含义——比如让「密码等于 x」变成「密码不等于空」，直接登录成功。

**成因与位置**：
主线里的 strcpy 是「不检查长度」；这里的等价物是「不检查类型」。程序期望收到一个字符串，结果收到一个对象，还照样把它交给数据库：

```json
// 演示样例：期望 password 是字符串，实际收到对象
{"username": "admin", "password": {"$ne": ""}}
```

`$ne` 的意思是「不等于」——于是查询变成「用户名是 admin，且密码不等于空字符串」，任何非空密码都通过了。偷懒的写法还有把整个请求体直接丢进 `find(req.body)`，以及在 `$where` 里拼接 JavaScript。

**分类（按利用方式）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 操作符注入 | 把字符串换成 `{"$ne": ""}` 这类对象 | 登录绕过、返回条数异常 |
| 正则盲注 | 用 `$regex` 逐字符试探 | 响应随前缀匹配变化 |
| JS 执行 | `$where` / `mapReduce` 里拼接脚本 | 明显延迟或异常行为 |
| 参数污染 | 同时传 `a=x` 和 `a[$ne]=1`，看后端怎么解析 | 类型转换后的意外结果 |

**典型特征（怎么发现）**：
- 接口接收 JSON，把字符串值换成 `{"$ne": null}` 后行为改变。
- URL 参数写成 `username[$ne]=1` 后返回异常或直接登录成功（某些语言会把这种写法解析成数组/对象）。
- 输入 `$where` 类表达式后出现明显延迟。

**危害**：认证绕过、全量数据读取、服务端脚本执行（在支持 `$where` 的旧配置里）、正则灾难性回溯导致的拒绝服务。

**挖掘与验证思路**：
1. 看接口是否接收 JSON，尝试把字符串换成对象 `{"$ne": null}`。
2. 试常见操作符：`$ne`、`$gt`、`$regex`、`$in`、`$exists`。
3. 用 `{"$regex":"^a"}` 观察响应差异，逐字符猜解。
4. 同时传 `username=x&username[$ne]=1`，看后端类型转换结果。
5. 注意 `Content-Type: application/json` 与表单参数的解析差异，两条路都要看。

**防护**：
- **根治**：强制类型校验——期望字符串就必须是字符串，收到对象/数组直接拒绝。
- **加固**：用数据库驱动的查询构造器，禁止把整个请求体直接丢进 `find()`；关闭服务端 JS 执行（MongoDB 关闭 `$where`、`mapReduce` 的脚本能力）；按库授权数据库账号。
- **兜底**：WAF / 网关层限制参数结构。

**易错点**：
- 只想到 SQL 注入而忽略 JSON 接口。
- 忽略表单参数与 JSON 的解析差异；`a[$ne]=1` 这种写法在部分框架里会被自动转成对象。
- 以为 NoSQL「没有 SQL 语句」就没注入——注入的本质是「数据被当成查询结构」，与有无 SQL 无关。

**附加自测（演示样例，2 题）**｜中/高档第一期的主体是案例演示+指导；这 2 题是可选巩固，**不套用低档「3 题」规则**（R6 只针对低难度）。

*题 1*｜材料：某 JSON 登录接口，正常请求是 `{"user":"admin","pass":"123456"}`。测试者把 `pass` 改成 `{"$ne":""}` 后登录成功。
问：发生了什么？
- A. 查询里的「密码等于」被改成了「密码不等于空」，条件被攻击者改写 → ✔ 正确。解释：本该是字符串的字段变成了操作符对象，查询结构被改写了——这就是 NoSQL 注入。
- B. 数据库把密码自动改成了 123456 → ✘ 错误。数据库没有改数据，只是查询条件被换了含义。
- C. 这是 SQL 注入的一种 → ✘ 错误。攻击对象是 NoSQL 查询对象，不是 SQL 语句；但两者的本质（数据被当成指令/结构）相同。
- D. 因为密码太短 → ✘ 错误。密码长度与这次条件改写无关。

*题 2*｜材料：开发说「我们不用 SQL，所以不需要做类型校验」。
问：这句话的问题在哪？
- A. 注入不挑语法，只要输入能改变查询结构就需要类型校验 → ✔ 正确。解释：期望字符串却接受对象，等于把「查询结构」的控制权交给了用户。
- B. 没问题，NoSQL 天生安全 → ✘ 错误。NoSQL 同样有查询语法，同样能被注入。
- C. 应该改用 SQL → ✘ 错误。换数据库不能替代类型校验。
- D. 只要把密码加密就行 → ✘ 错误。加密不改变「输入被当成操作符」这个问题。

**▶ 形态 B 附加层（第二期：案例演示 + 指导 + 交互闯关；第一期只交案例演示+指导）**

**案例演示**｜演示样例：某登录接口接收 `{"user":"admin","pass":"123456"}`。把 `pass` 换成 `{"$ne":""}` 后返回登录成功。界面只显示「登录成功/失败」，没有回显查询内容。

**指导模式**（默认开，可关）：
- **guideWhy**：盯住「期望字符串的位置收到了对象」。NoSQL 的注入点不是引号，而是**类型**——这是它和 8.1 SQL 注入最大的不同。

| 2 下探针 | 把 pass 改成 `{"$ne":""}` | 「这一步在验证什么？」 | 验证输入是否被当成查询操作符 | 不是测密码强度；不是测长度；不是测编码 |
| 3 得结论 | 返回从「失败」变「成功」 | 「结论是？」 | 类型校验缺失导致查询结构被改写 | 不是数据库损坏；不是缓存；不是前端 bug |

**verdict**：认出「类型即注入点」→ 通关；仍在找引号 → 提示回看 guideWhy。

### 8.3 命令注入（OS Command Injection）　`危险度 ★★★★★`　`本站难度：中`

**难度判定**：三问法命中 2 项——概念一句「把输入拼进系统命令」虽好懂，但**无回显时要理解延时/外带两种验证机制**，还要知道 shell 与命令分隔符，属于「要理解一个机制 + >2 个前置概念」，定中；危害极高，是「高危险、中难度」的例子。按决策 2 归入交互闯关形态。

**一句话**：程序把用户输入拼进一条系统命令，攻击者用命令分隔符（如 `;`）接上自己的命令——服务器执行的第一条是程序安排的，第二条就是攻击者写的。

**成因与位置**：
主线 L3 讲过「给复制函数加一条刻度线」。这里的问题不是缺刻度线，而是**根本不该让用户输入出现在命令行里**：

```python
# 演示样例：危险写法
os.system("ping -c 1 " + host)
```

用户输入 `127.0.0.1; id`，实际执行的是「先 ping，再 id」。高发功能：图片处理、视频转码、压缩解压、域名/IP 查询、二维码生成、PDF 生成、备份脚本——凡是「程序去叫了另一个外部程序」的地方都要看。

**分类（按能不能看到输出）**：

| 类型 | 白话 | 信号 |
|---|---|---|
| 有回显 | 命令输出直接显示在页面上 | 输入 `; id` 后页面出现用户信息 |
| 无回显 - 延时 | 看不到输出，但能让它「慢几秒」 | `; sleep 5` 后响应明显变慢 |
| 无回显 - 外带 | 让服务器主动访问攻击者能看到的地址 | DNSLog / HTTP 回连记录到请求 |

**典型特征（怎么发现）**：
- 参数值里出现 `;`、`|`、`&`、反引号、`$()`、`%0a`（换行）后行为变化。
- 输入 `127.0.0.1; id` 出现命令输出（有回显时）。
- 无回显时，`; ping -c 3 你的域名`（外带）或 `; sleep 5`（延时）有可观察变化。

**危害**：服务器完全沦陷——读配置、横向移动、留后门。通常直接评为严重。

**挖掘与验证思路**：
1. 找出所有「调用了外部程序」的功能：格式转换、二维码、打包、域名查询、日志分析。
2. 判断输入是否经过 shell：`;` 与 `|` 哪个生效（`|` 生效通常说明经过 shell）。
3. 无回显时用「延时 + 外带」双路验证，避免误判。
4. 只在授权范围内验证；教学演示用无害的 `sleep` 或回连标记，不做破坏性命令。

**防护**：
- **根治**：**不调用 shell**——用参数数组形式（`ProcessBuilder(["convert", in, out])`、`subprocess.run([...], shell=False)`）。命令与参数分开传递，分隔符就只是普通字符。
- **加固**：必须拼接时，参数用白名单（文件名只允许 `[a-zA-Z0-9._-]`）、路径规范化、禁止 `..`；尽量用安全的库替代外部命令（图像处理用库，不叫 `convert`）；运行账号降权（容器内非 root）。
- **兜底**：WAF / 命令审计。**只做黑名单过滤（`;|&`）几乎必然被绕过**，不可当主防护。

**易错点**：
- 只测表单不测文件名。
- 只测常见分隔符，忘了换行 `%0a`。
- 以为「参数被引号包住了」就安全——反引号与 `$()` 仍能突破。

**附加自测（演示样例，2 题）**｜中/高档第一期的主体是案例演示+指导；这 2 题是可选巩固，**不套用低档「3 题」规则**（R6 只针对低难度）。

*题 1*｜材料：某「网络测速」功能把用户输入填进 `ping -c 1 <输入>`。输入 `127.0.0.1; sleep 5` 后页面 5 秒才返回。
问：这说明什么？
- A. 输入里的分号结束了第一条命令，`sleep 5` 被服务器执行了 → ✔ 正确。解释：这是无回显场景最经典的延时验证法——看不到输出，但能观察到时间差。
- B. 网络真的很慢 → ✘ 错误。恰好 5 秒且只在输入带 `sleep 5` 时发生，不是网络抖动。
- C. 服务器做了限流 → ✘ 错误。限流不会精确对应输入的数字。
- D. 这只是命令写法问题，没有安全影响 → ✘ 错误。能追加任意命令就等于拿到了服务器执行权。

*题 2*｜材料：开发说「我把 `;`、`|`、`&` 都过滤掉了，安全了」。
问：为什么这不是根治？
- A. 还有换行、变量展开、反引号等多种方式，黑名单堵不完；根治是不调用 shell → ✔ 正确。解释：黑名单永远在追新写法；参数数组形式让分隔符失去意义，才叫根治。
- B. 过滤这三个已经够了 → ✘ 错误。换行 `%0a`、`$()`、反引号、`${IFS}` 等都能绕。
- C. 只要再加过滤 `sleep` 就行 → ✘ 错误。这是无限打补丁，不是根治。
- D. 应该改用 HTTPS → ✘ 错误。HTTPS 保护传输，不阻止服务端把输入拼进命令。

**▶ 形态 B 附加层（第二期：案例演示 + 指导 + 交互闯关；第一期只交案例演示+指导）**

> 分期说明：以下「案例演示」与「指导模式」属**第一期**交付；「交互闯关」表属**第二期**样板（套 TPL-INJECT），第一期不实现。

**案例演示**｜演示样例：某「网络测速」页，输入 host 执行 `ping -c 1 <host>`。输入 `127.0.0.1; sleep 5` 后页面卡 5 秒才回；输入 `127.0.0.1; id` 页面无输出。材料给「测速表单 + 两次请求的耗时截图」。

**指导模式**（默认开）：
- **guideWhy**：先看「输入里多出来的符号有没有生效」。`;` 生效说明输入进了命令行，这是命令注入的第一信号。
- **guideHow**：有回显就试 `; id` 看输出；没回显就走两条路——`; sleep 5`（看时间差）或 `; ping 你的域名`（看外带记录）。两条都只是确认，不做破坏。

| 1 找信号 | host 输入 `127.0.0.1; id`，页面无新内容 | 「该下什么探针？」 | 无回显→试延时或外带 | 不是多试几个引号；不是看源码颜色；不是刷新页面 |
| 2 读结果 | `; sleep 5` 的耗时从 0.2s 变 5.1s | 「说明什么？」 | 分号结束首条命令，第二条被执行 | 不是网络慢（只在带 sleep 时发生）；不是限流；不是缓存 |
| 3 选根治 | 开发列举四种改法 | 「哪个是根治？」 | 参数数组、shell=False | 过滤 `;|&`（可被 `%0a` 绕）；过滤 `sleep`（无限打补丁）；改用 HTTPS（无关） |

### 8.4 代码 / 表达式注入　`危险度 ★★★★★`　`本站难度：高`

**难度判定**：三问法命中 3 项——要理解「表达式引擎会求值」这一底层机制、要分辨 SpEL/OGNL/EL 等多套语法（>2 个前置概念）、还要自己构造表达式验证；且直接 RCE，是「高危险 + 高难度」。

**一句话**：程序把用户输入当成「一段可以计算的表达式」交给解释器执行。你输入 `7*7`，它真去算，返回 `49`——既然能算算术，也就能调用更危险的东西。

**成因与位置**：
主线 L2 说「先找危险调用」。这里的危险调用是「表达式求值函数」：

```python
# 演示样例：危险写法
result = eval(user_input)          # 把用户输入当代码算
```

Java 生态里更隐蔽：Spring 的 SpEL（`${...}` / `#{...}`）、Struts2 的 OGNL、JSP EL、脚本引擎。高发功能是「让用户输入公式」的地方——搜索条件、公式字段、报表自定义列、规则配置、低代码平台。**和主线的对应**：`eval` 就是 Web 版的「把输入当指令执行」，比 strcpy 更直接。

**分类（按表达式语言）**：

| 语言 / 框架 | 探测写法 | 信号 |
|---|---|---|
| 通用 eval | `7*7` | 返回 `49` |
| Java SpEL | `${7*7}` / `#{7*7}` | 返回 `49`；报错含 `SpelEvaluationException` |
| Struts2 OGNL | `%{7*7}` | 返回 `49`；报错含 `OgnlException` |
| JSP EL / Thymeleaf | `${7*7}` | 返回 `49` |

**典型特征（怎么发现）**：
- 输入 `7*7`、`${7*7}`、`#{7*7}` 返回 `49`。
- 报错里出现 SpEL/OGNL 等引擎名为强信号。
- 「可写公式/表达式」的功能一律优先看。

**危害**：直接远程代码执行（RCE），等同拿到服务器。

**挖掘与验证思路**：
1. 列出所有「用户能写表达式」的输入点。
2. 先用纯算术 `7*7` 探测是否被求值（无害）。
3. 确认引擎与沙箱后，再尝试读系统属性/环境变量，最后才谈命令执行——**务必在授权范围内**。
4. 关注版本：老框架有公开 CVE。

**防护**：
- **根治**：不把用户输入交给表达式引擎；确需动态能力时用**受限 DSL**〔T: dsl〕（只允许枚举字段与运算）。
- **加固**：升级框架、关闭危险动态特性（如 Struts2 静态方法访问）、沙箱隔离 + 超时限制。
- **兜底**：WAF 规则，只做兜底。

**易错点**：以为「前端没入口」就安全——后端接口照样能调；忽略管理后台的表达式配置功能。

**▶ 形态 B 附加层（第二期：案例演示 + 指导 + 交互闯关；第一期只交案例演示+指导）**

> 分期说明：以下「案例演示」与「指导模式」属**第一期**交付；「交互闯关」表属**第二期**样板（套 TPL-INJECT），第一期不实现。

**案例演示**｜演示样例：某报表「自定义计算列」允许输入公式，输入 `${7*7}` 页面显示 49，输入常规文本原样显示。

**指导模式**：
- **guideWhy**：返回 49 说明输入被「算了」而不是「显示」了——这是表达式注入的指纹。
- **guideHow**：先算术探测确认被求值 → 认引擎（看报错关键字）→ 再判断有无沙箱。只在授权环境推进到读属性一步。

**交互闯关（3 stage）**：
| Stage | 材料（tool=observe/code） | 提问 | 正确项 | 错误项（全给） |
|---|---|---|---|---|
| 1 认指纹 | 输入 `${7*7}` 返回 49 | 「说明什么？」 | 输入被表达式引擎求值了 | 不是前端计算；不是缓存；不是 XSS |
| 2 认引擎 | 报错含 `SpelEvaluationException` | 「是什么引擎？」 | Java SpEL | 不是 OGNL；不是 JS；不是 SQL |
| 3 选根治 | 四个改法 | 「哪个根治？」 | 受限 DSL / 不交给表达式引擎 | 过滤 `$` 和 `#`（可绕）；升级但不关特性；只加 WAF |

**verdict**：能区分「被求值」与「被显示」、选对根治 → 通关。

### 8.5 服务端模板注入 SSTI　`危险度 ★★★★★`　`本站难度：高`　【形态 B 完整示例】

> 这一条是**中/高难度交互形态的完整样板**。低难度形态的完整样板见 8.8 CRLF 注入。请对比两者，一眼看出区别。

**难度判定**：三问法命中 3 项——要理解「模板引擎会渲染表达式」这一机制、要分辨 Jinja2/Twig/Freemarker 等多套语法（>2 前置概念）、要自己构造 `{{7*7}}` 之类的载荷验证；可达 RCE，高危险 + 高难度。

**一句话**：用户输入被当成「模板内容」而不是「模板变量」来渲染，于是模板引擎的表达式被执行——输入 `{{7*7}}` 返回 `49` 就是信号，继续深入可读文件、拿环境变量，最终执行代码。

**成因与位置**：
正常写法是「模板固定，数据作变量填进去」。偷懒的写法是把用户输入直接当模板渲染：

```python
# 演示样例：危险写法（Flask + Jinja2）
return render_template_string("你好 " + user_input)   # 用户输入成了模板的一部分
```

若写成 `render_template("hello.html", name=user_input)`，用户输入只是变量，会被转义显示，安全。高发位置：把用户名/昵称拼进模板再渲染、邮件/短信/PDF 模板、页面装修、主题自定义。

**分类（按模板引擎，即「用哪套语法探测」）**：

| 引擎 | 探测载荷 | 返回 49 即命中 |
|---|---|---|
| Jinja2 / Twig | `{{7*7}}` | 是 |
| Freemarker | `${7*7}` | 是 |
| ERB / EJS | `<%= 7*7 %>` | 是 |
| Velocity / Smarty / Handlebars | 各自语法 | 按引擎变体 |

**典型特征（怎么发现）**：
- 输入 `{{7*7}}` 返回 `49`；输入 `<b>x</b>` 若被原样渲染成加粗而非转义显示，也是信号。
- 报错暴露模板引擎名。
- 「模板名可控」与「模板内容可控」是两种漏洞，**后者更严重**。

**危害**：读服务器文件、环境变量、密钥，最终远程代码执行（RCE）。

**挖掘与验证思路**：
1. 先确认输入是「被渲染」还是「被转义」：传 `{{7*7}}` 与 `<b>x</b>` 看输出。
2. 用不同语法定位引擎（看哪个载荷生效、报错叫什么）。
3. 定位后按该引擎公开路径验证：读配置 → 找对象链 → 命令执行（**只在授权环境**）。
4. 区分「模板名可控」与「模板内容可控」，后者优先。

**防护**：
- **根治**：模板只允许开发者控制，用户数据只能作为变量传入并自动转义。
- **加固**：用沙箱模式（Jinja2 `SandboxedEnvironment`）禁用危险全局对象；模板管理功能加权限与审计；禁止用户自定义模板语法。
- **兜底**：WAF，只做兜底。

**易错点**：
- 以为「模板注入 = XSS」——危害量级完全不同（XSS 在浏览器，SSTI 在服务器）。
- 只测 `{{7*7}}`，不测 `${}`、`<%= %>` 等其他语法。

### 8.6 LDAP / XPath / XQuery 注入　`危险度 ★★★☆☆`　`本站难度：中`

**难度判定**：三问法命中 2 项——要理解「目录查询/树查询」这套新机制，要构造 `*)(uid=*` 之类载荷验证；但语法单一、变体少，定中。

**一句话**：程序把用户输入拼进 LDAP 过滤器或 XPath 查询，改变了查询逻辑——像把「找张三」的条件改成了「找所有人」，从而绕过登录或读到本不该看的目录数据。

**成因与位置**：
和 8.1 同源，只是「被拼进去的语言」从 SQL 换成了 LDAP/XPath：

```
# 演示样例：危险写法（LDAP 过滤器）
filter = "(&(uid=" + user + ")(userPassword=" + pwd + "))"
```
高发位置：企业统一登录（AD/LDAP）、组织架构查询、XML 数据查询接口。

**分类**：LDAP 注入（拼进过滤器）、XPath 注入（拼进 XML 查询）、XQuery 注入（拼进 XQuery 表达式）。

**典型特征（怎么发现）**：
- 登录框输入 `*)(uid=*))(|(uid=*` 类载荷可绕过（LDAP）。
- XPath 输入 `' or '1'='1` 返回全部节点。
- 报错泄露过滤器结构。

**危害**：认证绕过、目录信息泄露（员工账号、手机号、组织结构）、越权读取 XML 数据。

**挖掘与验证思路**：
1. 找出基于 AD/LDAP 的登录与查询功能。
2. 输入 `*`、`)`、`(` 观察行为差异。
3. 用真假条件差异判断过滤条件是否被改写。

**防护**：
- **根治**：LDAP 用官方转义函数（RFC 4515〔T: rfc4515〕，转义 `\*()\0`）；XPath 用参数化 API（变量绑定）。
- **加固**：限制查询返回字段与条数。
- **兜底**：WAF。

**易错点**：只转义 `(` `)` 漏掉 `*` 和 `\`；把「密码错误」和「用户不存在」返回不同信息，造成账号枚举。

**▶ 形态 B 附加层（第二期：案例演示 + 指导 + 交互闯关；第一期只交案例演示+指导）**

> 分期说明：以下「案例演示」与「指导模式」属**第一期**交付；「交互闯关」表属**第二期**样板（套 TPL-INJECT），第一期不实现。

**案例演示**｜演示样例：某企业内网登录页，输入用户名 `admin`、任意密码被拒；输入用户名 `*)(uid=*))(|(uid=*`、任意密码后登录成功并跳到首页。

- **guideHow**：先正常登录看失败 → 输入带 `*` `)` 的探测串 → 看是否绕过 → 确认后用转义函数修。

|---|---|---|---|---|
| 1 认信号 | 输入含 `*)(` 后登录成功 | 「发生了什么？」 | 查询条件被改写成「匹配所有人」 | 不是密码对了；不是缓存；不是前端 bug |
| 2 选语言 | 目标是企业统一登录 | 「该用什么转义？」 | LDAP 的 RFC 4515 转义 | 用 SQL 参数化（语言不对）；过滤空格（无关）；换 HTTPS（无关） |
| 3 选根治 | 四种改法 | 「哪个根治？」 | LDAP 转义函数 / XPath 变量绑定 | 只转义 `()`（漏 `*\`）；只限条数（不防绕过）；只加 WAF |

**verdict**：认出「查询结构被改写」并选对转义 → 通关。

〔本章术语锚点〕`ldap`、`xpath`、`rfc4515`、`directory-query`

### 8.7 ORM / HQL 注入　`危险度 ★★★★☆`　`本站难度：低`

**难度判定**：三问法命中 0~1 项——它就是 8.1 SQL 注入换了个马甲（拼接点从原生 SQL 换成 ORM 的字符串接口），读者已懂 8.1，这里只多「哪些接口会拼接」一个记忆点。

**一句话**：ORM〔T: orm〕框架本该帮你把数据和语句分开，但它的「字符串查询接口」被拿来拼接用户输入，等于绕过了 ORM 的保护——本质还是 8.1 的 SQL 注入。

**成因与位置**：
正常写法 `where(name=:n)` 用绑定参数，安全；危险写法把用户输入拼进字符串：

```java
// 演示样例：危险写法
createQuery("from User where name='" + n + "'");   // HQL 拼接
```

高发位置：`whereRaw`、`nativeQuery`、`createQuery`、`order by` 动态字段、`like` 拼接。

**典型特征（怎么发现）**：
- 代码里搜 `Raw`、`nativeQuery`、`createQuery`、字符串 `+`。
- 排序/筛选/导出功能的字段参数可注入。

**危害**：与 SQL 注入同级，可拖库；HQL 还可能借实体属性访问到其他表。

**防护**：统一用绑定参数（`:name` / `?`）；动态标识符（表名/列名/排序方向）用白名单；代码评审加「禁止字符串拼接查询」静态检查。

**易错点**：认为「用了 ORM 就不会注入」——这是最普遍的误解，8.1 题 2 已经考过。

**微自测（演示样例，3 题：认出它 / 怎么防 / 易错点；形态 A：知识卡 + 自测，不闯关）**

*题 1 · 认出它*｜材料：某接口 `orderBy(request('sort'))`，`sort` 来自用户输入，`?sort=name` 正常，改成 `?sort=(select 1)` 后报错。
问：这说明什么？
- A. 排序参数被拼进 SQL 语句，用户输入被当成结构解析了 → ✔ 正确。解释：`order by` 后面是可控的，输入能改变查询结构，这就是注入信号。
- B. 数据库不支持排序 → ✘ 错误。正常排序能用，只是特殊输入触发了异常。
- C. 这是前端校验问题 → ✘ 错误。报错来自后端查询构造。
- D. 参数长度不够 → ✘ 错误。与长度无关。

*题 2 · 怎么防*｜材料：同一个动态排序接口，开发给出四种改法：① 用白名单枚举允许的排序列（name/age/id）；② 过滤 `(` 和 `select`；③ 把 sort 转义后拼接；④ 只加 WAF。
问：哪个是根治？
- A. ① 用白名单，只允许从枚举的列名里选 → ✔ 正确。解释：标识符（列名）没法用绑定参数，白名单是唯一根治手段。
- B. ② 过滤关键字 → ✘ 错误。黑名单可绕，且合法列名里也可能含被过滤字符。
- C. ③ 转义后拼接 → ✘ 错误。转义解决的是「值」的问题，标识符位置仍被拼接。
- D. ④ 加 WAF → ✘ 错误。WAF 是兜底，不替代白名单。

*题 3 · 易错点*｜材料：开发说「我们换 HQL 了，不会 SQL 注入」。
问：对吗？
- A. 不对，HQL 字符串拼接同样可注入 → ✔ 正确。解释：本质都是「输入被当查询结构」。
- B. 对，HQL 与 SQL 不同 → ✘ 错误。语法不同但拼接风险相同。
- C. 对，只要用了 ORM → ✘ 错误。ORM 的原生接口（createQuery/whereRaw）照样拼接。
- D. 要看数据库版本 → ✘ 错误。不看版本也能判断：动态拼接本身就是风险点。

〔本章术语锚点〕`orm`（复用）、`hql`、`query-builder`、`identifier-whitelist`

### 8.8 CRLF 注入　`危险度 ★★★☆☆`　`本站难度：低`　【形态 A 完整示例】

> 这一条是**低难度「知识卡 + 自测」的完整样板**。高难度交互形态的完整样板见 8.5 SSTI 注入。请对比：本条**没有**案例演示、指导模式、闯关 stages，只有知识卡 + 2 道题。

**难度判定**：三问法命中 0 项——单一输入点（一个参数）、一个生活例子（「在句子里偷偷按了回车换行」）就能讲明白、无前置知识。低难度，只用知识卡 + 自测。

**一句话**：输入里的「回车换行」被程序写进了本不该换行的地方——比如 HTTP 响应头或日志——于是凭空多出一行，攻击者能塞进一个假的响应头或假日志。

**成因与位置**：
回车换行在网址里写成 `%0d%0a`。程序若把用户输入原样拼进响应头，攻击者就能「另起一行」：

```text
# 演示样例：危险写法（重定向参数）
Location: /go?url=<用户输入>
# 输入：/go?url=x%0d%0aSet-Cookie:admin=1
# 结果：响应里真的多出一行 Set-Cookie:admin=1
```
高发位置：重定向 URL 参数、写入响应头/邮件头/日志的字段。

**分类（按塞进哪里）**：
| 类型 | 白话 | 后果 |
|---|---|---|
| 响应拆分 | 塞进 HTTP 响应头 | 会话固定、XSS、缓存投毒 |
| 邮件头注入 | 塞进邮件头 | 伪造发件人、群发钓鱼 |
| 日志伪造 | 塞进日志 | 伪造整行记录、掩盖攻击痕迹 |

**典型特征（怎么发现）**：
- 输入 `%0d%0aSet-Cookie:test=1`，响应里出现新的 `Set-Cookie` 头。
- 重定向参数可注入 `Location`。
- 日志里出现格式规整、明显非程序生成的整行记录。

**危害**：会话固定、缓存投毒、借拆分响应体造成 XSS、钓鱼邮件伪造、日志掩盖攻击痕迹。

**挖掘与验证思路**：
1. 找所有「用户输入会被写进头/日志」的位置。
2. 在参数后加 `%0d%0aX-Test:1`，看响应是否多出 `X-Test` 头。
3. 确认后按「塞进哪类」评估危害。

**防护**：
- **根治**：写入响应头/邮件头的值做严格白名单（只允许 URL 安全字符）；用框架提供的安全重定向 API，不手拼 `Location`。
- **加固**：框架层统一拒绝含 `\r`、`\n` 的输入。
- **兜底**：网关规则。

**易错点**：只过滤 `\n` 不过滤 `\r`；不同语言/中间件对换行处理不一致（`%0d`、`%0a`、`%0a` 的编码变体）。

**微自测（演示样例，3 题：认出它 / 怎么防 / 易错点）**

*题 1 · 认出它*｜材料：输入 `?url=x%0d%0aSet-Cookie:admin=1` 后，响应里真的多了一行 `Set-Cookie:admin=1`。
问：最贴切的解释是？
- A. `%0d%0a` 是回车换行，让攻击者另起一行塞进了假响应头 → ✔ 正确。解释：本该是一行头的值被当成「新的一行」，这就是响应拆分。
- B. 服务器自动给用户发了管理员 Cookie → ✘ 错误。是攻击者拼进去的，不是服务器本意。
- C. 这是 SQL 注入 → ✘ 错误。没有碰数据库。
- D. 因为没用 HTTPS → ✘ 错误。HTTPS 不阻止把换行写进头。

*题 2 · 怎么防*｜材料：某重定向功能要把用户输入拼进 `Location` 头，开发给出四种改法：① 用框架的安全重定向 API、对写入头的值做严格白名单；② 过滤 `%0d%0a` 这几个字符；③ 把参数 URL 编码一次；④ 只加 WAF。
问：哪个是根治？
- A. ① 用安全 API + 白名单，只允许 URL 安全字符 → ✔ 正确。解释：输入永远进不了「头结构」的位置，另起一行无从谈起——根治。
- B. ② 过滤 `%0d%0a` → ✘ 错误。有 `%0d`、`%0a`、双重编码等多种变体，黑名单追不完。
- C. ③ URL 编码一次 → ✘ 错误。编码可能被框架解码还原，不能作为唯一防线。
- D. ④ 加 WAF → ✘ 错误。WAF 是兜底。

*题 3 · 易错点*｜材料：开发说「我过滤了 `\n`，安全了」。
问：为什么不够？
- A. 还要过滤 `\r`，且编码变体多；根治是白名单 + 安全重定向 API → ✔ 正确。解释：HTTP 头以 `\r\n` 分隔，只挡其中一个不够；且中间件解析差异多，白名单才稳。
- B. 过滤 `\n` 就够了 → ✘ 错误。`\r` 也能参与拆分。
- C. 改用 POST → ✘ 错误。换行照样能写进头。
- D. 加长响应头 → ✘ 错误。无关。

**本条到此结束——没有闯关 stages。** 低难度条目「读知识卡 + 做 3 题」即完成学习，这是与中/高难度形态的关键区别。

〔本章术语锚点〕`crlf`、`http-header`、`response-splitting`、`whitelist`（复用）

### 8.9 日志注入 / 终端转义注入　`危险度 ★★☆☆☆`　`本站难度：低`

**难度判定**：三问法命中 0 项——单一输入点（写进日志的字段）、一个例子（「在日志里藏一段控制码，管理员查看时骗过他的眼睛」）讲明白、无前置知识。低难度，知识卡 + 自测。

**一句话**：恶意输入被写进日志，管理员在终端查看日志时，里面的 ANSI 控制码被终端执行——能改窗口标题、把某行隐藏、或伪造出一条看似正常的日志，干扰审计。

**成因与位置**：
日志系统若把用户输入原样写入，输入里的控制字符（如 `\x1b`）就进了日志文件。查看器若渲染 ANSI 转义序列，就会「执行」它。高发位置：记录用户名、URL、请求参数的日志字段；运维用 `cat` 直接看日志的场景。

**分类**：日志伪造（塞入假记录）、终端转义注入（塞入 ANSI 控制码改显示）。

**典型特征（怎么发现）**：
- 输入里含 `\x1b[` 等控制码后在终端查看出现异常显示。
- 日志里出现格式与程序输出不一致的「整行正常记录」。

**危害**：干扰审计、掩盖攻击痕迹、在特定场景误导运维（★低，因为通常只影响查看体验与审计准确性）。

**防护**：日志输出时转义控制字符；日志查看器禁用 ANSI 渲染；用结构化日志（JSON）并把用户数据放独立字段。

**易错点**：以为「危害小就不用防」——它常与其他漏洞组合，用来掩盖入侵痕迹（呼应第 0 章铁律三「漏洞链」）。

**微自测（演示样例，3 题：认出它 / 怎么防 / 易错点，形态 A）**

*题 1 · 认出它*｜材料：某字段名被写入日志，运维 `cat` 日志时终端标题被改成了一条假消息。
问：原因最可能是？
- A. 输入里的 ANSI 控制码被终端执行了 → ✔ 正确。解释：控制码随输入进了日志，查看时被终端当成指令渲染。
- B. 服务器被完全控制 → ✘ 错误。危害通常仅限显示层。
- C. 这是 XSS → ✘ 错误。发生在终端查看日志时，不是浏览器。
- D. 日志系统自动生成的 → ✘ 错误。是输入带进来的。

*题 2 · 怎么防*｜材料：日志系统要把用户名写进日志，开发给出四种改法：① 输出时转义控制字符 + 用结构化日志（JSON）把用户数据放独立字段；② 过滤 `\x1b[` 这几个字符；③ 把用户名缩短；④ 只加 WAF。
问：哪个是根治？
- A. ① 转义控制字符 + 结构化日志 → ✔ 正确。解释：控制字符到不了「被终端当指令执行」的位置，用户数据在独立字段里——根治。
- B. ② 过滤 `\x1b[` → ✘ 错误。控制码有多种写法，黑名单追不完。
- C. ③ 缩短用户名 → ✘ 错误。短字符串也能藏控制码。
- D. ④ 加 WAF → ✘ 错误。WAF 管不到日志查看环节。

*题 3 · 易错点*｜材料：开发说「这个洞危害才两星，不用管」。
问：产品口径怎么看？
- A. 危害低≠可忽略，它常用来掩盖其他攻击痕迹 → ✔ 正确。解释：★只说危害大小，且漏洞可串联（铁律三）。
- B. 两星以下都不用修 → ✘ 错误。没有这条规则。
- C. 危害低说明学习难度也低 → ✘ 错误。危害与难度是两个维度。
- D. 只加 WAF → ✘ 错误。根治是转义控制字符 + 结构化日志。

〔本章术语锚点〕`log-injection`、`ansi-escape`、`structured-logging`
